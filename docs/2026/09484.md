# [原创]【老树新枝】com接口过uac另类应用

一、概述

         近日在测试COM串链时发现，利用windows的程序与管理功能卸载某些进程时，意外的将我放在根目录下用来测试的Program.exe执行起来。

![](https://bbs.kanxue.com/upload/attach/201903/258629_3JENFC9MZ4W5BUQ.jpg)

![](https://bbs.kanxue.com/upload/attach/201903/258629_RKB42FCCZGB6N3F.jpg)

很明显微软在处理这里的时候没有严格的传递命令行，导致路径被空格截断，使得空格后面的路径被当作命令行执行。

测试环境

Win7 x86 sp1、 win10 x86 16193

测试工具

Procmon、procxp、ida、windbg等

二、COM接口绕过UAC的再利用

本次的方法和之前UACme提到到的利用控制面板启动卸载程序绕UAC的方法类似， 参考d39K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2X3M7X3g2W2j5Y4g2X3i4K6u0W2j5$3!0E0i4K6u0r3N6Y4g2D9M7#2)9J5c8U0p5^5x3K6V1I4y4q4)9J5k6h3S2@1L8h3H3`.

2.1原理

参考之前的分析，我们之间将断点设置在explorer.exe的Kernel32!CreateProcessW上，从控制面板中执行卸载程序，这时触发中断

![](https://bbs.kanxue.com/upload/attach/201903/258629_TZ93QZGNRCW5DPN.jpg)

可以看到是调用appwiz!CARPUninstallStringLauncher::LaunchUninstallStringAndWait接口进行提取操作

然后我们来看看CreateProcessW的参数

![](https://bbs.kanxue.com/upload/attach/201903/258629_8ACETFJ23PQPMPF.jpg)

可以很明显的看到，lpApplicationName参数已经被设成为D:\Program.exe，并且lpCommandLine也被设置为"D:\Program.exe" Files\\*\\*\UnInstaller.exe

我们来看看LaunchUninstallStringAndWait这个函数的实现。

![](https://bbs.kanxue.com/upload/attach/201903/258629_37AK3EEG9QATKBR.jpg)

调试后可以发现lpCommandLine与lpApplicationName都被SHEvaluateSystemCommandTemplate函数转换过，那么F5一下切换到伪代码看看。

![](https://bbs.kanxue.com/upload/attach/201903/258629_UE95WS5MJ4Z4RRR.jpg)

那么SHEvaluateSystemCommandTemplate函数是做什么的？查询MSDN的结果是

![](https://bbs.kanxue.com/upload/attach/201903/258629_6GNPT7A5H8DJR93.jpg)

函数是用于CreateProcess与ShellExecute的路径参数进行安全性检测，继续F5

![](https://bbs.kanxue.com/upload/attach/201903/258629_KSG3WMTFGEM2KBJ.jpg)

可以看到其实问题出在\_PathGetArgsLikeCreateProcess函数中，由于只是校验了找到的第一个分隔符，所以我们可以通过遍历注册表查找包含空格的卸载路径，然后将需要提权的文件放在带空格的目录的同级目录下（必须是第一个空格，这里按照第一个空格做分割）。

其实这个问题很好规避，及在写入注册表的时候添加双引号包含路径即可，不过这种历史遗留问题应该还有不少，不知道还有多少坑会被我们踩完
