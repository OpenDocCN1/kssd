
# Android 安全开发之浅谈密钥硬编码

作者：伊樵、呆狐@阿里聚安全

## 1. 简介

在阿里聚安全的漏洞扫描器和人工 APP 安全审计中，经常发现有开发者将密钥硬编码在 Java 代码或文件中，这样做会引起很大风险。信息安全的基础在于密码学，而常用的密码学算法都是公开的。加密内容的保密依靠的是密钥的保密；密钥如果泄露，对于对称密码算法，根据用到的密钥算法和加密后的密文，很容易得到加密前的明文；对于非对称密码算法或者签名算法，根据密钥和要加密的明文，很容易计算出签名值，从而伪造签名。

## 2. 风险案例

密钥硬编码在代码中，根据密钥用途的不同，会导致不同的安全风险：有的导致加密数据被破解，数据不再保密；有的导致和服务器通信的加签被破解，引发各种血案。以下借用乌云上已公布的几个 APP 漏洞来讲讲。

### 2.1 某互联网金融 APP 加密算法被破解，导致敏感信息泄露

某 P2P 应用客户端用于加密数据的 DES 算法密钥硬编码在 Java 代码中，而 DES 算法是对称密码算法，即加密密钥和解密密钥相同。

反编译 APP，发现 DES 算法：

![](https://bbs.kanxue.com/upload/attach/201605/666663_b4c9d2a401f0e9a8.png)

发现 DES 算法的密钥硬编码为“yrdAppKe”，用来加密手势密码：

![](https://bbs.kanxue.com/upload/attach/201605/666663_3f678b3e63798374.png)

将手势密码用 DES 加密后，存放在本地的`LocusPassWordView.xml`文件中：

![](https://bbs.kanxue.com/upload/attach/201605/666663_33124ec04dcb26d2.png)

知道了密文、加密算法以及密钥，通过解密操作，可以从文件中恢复出原始的手势密码，或者生成新的手势密码。

而与服务器通信时，接口中的 Jason 字段也用了 DES 算法，密钥硬编码为“yRdappKY”：

![](https://bbs.kanxue.com/upload/attach/201605/666663_65c5348cb40ee621.png)

![](https://bbs.kanxue.com/upload/attach/201605/666663_6b7a5eb017b75ac5.png)

和服务器通信采用 HTTP 传输，没有使用 HTTPS 加密通信。如果采用中间人攻击或者路由器镜像获取流量数据，就可以破解出用户的通信内容。

### 2.2 某租车 APP 加密算法被破解，导致一系列风险

某租车 APP 与服务器通信的接口采用 HTTP 传输数据，并且对传输的部分参数进行了加密。加密算法采用 AES，但是密钥硬编码在 Java 代码中，为“shenzhoucar123123”，可被逆向分析出来，导致伪造请求。结合服务器端的漏洞，会引起越权访问的风险，如越权查看其他用户的订单等。

和服务器通信时的数据为：

![](https://bbs.kanxue.com/upload/attach/201605/666663_b6f5c4a002953e53.jpg)

`q`字段是加密后的内容。逆向 APP，从登录`Activity`入手：

![](https://bbs.kanxue.com/upload/attach/201605/666663_00b7805c215af546.png)

分析登录流程：`v1`是用户名，`v2`是密码，`v3`是`PushId`。在用户名和密码不为空并且长度不小于 11 的情况下，执行`LoginOperate`相关操作。追踪`LoginOperate`的实现，发现其继承自`BaseOperate`，继续追踪`BaseOperate`的实现：

![](https://bbs.kanxue.com/upload/attach/201605/666663_e48f9c22e47a26e8.png)

在`BaseOperate`的`initUrl()`方法中，找到了 APP 生成请求数据的方式：

![](https://bbs.kanxue.com/upload/attach/201605/666663_5ee328cf32b51f81.png)

继续追踪上图中的`initJsonUrl()`方法，发现其调用了 AES 加密：

![](https://bbs.kanxue.com/upload/attach/201605/666663_4c3c6625c2439e2b.jpg)

继续追踪`aes.onEncrypt()`函数：

![](https://bbs.kanxue.com/upload/attach/201605/666663_9008e173b1ba7c97.png)

在`onEncrypt()`函数中调用了`encrypt()`函数来加密数据。追踪`encrypt()`函数的实现，发现其使用 AES 算法，并且密钥硬编码在 Java 代码中，为“shenzhoucar123123”。

![](https://bbs.kanxue.com/upload/attach/201605/666663_7a1a01bca02967fb.png)

到现在，请求中的数据加密是如何实现的就清晰了。另外，由于服务器权限控制不严，可以构造订单 ID 请求，达到越权访问其他用户订单的目的。

构造`{"id":"11468061"}`的请求：

![](https://bbs.kanxue.com/upload/attach/201605/666663_1be003a94bd70ab1.jpg)

其中`uid`设置为你自己的`uid`即可，可以成功看到其他人的订单：

![](https://bbs.kanxue.com/upload/attach/201605/666663_39001dc0c0f89b21.png)

攻击者完全可以使用其他脚本重新实现相同的加密功能并拼接出各个接口请求，批量刷取订单信息和用户其他信息。

### 2.3 某酒店 APP 加签算法被破解，导致一系列风险

某酒店 APP 和服务器通信时，接口采用 HTTP 通信，数据进行了加密，并且对传输参数进行签名。服务器端校验签名，以检查传输的数据是否被篡改。但是加签算法和密钥被逆向分析后，可导致加签机制失效。攻击者可任意伪造请求包，若结合服务器端的权限控制漏洞，则可引发越权风险等。

APP 和服务器通信的原始包如下图，可以看到有加签字段`sign`：

![](https://bbs.kanxue.com/upload/attach/201605/666663_a15d0e899e73efe9.png)

逆向 APP，定位到加密算法的逻辑代码`com.htinns.biz.HttpUtils.class`，其实现逻辑为：

![](https://bbs.kanxue.com/upload/attach/201605/666663_1817d81f3b26baf1.png)

原始数据是`unSignData`，使用 RC4 算法加密，密钥为`KEY`变量所代表的值，加密后的数据为`signData`，传输数据时的`data`字段为`signData`。

加签字段`signd`的生成方法是：将`unsignData`拼接时间戳`time`和`resultkey`，然后做 MD5，再进行 Base64 编码。时间戳保证了每次请求包都不一样。

`sendSign()`算法是用 C 或 C++ 写的，放入了 so 库，其他重要算法都是用 Java 写的。

可以使用 IDA 逆向分析 so 库，找到`sendSign()`方法：

![](https://bbs.kanxue.com/upload/attach/201605/666663_ac41ab563fec0d70.png)

而乌云漏洞提交者采用的是分析`sign`和`getSign(sign)`的数据，做一个算法破解字典。其实还有一种方法：直接调用此 so 库来生成字典。

签名破解以后，就可以构造发送给服务器的数据包，进行其他方面的安全测试，比如越权、重置密码等。

## 3. 阿里聚安全开发建议

通过以上案例，并总结自己平时发现密钥硬编码的主要形式有：

1. 密钥直接以明文存在 sharedprefs 文件中，这是最不安全的。
2. 密钥直接硬编码在 Java 代码中，这很不安全，dex 文件很容易被逆向成 Java 代码。
3. 将密钥分成不同的几段，有的存储在文件中，有的存储在代码中，最后将它们拼接起来，可以将整个操作写得很复杂。这仍然是在 Java 层，逆向者只要花点时间，也很容易逆向。
4. 用 NDK 开发，将密钥放在 so 文件中，加密解密操作都在 so 文件里。这在一定程度上提高了安全性，挡住了一些逆向者，但是有经验的逆向者还是会使用 IDA 破解。
5. 在 so 文件中不存储密钥，而是在 so 文件中对密钥进行加解密操作；将加密后的密钥命名为其他普通文件，存放在 assets 目录下或者其他目录下；接着在 so 文件里面添加无关代码（花指令）。虽然可以增加静态分析难度，但是可以使用动态调试的方法追踪加密解密函数，也可以查找到密钥内容。

保证密钥的安全确实是件难事，涉及到密钥分发、存储、失效回收、APP 防反编译和防调试，还有风险评估。可以说，在设备上安全存储密钥基本无解，只能选择增大攻击者的逆向成本，让攻击者知难而退。而普通开发者要妥善保护密钥，则需要耗费很大的心血。

产品设计者或者开发者要明白自己的密钥是做什么用的、重要程度怎么样、密钥被逆向出来会造成什么风险，并通过评估 APP 应用的重要程度来选择相应的技术方案。

所以建议不妨试试阿里聚安全的安全加固和安全组件。其中，安全组件中的安全加密功能提供了开发者密钥的安全管理与加密算法实现，保证密钥的安全性，实现安全的加解密操作；安全签名功能实现客户端请求的签名处理，保证客户端与服务端通信请求不被伪造。安全加固提升安全等级，防止应用被逆向破解。这样同时从应用层、运行层、Native 层提供多层次、全方位、立体防护。另外还有安全沙箱、白盒加密、底层加固，共同保证客户端数据安全。攻防是不断变化演进的，阿里聚安全提供的服务能实时更新客户端模块。通过阿里聚安全的漏洞扫描来检测应用是否具有密钥硬编码风险，可以保证在攻防对抗中永远处于上风。

专业的事情交给专业的人来做，自己的主要精力用来做功能开发或者业务逻辑，快速打造能赢得市场的可靠产品才是王道。
