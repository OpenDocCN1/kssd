

# Linux Kernel Debug设计浅析

## QEMU启动参数

Linux版本5.2.0-rc4

```bash
qemu-system-x86_64 -smp 4 -kernel bzImage -m 4096 -hda ~/stretch.img -serial stdio -append "earlyprintk=serial console=ttyS0 kgdboc=ttyS0 kgdbwait root=/dev/sda nokaslr" -enable-kvm -cpu host -s -S -display none
```

启动后效果如下：

![图1](https://bbs.kanxue.com/upload/attach/201907/603450_QYHU9ZDB2GK9Z6B.png)

得到一个可以交互的Kernel Debug。这里是KDB的命令行，并不是KGDB的部分，后面会说明它们之间的关系。

此时在调试端按`Ctrl + C`中断，看到此时KDB的栈回溯。

![图2](https://bbs.kanxue.com/upload/attach/201907/603450_7EFVXAP4VC6C24Z.png)

## 内核命令行参数分析

图2看到KDB是从一个`int3`中断进入的。分析参数后发现是`kgdbwait`参数最后调用`kgdb_breakpoint()`，也就是`int 3`的原因。

![图3](https://bbs.kanxue.com/upload/attach/201907/603450_G2ZQ7YSGTWWU2AR.png)

从`int3`中断向上找关键函数，发现`kgdb_cpu_enter()`是KDB的入口。重启虚拟机对`kgdb_cpu_enter()`下断点，发现`kgdb_cpu_enter()`并不是只中断一次。

![图4](https://bbs.kanxue.com/upload/attach/201907/603450_QEGN3BHEW2NAWPD.png)

这次是从`nmi`中断进入的，也就是还有代码给CPU发送了一个`nmi`导致。最后找到是`kgdb_cpu_enter()`发送的NMI中断。

![图5](https://bbs.kanxue.com/upload/attach/201907/603450_WYENVRSA8EXQU5G.png)

代码给了解释。原来是`int3`中断只能让一个核进入KDB。对于多核系统，仅让一个核进入KDB而其他核正常运行显然不合理，所以要让所有核都进入KDB。`kgdb_cpu_enter()` → `kdb_stub()` → `kdb_main_loop()` → `kdb_parse()`，执行对应每个命令的处理函数。

![图6](https://bbs.kanxue.com/upload/attach/201907/603450_QPVVZBJDNTASVRG.png)

为了能用从QEMU动态抓到这个过程，需要修改QEMU的启动参数。

![图10](https://bbs.kanxue.com/upload/attach/201907/603450_8PB97DRB7JUNQ4J.png)

又增加了一个串口，第一个串口`ttyS0`用于打印内核启动流程，`ttyS1`用于建立GDB和内核之间的连接。所以除了用`target remote localhost:1234`连接的调试，还可以用`target remote /dev/pts/3`连接。这样就可以从第一个GDB中看到第二个的连接过程和处理逻辑。
