## 正文开始
关于CVE-2017-8890的原理分析已经有好几位前辈分析过了，本文也做一个简单的总结。首先会从补丁分析一下漏洞的成因，其次会从调试的角度验证之前分析的内容。
## 漏洞原理
通过该漏洞的patch，我们可以看到在 <a href="elink@ffbK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4K9i4c8Z5N6h3u0Q4x3X3g2U0L8$3#2Q4x3V1k6@1L8%4u0$3j5h3I4V1M7#2)9J5c8X3I4A6L8Y4g2^5i4K6u0r3j5$3!0E0L8h3W2@1i4K6u0r3y4U0f1%4z5o6x3I4k6X3k6U0x3K6S2W2x3K6l9H3z5e0u0S2x3X3b7#2k6U0l9K6k6o6x3^5y4h3b7%4x3e0m8W2j5U0R3^5j5U0l9&6j5g2)9K6c8X3c8A6k6X3k6Q4x3@1c8#2L8X3W2X3K9h3g2V1i4K6t1K6k6r3W2X3k6W2)9J5k6o6x3&6y4K6y4X3x3X3p5H3z5e0W2V1y4K6g2T1x3h3g2U0z5h3j5%4k6X3f1$3z5o6k6U0k6o6l9%4z5e0k6S2">net/ipv4/inet\_connection\_sock.c</a>中，增加了对于mc\_list的置NULL操作。newsk是一个sock的结构体指针（struct sock \*newsk）。
![Alt text](./upload/attach/201901/730610\_79P5BVQ5SMUYVU3.png)
通过查看sock结构体在kernel4.10.0中的源码，可知mc\_list是ip\_mc\_socklist的结构体指针。所以我们可以确定ip\_mc\_socklist就是存在问题的结构体。
![Alt text](./upload/attach/201901/730610\_WB8W9BNCYP5EMPN.png)
为什么要对mc\_list置NULL呢？这得看一下inet\_connection\_sock.c中inet\_csk\_clone\_lock的功能。该函数的调用过程如下，引用云图信安文章中用understand生成的调用流程图：
![Alt text](./upload/attach/201901/730610\_6XBJ9YHGG4F3PGP.png)
这里对以上函数做简单分析（现在感觉用处不大），具体的过程可以看源码实现：
- 源头是tcp\_v4\_rcv这个函数。tcp\_v4\_rcv中调用了 tcp\_check\_req。
- <a href="elink@5e6K9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8Y4N6%4N6#2)9J5k6h3I4A6L8Y4g2^5K9h3c8U0i4K6u0W2j5$3!0E0i4K6u0r3e0r3W2F1N6i4S2Q4x3V1j5J5x3o6p5K6i4K6u0V1x3o6u0Q4x3V1j5%4z5e0R3#2z5i4l9@1i4K6u0W2K9s2c8E0">tcp\_check\_req</a>会检查包是否正确，会return一个新建立的socket。
- tcp\_check\_req是调用 tcp\_v4\_syn\_recv\_sock来实现的，<a href="elink@349K9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8X3u0D9L8$3N6Q4x3X3g2U0M7$3c8F1i4K6u0W2L8X3g2@1i4K6u0r3P5X3S2S2L8X3N6K6K9$3c8Q4x3V1k6S2M7Y4c8A6j5$3I4W2i4K6u0r3k6r3g2@1j5h3W2D9M7#2)9J5c8U0p5%4z5e0p5%4y4o6l9I4">tcp\_v4\_syn\_recv\_sock</a>里面会初始化和创建一个新的socket。
- tcp\_v4\_syn\_recv\_sock 是调用tcp\_create\_openreq\_child 来实现的。 tcp\_create\_openreq\_child(sk, req, skb)根据监听sock和req，为新连接创建一个传输控制块，并初始化。
- tcp\_create\_openreq\_child是调用 inet\_csk\_clone\_lock来实现的。该函数会创建一个socket，其实是根据父socket来创建child socket。
到这里已经定位到了`inet\_csk\_clone\_lock`函数。看一下源码：
![Alt text](./upload/attach/201901/730610\_76ZSUFKS7NRKUGM.png)
这个函数在clone sk给newsk时，通过调用链：`inet\_csk\_clone\_lock -> sk\_clone\_lock(sk, priority)->sock\_copy(newsk, sk);`来完成对sk的拷贝。拷贝完成后没有对mc\_list初始化，因此在newsk和sk中存在同一个指向ip\_mc\_socklist的结构体指针。
总结一下目前的漏洞原因：根据PATCH代码分析，在建立socket连接时，由父socket copy数据 给子 socket，mc\_list这个ip\_mc\_socklist类型的结构体指针没有被置为NULL，因此子socket中存在对父socket中数据的引用。
## POC
由于是double free的漏洞，写POC时，必然要对mc\_list进行创建和二次释放。创建和释放的过程需要通过understand找关于mc\_list的引用。细节还是参考云图信安的文章[1]吧。不重复赘述了。

释放过程：
![Alt text](./upload/attach/201901/730610\_TRCQRZ3KXXX7EXD.png)
POC伪代码:
```c
sockfd = socket(AF\_INET, xx, IPPROTO\_TCP);
setsockopt(sockfd, SOL\_IP, MCAST\_JOIN\_GROUP, xxxx, xxxx);
bind(sockfd, xxxx, xxxx);
listen(sockfd, xxxx)
newsockfd = accept(sockfd, xxxx, xxxx);
close(newsockfd);// first free (kfree\_rcu)
sleep(5);// wait rcu free(real first free)
close(sockfd);// double free
```
创建一个socket并加入组播模式（MCAST\_JOIN\_GROUP），这时socket中存在mc\_list结构体，监听该socket，并用accept等待连接。建立连接时，会创建新的子sokcet，其中依然存在父socket的mc\_list结构体。关闭新的socket，这时等待RCU机制的的宽限期结束后，在rcu回调函数中触发第一次kfree。之后关闭父socket，同样的位置触发第二次free。（也就是两次free的位置都是相同的，之前被别的文章误导了）

### mc\_list 的free过程
- ip\_mc\_drop\_socket
mc\_list在这个函数里面释放。由于mc\_list是一个单链表，通过next\_rcu来索引下一个mc\_list。因此在释放的时候，会循环遍历这个链表。此外，由于mc\_list是ip\_mc\_socklist的结构体，引用了rcu机制（正常采用rcu机制保护的结构体中会有struct rcu\_head rcu; 这个成员）因此对于该结构体写比较特殊（释放也可以理解为是写过程）。
简单来说可以理解为当有一个线程要对该成员写时，开始一个宽限期，等到所有读的线程结束后，宽限期结束，通过触发时钟中断检查是否存在回调函数，如果存在回调函数，则在回调函数中写。简单的rcu机制可以参考这篇文章：<a href="elink@37fK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6T1L8r3!0Y4i4K6u0W2j5%4y4V1L8W2)9J5k6h3&6W2N6q4)9J5c8Y4c8Z5K9h3&6C8i4K6g2X3P5h3y4^5i4K6u0r3j5i4u0@1K9h3y4D9k6g2)9J5c8X3c8W2N6r3q4A6L8s2y4Q4x3V1j5^5x3e0p5#2y4e0j5%4x3R3`.`.">浅析linux kernel RCU机制</a>

最终根据oops信息发现kernel在`ip\_mc\_leave\_src`中出现了空指针引用的错误（位于第二次free的调用链中）。
在第一次mc\_list释放后，这块dirty内存的数据就可能会其它线程使用了。根据源码和反汇编代码分析可知，指针psf是iml->sflist处的值，即[mc\_list+0x18]，地址存在rbx中，rbx的值为0x2。从mc\_list中取出psf后，ip\_mc\_leave\_src中引用了psf->sl\_count导致了空指针引用。
`mov ecx,DWORD PTR [rbx+0x4] //arg4 psf->sl\_count`

## 漏洞原理

通过该漏洞的patch，我们可以看到在 [net/ipv4/inet\_connection\_sock.c](https://bbs.kanxue.com/elink@936K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4K9i4c8Z5N6h3u0Q4x3X3g2U0L8$3#2Q4x3V1k6@1L8%4u0$3j5h3I4V1M7#2)9J5c8X3I4A6L8Y4g2^5i4K6u0r3j5$3!0E0L8h3W2@1i4K6u0r3y4U0f1%4z5o6x3I4k6X3k6U0x3K6S2W2x3K6l9H3z5e0u0S2x3X3b7#2k6U0l9K6k6o6x3^5y4h3b7%4x3e0m8W2j5U0R3^5j5U0l9&6j5g2)9K6c8X3c8A6k6X3k6Q4x3@1c8#2L8X3W2X3K9h3g2V1i4K6t1K6k6r3W2X3k6W2)9J5k6o6x3&6y4K6y4X3x3X3p5H3z5e0W2V1y4K6g2T1x3h3g2U0z5h3j5%4k6X3f1$3z5o6k6U0k6o6l9%4z5e0k6S2)中，增加了对于mc\_list的置NULL操作。newsk是一个sock的结构体指针（struct sock \*newsk）。
![Alt text](https://bbs.kanxue.com/./upload/attach/201901/730610_79P5BVQ5SMUYVU3.png)

通过查看sock结构体在kernel4.10.0中的源码，可知mc\_list是ip\_mc\_socklist的结构体指针。所以我们可以确定ip\_mc\_socklist就是存在问题的结构体。
![Alt text](https://bbs.kanxue.com/./upload/attach/201901/730610_WB8W9BNCYP5EMPN.png)
为什么要对mc\_list置NULL呢？这得看一下inet\_connection\_sock.c中inet\_csk\_clone\_lock的功能。该函数的调用过程如下，引用云图信安文章中用understand生成的调用流程图：
![Alt text](https://bbs.kanxue.com/./upload/attach/201901/730610_6XBJ9YHGG4F3PGP.png)
这里对以上函数做简单分析（现在感觉用处不大），具体的过程可以看源码实现：

- 源头是tcp\_v4\_rcv这个函数。tcp\_v4\_rcv中调用了 tcp\_check\_req。
- [tcp\_check\_req](https://bbs.kanxue.com/elink@68cK9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8Y4N6%4N6#2)9J5k6h3I4A6L8Y4g2^5K9h3c8U0i4K6u0W2j5$3!0E0i4K6u0r3e0r3W2F1N6i4S2Q4x3V1j5J5x3o6p5K6i4K6u0V1x3o6u0Q4x3V1j5%4z5e0R3#2z5i4l9@1i4K6u0W2K9s2c8E0)会检查包是否正确，会return一个新建立的socket。
- tcp\_check\_req是调用 tcp\_v4\_syn\_recv\_sock来实现的，[tcp\_v4\_syn\_recv\_sock](https://bbs.kanxue.com/elink@18aK9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8X3u0D9L8$3N6Q4x3X3g2U0M7$3c8F1i4K6u0W2L8X3g2@1i4K6u0r3P5X3S2S2L8X3N6K6K9$3c8Q4x3V1k6S2M7Y4c8A6j5$3I4W2i4K6u0r3k6r3g2@1j5h3W2D9M7#2)9J5c8U0p5%4z5e0p5%4y4o6l9I4)里面会初始化和创建一个新的socket。
- tcp\_v4\_syn\_recv\_sock 是调用tcp\_create\_openreq\_child 来实现的。 tcp\_create\_openreq\_child(sk, req, skb)根据监听sock和req，为新连接创建一个传输控制块，并初始化。
- tcp\_create\_openreq\_child是调用 inet\_csk\_clone\_lock来实现的。该函数会创建一个socket，其实是根据父socket来创建child socket。
  到这里已经定位到了`inet_csk_clone_lock`函数。看一下源码：
  ![Alt text](https://bbs.kanxue.com/./upload/attach/201901/730610_76ZSUFKS7NRKUGM.png)
  这个函数在clone sk给newsk时，通过调用链：`inet_csk_clone_lock -> sk_clone_lock(sk, priority)->sock_copy(newsk, sk);`来完成对sk的拷贝。拷贝完成后没有对mc\_list初始化，因此在newsk和sk中存在同一个指向ip\_mc\_socklist的结构体指针。

总结一下目前的漏洞原因：根据PATCH代码分析，在建立socket连接时，由父socket copy数据 给子 socket，mc\_list这个ip\_mc\_socklist类型的结构体指针没有被置为NULL，因此子socket中存在对父socket中数据的引用。

由于是double free的漏洞，写POC时，必然要对mc\_list进行创建和二次释放。创建和释放的过程需要通过understand找关于mc\_list的引用。细节还是参考云图信安的文章[1]吧。不重复赘述了。

POC伪代码:

```
sockfd = socket(AF_INET, xx, IPPROTO_TCP);
setsockopt(sockfd, SOL_IP, MCAST_JOIN_GROUP, xxxx, xxxx);
bind(sockfd, xxxx, xxxx);
listen(sockfd, xxxx)
newsockfd = accept(sockfd, xxxx, xxxx);
close(newsockfd);// first free (kfree_rcu)
sleep(5);// wait rcu free(real first free)
close(sockfd);// double free
```

创建一个socket并加入组播模式（MCAST\_JOIN\_GROUP），这时socket中存在mc\_list结构体，监听该socket，并用accept等待连接。建立连接时，会创建新的子sokcet，其中依然存在父socket的mc\_list结构体。关闭新的socket，这时等待RCU机制的的宽限期结束后，在rcu回调函数中触发第一次kfree。之后关闭父socket，同样的位置触发第二次free。（也就是两次free的位置都是相同的，之前被别的文章误导了）

### mc\_list 的free过程

- ip\_mc\_drop\_socket

mc\_list在这个函数里面释放。由于mc\_list是一个单链表，通过next\_rcu来索引下一个mc\_list。因此在释放的时候，会循环遍历这个链表。此外，由于mc\_list是ip\_mc\_socklist的结构体，引用了rcu机制（正常采用rcu机制保护的结构体中会有struct rcu\_head rcu; 这个成员）因此对于该结构体写比较特殊（释放也可以理解为是写过程）。

简单来说可以理解为当有一个线程要对该成员写时，开始一个宽限期，等到所有读的线程结束后，宽限期结束，通过触发时钟中断检查是否存在回调函数，如果存在回调函数，则在回调函数中写。简单的rcu机制可以参考这篇文章：[浅析linux kernel RCU机制](https://bbs.kanxue.com/elink@a39K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6T1L8r3!0Y4i4K6u0W2j5%4y4V1L8W2)9J5k6h3&6W2N6q4)9J5c8Y4c8Z5K9h3&6C8i4K6g2X3P5h3y4^5i4K6u0r3j5i4u0@1K9h3y4D9k6g2)9J5c8X3c8W2N6r3q4A6L8s2y4Q4x3V1j5^5x3e0p5#2y4e0j5%4x3R3`.`.)
