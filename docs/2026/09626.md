# [原创]修改vft设置MFC程序的属性页字体

前几天因为工作关系要用到IAR Embedded workbench for ARM(EWARM), 然后经常的修改编译选项, 所以对工程选项对话框的MS Sans Serif字体看的很不顺眼; 这要不改掉, 简直没法干活了!
首先是把一堆带对话框资源的语言文件丢到Sisulizer里面批量改了字体, 然后替换以后, 点开一看, 左边的列表变Tahoma了, 右边的选项卡还一直保持着MS Sans Serif.
看起来不妙啊. 于是拽出了ApiMonitor, 勾了CreateFont和CreateFontIndirect四个函数.
然后启动改造版的LibSpy, 查看右边选项页的字体.

![](https://bbs.kanxue.com/upload/attach/201212/670_4acfddtj7yga2ew.png)

将hFont的值填入ApiMonitor搜索, 这个选项卡果然是ComCtl32的属性卡.

![](https://bbs.kanxue.com/upload/attach/201212/670_3rn29re4u54j2zr.png)

看到这里懂行的可能要说了, MS Shell Dlg不是会自动映射为Tahoma或者Segoe UI么? 这个解释起来就不是三言两语能说清的了, 这里最后显示用的是Microsoft Reference Sans Serif, 可以看成是开了抗锯齿的MS Sans Serif.
调用MFC90的地址是10042300+0x2521B = 1006751B, 因为ApiMonitor只能识别导出表, 这里的函数名并不是代码所在的函数.

从Call Stack可以看出, 是CreatePropertySheetPage时候, 从对话框资源读到的, 当然这个对话框资源, 就是WinSxs和System32下面的comctl32.dll.
用了v6以上的就是WinSxs, 否则是System32目录下的.

在以前的系统, 我是直接修改这comctrl32文件里面的对话框字体的, 但是后来看到过MSDN blog上的一篇文章, 介绍了因为历史失误, 选项卡显示出来后和资源按编辑器中大小不一致, 边缘被裁掉, 导致很多软件作者在使用选项卡时候, 反向拉伸对话框来撑到正确尺寸, 当然基本所有程序选项卡中显示字体都是Microsoft Reference Sans Serif (由MS Shell Dlg匹配而来), 除非特地处理了字体.
所以我以前那样改了以后, 字体是变到我想要的Tahoma了, 但是那些针对缩放bug做了放大的程序, 属性页会变大, 当年在群里也讨论了半天, 也没整出个两全其美的办法.
PS: 微软在CPropertySheet的构造和DoModal里用DS\_SHELLFONT标志来指定自身不使用缩放workaround, 另外提供了一个PrpFont例子来演示修改字体, 就是派生自己的类, 重载CPropertySheet的OnInitDialog函数, 查找所有子控件并修改字体.
不过我们这里没有代码, 要修改的话, 直接修改这个创建链条中的任一环节, 也就是修改ProjectManagerGui.dll, mfc90.dll, comctl32.dll之中任意一个, 应该可行.
剩下还有个另外的方法, 就是重载这个纯虚函数, 正好我们有一个语言文件, ProjectManagerGui.ENU.dll, 先看看是什么方式使用的吧, 是LoadLibrary还是LoadLibraryEx的DATAFILE方式.
照样请出ApiMonitor, 监视LoadLibrary/EX这四个函数, 可以看到是IdeFramework.dll载入ProjectManagerGui.dll时候他直接用LoadLibraryA载入的.

![](https://bbs.kanxue.com/upload/attach/201212/670_d08o3535r1h3qum.png)

LordPE查看ProjectManagerGui.ENU.dll, 是一个没有入口代码的纯资源dll.
因为LoadLibrary没有办法指定只加载资源, 这样我们可以把代码加到资源dll里面, 载入时候hook掉已经在内存中的ProjectManagerGui.dll.
先去看看第一次的CallStack发起的地方, 也就是前面算出来的1006751B,

我们感兴趣的是末尾这三个函数, 不过因为这个程序的选项页没有尺寸问题, 而Create和DoModal时候, 窗体句柄尚未附加, 设置字体无效, 所以还是去搞OnInitDialog比较好.
因为MyPropertySheet\_\_OnInitDialog是通过mfc的dll调用的, 所以不好找到call的地方修改成call我们的函数, 要是原来我可能就用改掉MyPropertySheet\_\_OnInitDialog前面几个字节去跳转的方式, 不过今天决定试一试补丁掉vft, 也就等于派生了一个没有添加成员变量, 只重载了OnInitDialog的类.

```
__declspec(naked) BOOL __stdcall my_FooPropSheetOnInitDialog( /*CPropertySheet *Self,*/ )
{
    __asm {
        PUSH ECX
        PUSH FALSE
        PUSH TRUE
        PUSH TRUE // lParam (redraw)
        PUSH DWORD PTR [gSheetTahoma] // wParam (font)
        PUSH WM_SETFONT // Message
        PUSH DWORD PTR [ECX+0x20] // m_hWnd
        CALL CWnd::SendMessageToDescendants
        POP ECX

        // use call instead jmp coz no stack argument
        CALL [gfPrjMgrGui_FooPropSheetOnInitDialog]

        RETN
    }
}
```


这个代码就相当于这样

```
BOOL MyFooPropertySheet::OnInitDialog()
{
    // Tell all dialog controls what font to use
    SendMessageToDescendants (WM_SETFONT, (WPARAM)gSheetTahoma, 1, TRUE, FALSE);
    return FooPropertySheet::OnInitDialog();
}
```



附带一提, \_\_declspec(naked)有返回值类型后面和写在返回值类型前面两种写法, 但是当返回值类型不是基础数据类型时候, 就得写在返回值类型前面.
另外对于经过修饰, 带有奇怪符号的CWnd::SendMessageToDescendants函数(修饰后名称?SendMessageToDescendants@CWnd@@SGXPAUHWND\_\_@@IIJHH@Z), 可以把调用的地方写在asm文件里, 用extern proto的方式, 也可以声明个变量, 用GetProcAddress的方式, 不过这里我选择了创建一个结构/类, 添加成员函数名的方式.
在undname中得到如下结果
Undecoration of :- "?SendMessageToDescendants@CWnd@@SGXPAUHWND\_\_@@IIJHH@Z"
is :- "public: static void \_\_stdcall CWnd::SendMessageToDescendants(struct HWND\_\_ \*,unsigned int,unsigned int,long,int,int)"
实际上这个函数是inline方式, 实现部分在wincore.cpp可以看到, 基本就类似于PrpFont中, 循环给子窗口发消息.
这也是选择这个函数的原因.
创建好的占坑类如下

```
struct CWnd {
    // Original is inline wrapper to call static function in wincore.cpp
    static void PASCAL SendMessageToDescendants(HWND hWnd, UINT message,
                                               WPARAM wParam, LPARAM lParam, BOOL bDeep, BOOL bOnlyPerm);
};
```



也可以用class + public, 效果一样. 名称修饰是不区分class/struct/namespace和返回值类型的.
为什么不直接包含atlwin.h, 因为我们建立的工程不是MFC工程, 改为MFC后dll会变大好不爽.
这样链接的时候, linker就会去寻找?SendMessageToDescendants@CWnd@@SGXPAUHWND\_\_@@IIJHH@Z这个符号, 我们再把mfc90.lib加到工程的链接选项里面.
编译成dll, 用CodeInjector注入, 查看工程选项卡, Tab标题已经变成了想要的Tahoma, 不过下面的各种选择框还是原来的样子.
没关系, 因为我们还没处理PropertyPage.

找PropertyPage时候, 发现实际上有六个派生类, 为了不涉及无辜, 还是只hook一个吧, 经过6次测试, 最后一个就是工程选项的PropertyPage回调的地方.

![](https://bbs.kanxue.com/upload/attach/201212/670_7yfpj2xdkylpbp2.png)

注入后的样子, Microsoft Reference Sans Serif可耻的消灭了.
另外顺便一提, 我们是处理的没有用栈传递参数的回调函数, 所以可以直接再次call, 压入的地址不会破坏原来的参数列表, 做完我们的事情, 最后末尾调用父类函数的情况, 可以直接jmp, 栈顶保留的调用方的返回地址会被父类函数使用.
不过如果有需要一开始就调用父类函数, 还需要额外使用堆栈的情况, 要么就是一个一个push [esp+4], 因为每次push后esp都会自增所以重复参数数量-1次即可, 不过这样就等于增加了一次栈的深度.
还有个办法, 就是这样

```
        MOV DWORD PTR[ESP], offset label_magicret
        JMP [gfPrjMgrGui_FooPropSheetCtor] // will return to next line
label_magicret:
```


这样jmp后, 父类函数的RETN取到的就是我们的地址, 实际返回的是label\_magicret下面这行, 而这下一行的堆栈就和返回调用处地址时候一样的布局了, 可以继续执行我们的代码, 在末尾再直接跳回去原来的返回地址.

注入证实可用以后, 就开始做资源替换版的. 用Restrator把资源从语言文件里解出来, 加到工程中.
编译后, 替换原文件, 运行成功, 不过关闭时候, 出现一个MFC处理Terminate中的异常. 经过反复测试, 是hook代码地方出的问题.
在获取ProjectManagerGui.dll的地址以便补丁vft时候, 一开始是用的GetModuleHandle不带路径, 然后复制了一份带路径的是LoadLibrary, 这样这个ProjectManagerGui.dll的生命周期要出问题.
改成GetModuleHandle带完整路径后, 变成另外的异常, 读写异常.
因为一开始设计的是注射, 所以注射和取消注射时候, ProjectManagerGui.dll都在内存中, 而程序终止时候就不一样了. 再次修改拆除hook的函数, 判断是程序终止, 就跳过拆除hook.
世界终于清静了~~~
附带的idb和工程, 对应最新的IAR EWARM 6.40版的, 可以用来做为类似的重载虚函数参考.
其中Debug/Release模式都是输出hook用的dll, shipping模式是编译包含资源的替换dll, 同时还去掉了日志, 增加了pushad.
为了避免在多线程调用时候, dll入口函数反复调用不停地补丁和恢复, 还调用了DisableThreadLibraryCalls.
