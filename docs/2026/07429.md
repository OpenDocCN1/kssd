
# 分享一下win10rs5的PatchGuard部分攻击方法

系统环境是win10 1809 17763.437

我没有研究怎么解密上下文，我主要是想办法得到Pg蓝屏时候的堆栈，然后根据对应的方法找对应的攻击措施。

对于dpc例程来说，最有帮助来判断是不是pg的dpc就是`DefferContext`，很多资料都提了。

首先我做的是hook `KiDispatchException`，一方面是能够更快的触发PG，另一方面是在PG接手异常前，`DbgBreakPoint()`，让调试器接管，这样就可以得到PG调用的堆栈。在`KiDispatchException`中我们可以判断`rip`，`rbx`，`rdx`。大多数通过异常触发DPC都是触发`KiCustomRecurseRoutinex`这里，但是不管你是把`rip`跳过那条异常指令还是给一个合法的寄存器让他解引用来绕过异常，后面都还是会出另一个异常，而且有时候会连续验证2次。![](https://bbs.kanxue.com/upload/attach/202108/865434_VSBC4D4KJ4Y7EF7.jpg)

PatchGuard会在`\_except`块里恢复寄存器，然后再执行这个函数正常的功能。也就是说没有执行他的except块后面正常执行的时候还是会蓝屏。

下面是其中一次的堆栈，

![](https://bbs.kanxue.com/upload/attach/202108/865434_KWVK6US4E7YBAWR.jpg)

上面是其中一种，攻击方法是hook `KiProcessExpiredTimerList`，

![](https://bbs.kanxue.com/upload/attach/202108/865434_GFTV4MAUGJBYBKC.jpg)

原理是替换一个垃圾DPC让Pg执行。我一开始还想过hook `\_guard\_dispatch\_icall`来处理所有的函数指针调用，发现一hook就死机，不管是虚拟机还是主机都一样。

在打第二次虚拟机快照的时候，Pg又蓝屏了。这一次他并没有通过异常，也没用DPC。我想了一会没想出来他是怎么触发的。

然后我从PG的上下文内存分配入手，一开始我什么也不知道，就直接hook `ExallocatePoolWithTag`来试一下，在所有分配大字节全部断下

![](https://bbs.kanxue.com/upload/attach/202108/QKUE5FCVB7DWFVG.jpg)

然后看堆栈，因为pg执行是没有模块并且临时分配的，windbg肯定识别不出名字，把堆栈过滤一下，一个个排除可疑线程，结合IDA，能够断到这里来

![](https://bbs.kanxue.com/upload/attach/202108/865434_CPPJRZBPBN2ZSGD.jpg)

![](https://bbs.kanxue.com/upload/attach/202108/865434_JW3BEVVQST8EK6V.jpg)

![](https://bbs.kanxue.com/upload/attach/202108/865434_8Z45SJG3QBYY7SH.jpg)

这个函数特征码`8B 81 F8 07 00 00 0F 31 48 C1 E2 20`，我把这个函数叫`PgAllocateContext`，第一个参数就是上一次或全局上下文，作用是分配新的上下文准备验证。从这里可以看到PatchGuard至少有2种内存分配，后面好像还一种，但是又好像没什么关系。一个`MmAllocateIndependentPages`，一个`ExAllocatePoolWithTag`，`MmAllocateIndependentPages`这个除了pg一般系统函数用不到，而且绝大部分是用`ExAllocatePoolWithTag`分配的。一般情况，PG在系统开机时候生成一个或多个上下文，然后验证的时候，再临时分配新上下文并且马上开始验证，但是，有时候pg不临时分配context，看后面还有一种情况。还有pg调用函数都是通过`KeGuardDispatchIcall`用context内容跟作为索引来调用的。

既然我们断到了那个pg分配上下文的线程，我们就记住这个线程地址，然后恢复虚拟机快照直接找这个线程，因为pginit在开机就被调用了，他的验证手段选择完了，如果他选择是单独的一条线程，那他没验证的时候一定是通过某个方法在等待执行。

![](https://bbs.kanxue.com/upload/attach/202108/865434_3EEVHF2FRATSJBN.jpg)

上图就是pg的线程，可以看到入口点是`ExpWorkerThread`，我不知道这是pg插了一个apc进去执行的，还是他就是一条单独的system thread，伪造了入口点，但是都不重要。结合IDA，我们可以看到线程停

![](https://bbs.kanxue.com/upload/attach/202108/865434_CJNKZTVKBTPPEND.jpg)

在`FsRtlMdlReadCompleteDevEx`，这条线程就在这里调用`WaitForObject`，停住了，过几分钟就开始验证，然后蓝屏。

为了找到这条线程，我给每条系统线程插一个APC，堆栈回溯，检测他的返回地址，

```
RtlWalkFrameChain(stack, 10, 0);
```

![](https://bbs.kanxue.com/upload/attach/202108/865434_5QTME22DTXE9VZR.jpg)

`0x45d23345`就是`xor r10d,r10d    test r13d,r13d`，如果检测到了，就让他一直等。

![](https://bbs.kanxue.com/upload/attach/202108/865434_M3UZF2HYRQPBKJU.jpg)

上图第三个快照出的问题，可以看到是`KiSwInerruptDispatch`的问题，这个函数我下断点，一直断不下来，也就是说操作系统可以不需要函数，于是

![](https://bbs.kanxue.com/upload/attach/202108/865434_EUEW5X9RJRT74KW.jpg)

这里的`call rax`，我给`nop`了，然后pg问题确实可以解决，系统也能正常运行。

第四个有问题的快照，蓝屏的时候我也不知道哪里有问题，下内存分配的函数断点也没用。

![](https://bbs.kanxue.com/upload/attach/202108/865434_244TT4TGNUN4MST.jpg)

如上图，一般来说pg分配内存的时候，A是一个随机大小，B就是以`CmpAppendDllSection`开头的context，也就说真正的context不是页对齐的，但是我的实验表明他会是一个页不到的随机偏移，这也就是给`ExAllocatePoolWithTag`分配的big pool的第一个页的pte最高位置no excute能够断到`CmpAppendDllSection`执行的原因。

![](https://bbs.kanxue.com/upload/attach/202108/865434_967N73S939Z9G9W.jpg)

但是这个快照不是这样，这个快照验证的时候没有再分配内存，用的是上次的或一直存在于系统的上下文，那么就有个机会，也是我偶然发现的，这个109bugcheck的时候，通过magic number我们能找到这次蓝屏的context位置。我们恢复快照，因为这个context是打快照之前就存在了的，直接在这个context下硬件执行断点，可以断下来，断下来按`k`也可以获得此次的调用堆栈。其他验证手段这种方法都不行，因为临时分配context的话可能由于`Exallocatepoolwithtag`算法能够分配到同一个页，但是由于`rdtsc`导致每次`CmpAppendDllSection`相对于这个页的偏移不一样。下图是此次堆栈

![](https://bbs.kanxue.com/upload/attach/202108/865434_P42YV3TMUT2XN9Z.jpg)

![](https://bbs.kanxue.com/upload/attach/202108/865434_9XN94MEA4KZGEU5.jpg)

这个快照的解决方法是`KiExecuteAllDpcs`，替换函数指针，跟第一个一样。

pg大部分都是这几种方法，又打了2个快照触发不了就没搞了。
