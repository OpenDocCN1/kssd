## 0. 调试前准备工作

### 0.1 随机基址

- 用 `OD` 打开程序后，发现进入程序主逻辑后地址不是从 `0x00400000` 开始的，所以肯定不是固定基址。打开 `010Editor` 修改随机基址标志位（`PE` 标志下数一行零六个），由 `0x02` 改为 `0x03`，方便以后调试和分析：

![图片描述](upload/attach/201710/751258\_mn62wevgvy9ptay.png)

### 0.2 定位窗口回调

- 定位窗口回调我是一步步跟的，因为在窗口销毁之前的都是系统函数，也没有什么好说的。

- 跟到 `0x0043D39D` 那里后程序跑了起来，所以证明窗口回调是在这里注册的。

- 跟进去后发现了 `DialogBoxParamA` 这个 API，这就是在注册窗口回调。根据参数看到注册的窗口回调地址为 `0x0042E1A3`：

![图片描述](upload/attach/201710/751258\_iztx1j46n7507tt.png)

![图片描述](upload/attach/201710/751258\_rc71hwt43cnol4b.png)

- 这个地址是一个 `jmp 00434EF0`，说明程序是 `Debug` 版编译的（搞不清楚作者为什么要编译 `Debug` 版程序）。废话不多说了，找到了窗口回调，就可以开始分析程序了。

## 1. 反调试

### 1.1 运行检查

- 用 `IDA F5` 大法分析窗口回调中的代码：

![图片描述](upload/attach/201710/751258\_b4yhffqqzcsh5j5.png)

- 可以看到在窗口回调中有检查环境（`sub_42D4F1(); sub_42E428(); sub_42D825()` 里面都有检查，这些检查函数返回值如果为 `1` 就调用 `ExitProcess(0);`）。这些检查 `OD` 的反调试插件都可以过掉，但是我发现它是调用 `ExitProcess` 来退出程序的，所以就用 `010Editor` 把 `PE` 文件中所有调用这个 API 的二进制代码 `FF15CCF34900` 改为了 `0x90 (nop)`，防止其他地方也有调用该 API 退出进程。

- 这算是过掉了第一步的反调试。

### 1.2 `FindWindow`

- 在一开始运行程序时（没有开 `OD` 等调试工具），程序是正常的，但一打开 `OD`、`PEiD` 等工具后，程序会在按下验证序列号时自动退出。这个比较简单，可以通过 `OD` 跟踪、查看导入表中有什么奇怪的 API 后下断点（我就是在导入表中看到了 `FindWindow` 这个 API），然后在 `IDA` 中点进函数查看。

- 查看导入表：用 `OD` 随便双击一条调用系统 API 的指令，查看指令中的地址，在内存窗口跟随地址，右键选择“反汇编”，就可以看到导入表了。在导入表里可以发现该程序调用了哪些 API，这是个实用的技能。

- `IDA` 看到的：

![图片描述](upload/attach/201710/751258\_zyd6w3siwjpvudw.png)

- 过这个也很简单，抹掉该函数调用或者改掉字符串。我是在 `WinHex` 中找到字符串后直接抹掉的。

### 1.5 小结

- 虽然有这么多反调试，但全给 `nop` 掉就过了，所以感觉作者这次的反调试没有利用好。如果反调试代码里面又有解密、校验相关的代码或数据，像我这样暴力 `nop` 肯定就掉到坑里了。

### 2.2 多解分析

- 对多解的怀疑不仅仅是因为上面的原因，还有在前面对该 `memcmp` 比较参数的怀疑：

![图片描述](upload/attach/201710/751258\_v4gl31aqe4oft6t.png)

- 调试一下就可以发现，`v5` 是输入的字符串指针，`v6` 是经过算法编码后的字符串长度（就是前面在 `memcmp` 那里断到的 64 位长度的字符串）。

- 通过下图来理一下逻辑：

![图片描述](upload/attach/201710/751258\_8iv08499k2c58le.png)

- 所以 `memcmp` 比较的参数是移动后的，同时也解释了为什么之前输入内容后，`memcpy` 拿到的第一个字符串参数为空了，是因为字符串长度不够 64 位。

- 那推理一下，如果字符串长度超过 64 位呢？继续看图：

![图片描述](upload/attach/201710/751258\_kpvufvq7zet7pun.png)

- 看到这里是不是可以发现，如果输入的内容超过 64 位，那就会只判断后 64 位！

- 再结合前面发现的输入不同的数字出现的是相同的结果、输入不同的字母出现的是相同的结果（经过验证，其实是只要以数字开头就是相同的结果，只要以相同字母开头就是相同的结果）。那么就可以把这两点结合起来：先随便输入一小段字符，拿到经过算法加工的内容，将该内容补到刚才输入的字符后面再次输入。

- 比如输入 `abcdefg`，拿到 `432a34a4946708602bdf52a8b556a3c18ff9ab60c346da83579f149c4f366513`，然后构造出：

  `abcdefg432a34a4946708602bdf52a8b556a3c18ff9ab60c346da83579f149c4f366513`

- 再次输入：

![图片描述](upload/attach/201710/751258\_46ca22kw1io2r58.png)

- 于是 `memcmp` 这一层又轻松地过了。

- 但是我们可以发现，其实在 `memcpy` 后面还有一个校验函数：

![图片描述](upload/attach/201710/751258\_7l3p454ic1wyfeu.png)

![图片描述](upload/attach/201710/751258\_txbv703ia798mx9.png)

- 这个校验函数返回 `1` 为校验成功，返回 `0` 为校验失败。而在实际测试中，这段校验代码“时灵时不灵”。这段校验代码参考的内存则是一大片 `0`，加上一个特殊校验值，再加上原输入。但是由于不稳定，就没有继续分析这段校验代码了，暂时把这段代码当作失败的校验，静等作者公开出题思路。
