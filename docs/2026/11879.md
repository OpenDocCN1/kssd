## 1. 基础扫盲

此节是为完全没听说过`lex`这款软件的朋友准备的，有了解的请直接跳过。

“什么是词法分析器？”

简单而言，**词法分析器**，就是**在一段字符串中，找寻特定子字符串的程序**。如：对于这句话：”I study at KeRui.”，如何编写程序来判断它里面有几个单词？我们可以扫描这个字符串，以空格为界限划分，获取单词数目。

但是，当语句变成”I learn C, C++ and JAVA from KeRui.”，再用空格作为单词划分依据就不足够了，还需要逗号。

很容易理解，**当要处理的字符串越来越复杂，划分单词的依据也会越来越复杂**，编写这样的程序（词法分析器），将会是痛苦又无聊的。于是就有`lex`这样的“词法分析器的生成器”程序，它可以帮助我们生成处理字符串的程序。

具体而言，我们只要按`lex`规定的语法编写好`lex`文本文件，再交给`lex`程序“编译”，它就**会帮我们生成一个对应的c源码文件**，再将这个c源码文件编译，就可以得到分析字符串的程序了。

`lex`上手很容易，本文为了重点明确，就不涉及它的使用了，大家可参考

## 2. Lex应用案例之编写自己的MFC Spy

### 2.1 MFC Spy的原理

MFC框架中，使用以下三个宏实现消息映射：

```
//cpp文件中
BEGIN_MESSAGE_MAP
END_MESSAGE_MAP

//头文件中
DECLARE_MESSAGE_MAP
```

它们综合在一起的作用，就是**将要映射的消息及对应的响应函数集中放在了一个静态成员数组中**。因此，我们只要找到这个数组，就能定位代码，从而进行进一步的逆向分析工作。

要在整个内存块中找出一个数组来并不容易，不过好在MFC框架为了方便其自身，定义了查表的接口：

```
virtual const AFX_MSGMAP* GetMessageMap() const;
```

因此，我们的目的变得明确，就是要调用某个窗口对象的`GetMessageMap()`，它隐藏着以下问题：

- 如何获取对方MFC程序的窗口对象，这涉及到注入
- 如何将`GetMessageMap()`的返回结果传回MFC SPY程序，这涉及到进程间通信

明确了目的，做事的流程就很清晰了：

- 获取目标MFC程序的窗口句柄
- 注入对方MFC程序的进程
- 在对方进程中定位到`CWnd::FromHandlePermanent`并调用，获得窗口对象
- 调用窗口对象的`GetMessageMap()`函数，获得消息映射表

其中注入手段很关键，因为`FromHandle`函数内部的工作就是查句柄与对象指针的映射表，**而这个表又是以线程为单位存放的**，因此线程注入(`CreateRemoteThread`)是不会成功的。最方便的是用API提供的挂钩函数(`SetWindowsHookEx`)来注入，同时还要处理好同步、进程间通信问题：

```
void CMyMFCSpyDlg::OnSpyMFC()
{
    HANDLE hEvent = CreateEvent(NULL, FALSE, FALSE, "WaitForMySpyHookDll");
    HHOOK hhk = NULL;

    if(!IsWindow(m_hWndDest))
    {
        AfxMessageBox("NOT a valid handle");
    }

    if (!::SendMessage(m_hWndDest, WM_QUERYAFXWNDPROC, 0, 0))
    {
        AddHead2OutputBox("WM_QUERYAFXWNDPROC: Dest App is NOT a MFC application.\r\n");
        return;
    }

    BeginWaitCursor();

    /* 挂钩、注入、并等待返回结果 */

    //挂钩
    hhk = SetMFCSpyHook();
    if(!hhk)
    {
        AfxMessageBox("设置钩子失败");
    }

    //通知钩子处理事务
    ::SendMessage(m_hWndDest, WM_NULL, WP_BEGINSPY, LP_BEGINSPY);

    //等待处理完毕
    WaitForSpyDll();

    //通过FileMapObject读取目标信息
    ShowDestInf();

    ::UnhookWindowsHookEx(hhk);

    EndWaitCursor();
}
```

进程间通信我使用的是文件映射+发自定义消息，偷懒地使用的是定长协议：

```
void WriteMsgMapInf2File(AFX_MSGMAP *pMsgMap)
```

最终，获取了窗口对象指针后，取虚表、根据偏移获取`GetMessageMap()`，这里我觉得指针转换稍微麻烦点，因此用内嵌汇编完成的：

```
AFX_MSGMAP * GetRlsMsgMap(CWnd *pWnd)
{
    AFX_MSGMAP *pMsgMap = NULL;
    __asm 
    {
        push ecx;
        push ebx;

        mov ebx, pWnd;
        mov ecx, dword ptr [ebx];
        mov ecx, dword ptr [ecx + 0x30];
        call ecx;
        mov pMsgMap, eax;

        pop ebx;
        pop ecx;
    }
    return pMsgMap;
}
```

### 2.2 flex应用之提取消息宏

MFC Spy的技术难度并不大，但是有很多细节上的苦力活，比如获取到消息映射表以后，对消息的显示。因为编译时消息都被替换成了整型，若我们的程序仍然显示整型的话，并不友好。因此我们定义一下的结构体和宏，将消息的整型值与对应字符串绑定起来：

```
#define ToTagMsg(WndMsg) {WndMsg, #WndMsg} ,

struct tagWndMsg
{
   DWORD dwMsg;
   const char * strMsg;
};
```

这样，类似以下的数组编译时就会被替换：

```
tagWndMsg g_tagWndMsg[] = {
    ToTagMsg(WM_FLIP)
    ToTagMsg(WM_NULL)
};
//宏替换为：
tagWndMsg g_tagWndMsg[] = {
    {WM_FLIP, "WM_FLIP"} ,
    {WM_NULL, "WM_NULL" } ,
};
```

但是，以`WM_`开头的消息宏虽然都定义在`winuser.h`中，但数量巨大，手工添加显然也不是一个明智的选择。我们可以用`flex`写一个简单的程序，提取其中消息，并自动生成定义了相关数组的cpp文件：

```
%{
#include <stdio.h>
#include <string.h>

/* This program
 * converts the macros of windows message
 * to tagWndMsg containing the value and string
 */

unsigned int g_nMsgNum  = 0;

%}
MSGMACRO WM_[A-Z_]*
%x BLOCKCOMMENT
%%

\n                          { /* new line */ }

"//".*                      { /* eat up line comment */ }

"/*"                        { BEGIN BLOCKCOMMENT; }
<BLOCKCOMMENT>[^*\n]+       { /* eat up anything that's not a '*' */ }
<BLOCKCOMMENT>"*"           { /* eat up '*'s not followed by '/'s */ }
<BLOCKCOMMENT>\n            { /* new line */ }
<BLOCKCOMMENT>"*/"          { BEGIN INITIAL; }

{MSGMACRO}                  { printf("    ToTagMsg(%s)\n", yytext);  g_nMsgNum++;}

.                           { /* eat up whatever else */ }

%%
int main()
{
    char *szMacro = "#define ToTagMsg(WndMsg) {WndMsg, #WndMsg} ,\r\n";

    char *szTagMsg = "struct tagWndMsg\n"
                    "{\n"
                    "   DWORD dwMsg;\n"
                    "   const char * strMsg;\n"
                    "};\r\n";

    char *szBeginAry = "tagWndMsg g_tagWndMsg[] = {\n";
    char *szEndAry = "\n};";

    printf(szMacro);
    printf(szTagMsg);

    printf(szBeginAry);
    yylex();
    printf(szEndAry);

    printf("//Total Msg:%d", g_nMsgNum);
}

int yywrap()
{
    return 1;
}
```

将该`flex`文件编译生成cpp文件后，再编译cpp文件得exe程序，该程序可读取`winuser.h`中的信息生成含结构体数组的cpp源文件。**具体程序及代码见附件，使用方法，在命令行输入**：

```
GenMsgAry.exe < WinUser.h > Dest.cpp
```

### 2.3 flex应用之定位FromHandle

前文件中我们已经说过，我们需要通过调用`FromHandle`函数将窗口句柄转为窗口对象指针，因此定位目标程序`FromHandle`是实现MFC Spy的关键步骤。

目标程序的编译环境、链接方式不同，定位其`FromHandle(FromHandlePermanent)`的方法也不相同，因此，我们要先有能力判断目标程序的编译版本，我整理流程如下：

- 向目标程序发送`WM_QUERYAFXWNDPROC`消息，根据返回值可判断是否为MFC程序，若为MFC程序转至下一步，否则不处理
- 目标程序是MFC程序，通过遍历其模块查找MFC的dll来判断为动态链接还是静态链接的MFC程序，并采用对应方法获取`FromHandle`(见下)

对于动态链接的MFC程序，获取`FromHandlePermanent`相对容易，因为我方注入的代码与对方进程共享`MFCxx.DLL`，当挂钩成功后，只需要`LoadLibrary`与`GetProcAddress`即可获取`FromHandlePermanent`(`FromHandlePermanent`的导出序号是公开的)。核心代码：



```cpp
//mfc42d.Dll版本

PVOID GetDbgFromHandleAddr(HMODULE hModule)
{
    return GetProcAddress(hModule, (LPCSTR) 2220);
}

//mfc42.Dll版本

PVOID GetRlsFromHandleAddr(HMODULE hModule)
{
    return GetProcAddress(hModule, (LPCSTR) 2867);
}
```

对于静态链接的MFC程序，我们只能通过在主模块(exe文件)中搜索特征码来定位`FromHandle`。这里要注意，不同的MFC框架版本其`FromHandle`内部实现往往是不同的，此外，相同版本的MFC框架，其生成的Debug与Release版本的程序，`FromHandle`内部也是不同的。这两者组合起来，**若需要做一个通用的MFC Spy，我们需要提取很多版本的特征码**……这也是为什么网上流传的MFC Spy通用性都有待加强的原因。

不过好在，我们可以借助`flex`巧妙地完成这样的体力活，如下：

STEP1 自己编写对应的静态MFC程序样本，在其中打印出`FromHandle`的地址，方便我们定位函数

![](https://bbs.kanxue.com/upload/attach/201510/651791_x1cwjehrjp8p3bs.png)

STEP2 根据PE信息，将VA转换为文件偏移，用WinHex在文件中找到对应偏移，并拷贝对应字节作为特征码。

![](https://bbs.kanxue.com/upload/attach/201510/651791_lug6stn2w8y9xf2.png)

![](https://bbs.kanxue.com/upload/attach/201510/651791_nn9o48l3h2bkfka.png)

注意WinHex拷贝时，若使用“GREP Hex”，其结果可直接作为`lex`的正则表达式，我们就要用这种拷贝方式。

![](https://bbs.kanxue.com/upload/attach/201510/651791_9zufuwenbnaxnuu.png)

STEP3 特特征码中，要注意像`call`/`jcc`这样的相对跳的指令以及`push offset xxxx`这样的指令，它们之后所接的操作数不能作为特征码参考，我们在编写`flex`文件时要将其改为通配符

最后，我们编写出如下`lex`源码文件（**为重点明确，有省略，具体看源文件**）：

```cpp
%{

#include <stdio.h>
#include <string.h>
#include "Tokens.h"

unsigned int g_dwOffset  = 0;

%}
CALL \xE8[\x00-\xFF]{4,4}
PUSH_NUM \x68[\x00-\xFF]{4,4}
VC6_RLS_STC_PATTERN \x56\x57\x6A\x01{CALL}\x8B\xF0\xFF\x74\x24\x0C\x8B\xCE{CALL}\x8B\xF8\x56\x8B\xCF{CALL}\x8B\xC7\x5F\x5E\xC2\x04\x00
//... 各种特征码
%%

{VC6_RLS_STC_PATTERN} {
    return VC6_STC_RLS;
}

//... 找到特征码后各种对应处理方案

. {
    g_dwOffset += yyleng;
}

\r|\n {
    g_dwOffset += 1; //注意通配符 "." 是不匹配newline的
}

%%
int yywrap()
{
    return 1;
}

int FindMFCVersion(FILE *fp)
{
    yyin = fp;
    yyrestart(fp);
    g_dwOffset = 0;

    switch (yylex())
    {
    case VC6_STC_DBG:
        return VC6_STC_DBG;
        break;
    case VC6_STC_RLS:
        return VC6_STC_RLS;
        break;
    case VS2013_STC_RLS:
        return VS2013_STC_RLS;
    case  VS2013_STC_DBG:
        return VS2013_STC_DBG;
        break;
    }
    return 0;
}

unsigned int GetPatternOffset()
{
    return g_dwOffset;
}
```

其中，将`yylex()`再多包一层，成为`FindMFCVersion()`，并且加入`GetPatternOffset()`函数以获取特征码相对初始位置的偏移。这样做是使得封装性更好，而且，为了避开恼人的编译时头文件检查等，我推荐是直接将`FindMFCVersion`编译成`obj`文件供注入`dll`调用，**具体可参考附件里的对应工程**。

若不使用`flex`帮忙，通常定位特征码的方法，除了在目标函数内部找寻外，**还可以利用交叉引用寻找**（如某个函数调了`FromHandle`，先定位那个函数，再通过它定位`FromHandle`）。那样的策略更具有艺术性（可以找到某个特征码横跨好几个版本的MFC），不过**同时需要更多的精力去测试特征码的通用性、唯一性**。

### 3. 除数为常数的除法定式识别

编译器为了提供程序效率，对于一些特定的表达式，往往会进行优化，用**多条**效率高的指令取代一条效率低的指令（多条效率高的指令周期总和仍少于那条效率低的），也可能是多条指令配合，将有分支流程转为无分支流程。

因为优化的算法是有套路的，所以以上提到的“多条语句”组合在一起也是有套路的，这样的套路我们就称为“**代码定式**”了，按套路对汇编代码进行反解析，就要以得到相应的高级代码。

这里附给大家的是**除法定式的识别程序**，可以直接由IDA汇编代码得到对应的C语言代码。不过因为只支持一个定式一个定式的识别，所以使用前提大家还是得了解下除法优化的相关原理，**能看出某一块汇编代码是在做除法**。好在科锐的前辈已经整理得很完善，我就不啰嗦了，感兴趣可参考<http://bbs.pediy.com/showthread.php?t=113689>中的“**1.9、除法与取模运算的识别与优化原理**”

定式的识别是个苦力活，就是在不断调试语法怎样匹配，匹配成功后再根据优化算法逆回去求出源代码，具体大家看代码就可以体会。

![](https://bbs.kanxue.com/upload/attach/201510/651791_1xmx50iym219wu4.png)
