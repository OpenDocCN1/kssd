
# [翻译] Java 类型混淆，沙箱逃逸

上周，甲骨文公司公布了他们的季度重要补丁更新（CPU）。其中 7 个漏洞通过 ZDI 计划提交，其中的一个让人想起 2012 年底和 2013 年初的 Java 提交。这个漏洞，`CVE-2018-2826`（`ZDI-18-307`），是一个因类型检查不足引起的沙箱逃逸漏洞，由 xor19 发现。一个拥有低执行权限的攻击者可以利用这个漏洞来绕过 `SecurityManager` 并提权。

## 漏洞

漏洞位于反射 API（`java.lang.invoke.MethodHandles::tryFinally(MethodHandle target, MethodHandle cleanup)` 方法）的实现里。从这以后我会把该 API 称为 `MethodHandles::tryFinally()`。该 API 返回一个方法句柄，这个句柄通过把目标方法包进一个 `try-finally` 块来改写它。这个 cleanup 方法句柄体现了 `finally` 块的功能。任何在目标句柄执行期间抛出的异常都会被传递给 cleanup 句柄。

在 `MethodHandles::tryFinally()` 的实现里，不充分的类型检查发生了。对一个攻击者来说，在目标和 cleanup 方法句柄之间指派不匹配的 `Throwable` 对象是可能的，从而引起类型混淆。这样攻击者就可以把任何对象转化成任何类型。

## 一个例子

假设我们有下面两个类和方法。

![](https://bbs.kanxue.com/upload/attach/201806/724934_PBCEBQPUVFWW54Z.jpg)

攻击者构造了一个 `throwEx()` 方法句柄和 `handleEx()` 作为 cleanup。注意 `throwEx` 抛出一个 `Cast1` 类型的 `Throwable` 异常，并且 `handleEx()` 处理 `Cast2` 类型的 `Throwable` 异常。当攻击者在一个漏洞版本的 Java 调用新创建的方法句柄，它把 `Cast1` 类型的 `Throwable` 对象传递给 `handleEx()`，`handleEx()` 处理 `Cast2` 类型的 `Throwable` 对象，并没有对传入类型有任何处理或者适当的类型检查。当 `handleEx()` 继续处理 `Throwable` 异常时，它把 `Lemon` 对象当做了 `Lime`，这允许攻击者把 `Lemon` 转换成 `Lime`，用 `Lemon` 类调用了 `Lime` 类的 `makeLimenade()` 方法。

## 利用

在漏洞利用里，攻击者尝试通过反射函数把 Security Manager 置为空来绕过它。首先，攻击者通过 `MethodHandles::publicLookup()` 方法得到一个 `setSecurityManager` 方法句柄。然而，正常情况下 `setSecurityManager` 不能被 `MethodHandles::publicLookup()` 访问，所以攻击者定义了下面的代码并且利用类型混淆漏洞把 `Lookup` 对象转换成伪造的 `LookupMirror` 对象。

![](https://bbs.kanxue.com/upload/attach/201806/724934_7PDMBNMA6SU83M9.jpg)![]()

在 `handleEx()` 方法，攻击者把 `Lookup` 对象当作 `LookupMirror` 对象来操作。从下面相关的 OpenJDK 源代码可以看到，攻击者已经把 `Lookup` 对象的 `allowedModes` 属性改成了 `TRUSTED`，从而允许攻击者得到任何方法的方法句柄，包括 `setSecurityManager()`。

![](https://bbs.kanxue.com/upload/attach/201806/724934_782D5RSY9S46D23.jpg)

最终，攻击者使用可信的 `Lookup` 对象得到了 `setSecurityManager()` 的方法句柄，并且把 `SecurityManager` 设置为空，从而绕过 `SecurityManager` 产生的所有限制。

## 补丁

甲骨文公司通过把目标方法句柄抛出的对象转换成 cleanup 可以处理的对象来给这个漏洞打上了补丁。这保证了当类型不匹配并且显示转换不兼容时，`MethodHandles::tryFinally()` API 会抛出一个 `WrongMethodTypeException` 异常。

![](https://bbs.kanxue.com/upload/attach/201806/724934_FHHUN8CMF27EEPG.jpg)

## 结论

很有趣看到这些 Java 类型混淆漏洞继续被提交给 ZDI 计划，即使最近它们被利用的并不多。一旦浏览器安装了 “Click-to-Play”，实际的利用变得更加困难。这也反映在历年提交给这个计划的 Oracle Java 漏洞的数量上。数量的陡降与 Click-to-Play 的引入相一致，它也表明了类型混淆漏洞的利用困难驱使研究者转移到其他目标上。

![](https://bbs.kanxue.com/upload/attach/201806/724934_PNV2FK4HQ5XUPCT.png)![]()

当我的同事们在 2013 年出席 Java 漏洞利用的时候，甲骨文宣称超过 30 亿的设备运行 Java，现在这个数量甚至更加庞大。类型混淆漏洞是那时候利用最多的漏洞，所以很高兴看到这些漏洞被打上补丁，即使他们从来都没有被当作目标。
