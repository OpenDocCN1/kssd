![图片描述](upload/attach/202512/1028907_WRQQ9G2ZUJZEM44.webp)

此时就能够比较清晰的查看到，想要溢出覆盖到`SE Handler`的距离还差大概`999 + 4`字节

简单分析一下

`01c1fb5c`这里全是 A。说明到这里为止，还是1500 个 A 的部分，我们知道内存是小端序显示的，所以接下来的`42424241`实际上是`41` `42` `42` `42`，这就是为什么以`01c1fb5c+5`来计算

我们知道SEH这种结构体，`SE Handler`之前4个字节是`Next SEH`

所以实际上我们需要修改代码为：

```python
Next_Seh = '\x42' * 4
SE_Handler = '\x43' * 4
buffer = '\x41' * 2495 + Next_Seh + SE_Handler
buffer += '\x44' * (size - len(buffer))
```

![图片描述](upload/attach/202512/1028907_KJZN5BNNDVY3U2H.webp)

如果常规情况遇到这个情况，原因是在 HTTP 协议处理中，当程序接收到大于 127 (`0x7F`) 的扩展 ASCII 字符时，它会再次进行了 UTF-8 编码转换。比如在 UTF-8 中，`\x90` 会被编码为双字节序列 `\xC2\x90`。这个叫做**Character Encoding Expansion (字符编码膨胀)**

**注意：这里有个很大的坑，会在PPR指令查找的部分填坑**

这就是为什么内存里会平白无故多了一个 `\xC2`。

### 字符膨胀原因解释

多次排查以后，发现代码当中存在的问题，`Python 3` 的`Unicode`机制，我使用`encode()`来处理字符转换，所以会产生字符膨胀的问题，修改代码，直接用`bytes`这种方式就可以轻松避免这个问题 -_-
