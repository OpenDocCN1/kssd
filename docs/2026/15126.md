# [原创]简单尝试脱某加固的DEX壳

**0x00 序**
第一次尝试脱dex壳，样本是在“\*\*\*\*\*”官网上免费加固的，非商业版。

本文只是做些简单的笔记，给像我一样的逆向新手们提供点思路，高手们不要见笑。

**0x01 加固包和原包对比**
![](https://bbs.kanxue.com/upload/attach/201701/738921_p1rzta7kzhspnua.png)
加固后的classes.dex文件变大了，脱到JEB里面发现多了一些壳代码和一些垃圾类（jpvbhn、cioub、flsye…）。
![](https://bbs.kanxue.com/upload/attach/201701/738921_bywx20euxztov0a.png)
原包中，很多类方法的指令被抽空了，如下面的onCreate。
![](https://bbs.kanxue.com/upload/attach/201701/738921_ni5gx1va35vx44i.png)
将assets目录下的libexec.so脱到IDA中，发现个别方法被加密，并且用了o-llvm进行混淆编译。导出表中的那些x、y开头的变量就是o-llvm在编译过程中，添加混淆控制流（-bcf）时创建的。
![](https://bbs.kanxue.com/upload/attach/201701/738921_0qikwvdmhd0s3u7.png)
ptrace注入，从内存中dump出来一个libexec.so，看一下字符串表：
![](https://bbs.kanxue.com/upload/attach/201701/738921_459hdengnc6gtcs.png)
在字符串表中看到一些关键词（dvmResolveClass.c、HOOK:%s() write dex!），瞎猜\*\*\*\*\*可能是抽取dex中的方法指令，然后hook dalvik/art 关键函数，在运行时加载该类时再解密指令。所以用DexHunter试一下。
3ebK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4K9i4c8Z5N6h3u0Q4x3X3g2U0L8$3#2Q4x3V1k6\*7P5i4p5^5y4K6l9&6i4K6u0r3c8r3g2^5d9s2g2F1N6r3g2J5
ps：从字符串表也可以看到，\*\*\*\*\*为了“防模拟器”，判断了好多系统属性（ro.product.model、ro.product.device…）。

**0x02：利用DexHunter还原dex**
DexHunter的大致原理是在某dex的第一个类被加载时，遍历该dex文件的所有的class\_def\_item，主动加载所有的class（调用dvmDefineClass），并初始化（调用dvmIsClassInitialized和dvmInitClass），让壳自己完成方法指令的解密，然后再做必要修复并dump。
编译带DexHunter的dalvik，刷机之后试了一下，在脱壳过程中apk进程死了。
![](https://bbs.kanxue.com/upload/attach/201701/738921_4hbfn6ibdh1bi5n.png)
\*\*\*\*\*有点意思，应该是在libexec.so或libexecmain.so被加载之后，在native代码中判断了“/data/”目录下是否存在dexname文件（这也算DexHunter的一个特征），如果有则自退。
修改DexHunter源码，把dexname这个文件名改掉：
![](https://bbs.kanxue.com/upload/attach/201701/738921_bplb7tf9v3vqtjt.png)
再试一次，还是挂了，这次貌似是调用com.cioub类的clinit方法导致的。
![](https://bbs.kanxue.com/upload/attach/201701/738921_wuilar4icybp24q.png)
看一下com.cioub类的clinit方法的实现就明白了，上面提到的那些垃圾类（jpvbhn、cioub、flsye…）都是\*\*\*\*\*为了“防DexHunter”添加的。
![](https://bbs.kanxue.com/upload/attach/201701/738921_6si08wr0actqjgv.png)
先用笨方法解决一下，通过一个名单文件，将这些“防DexHunter”类pass掉。
![](https://bbs.kanxue.com/upload/attach/201701/738921_1ts1bw93y5ftgl1.png)
再试一次，脱出了whole.dex，这实际是一个odex文件，利用baksmali和smali将其转换为dex文件，拖到JEB中看一下：
![](https://bbs.kanxue.com/upload/attach/201701/738921_6lo9rthnlyf0ry8.png)
之前被抽空的onCreate方法成功还原了，去掉那些垃圾类和shell代码应该就差不多了。

**0x03 后序**
1、使用DexHunter脱完之后，如果还有方法没有还原，那加固厂商可能做了函数级加解密，在方法调用时再解密方法指令。
2、定位native方法指令在内存中的位置
![](https://bbs.kanxue.com/upload/attach/201701/738921_yhes3go0akdc4vb.png)
这3个native方法是\*\*\*\*\*加固之后的3个核心方法，但libexec.so的JNI\_Onload貌似加密了，并且导出函数的名字也混淆了（采用RegisterNative动态注册），找出对应的native函数有点费劲。
可以在dvmCallJNIMethod函数中加点log，其实这个函数中本来有log，只不过注掉了。放开的时候，要进行一下过滤，否则打出的日志太多会淹没其它有用的信息。
![](https://bbs.kanxue.com/upload/attach/201701/738921_6sqqptp9agl4q7l.png)
![](https://bbs.kanxue.com/upload/attach/201701/738921_upyh9dznu9hxelk.png)
3、\*\*\*\*\*应该已经有解释器壳了，猜测\*\*\*\*\*商业版以后可能会是“类抽取＋解释器壳”的形式，因为所有指令都解释执行的话，应该会对效率影响较大，所以二者结合是个不错的选择。
