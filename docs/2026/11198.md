
# [原创]360ini.dll注入explorer技术分析

前两天看了火绒安全实验室写的一篇分析360安全卫士极速版“诱导式”推广的文章，里面提到了一个下载安装模块`360ini.dll`会注入Windows资源管理器`explorer.exe`进程，利用系统进程下载360安装包，如下图所示。不过文章中仅仅只提到了`360ini.dll`模块会区分32位和64位的`explorer`进程进行注入，对于核心的注入技术细节没有再进一步深入，因此这篇文章尝试通过动静态等方式分析360选择的注入`explorer`的技术方式。

![图片描述](upload/attach/202210/758114_CPPQGVUKKNMW78V.png)

原文在这里：

<a href="elink@6c6K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6*7K9s2g2S2L8X3I4S2L8W2)9J5k6i4A6Z5K9h3S2#2i4K6u0W2j5$3!0E0i4K6u0r3M7q4)9J5c8U0f1%4y4U0l9@1x3e0t1$3y4b7`.`.">360安全卫士极速版"诱导式"推广 静默安装且对抗安全软件</a>

**先说结论：**

还是利用`NtSuspendThread`、`NtSetContextThread`、`NtResumeThread`等组合函数劫持`explorer`负责消息处理的UI线程执行流，不过在`shellcode`执行结束后会将控制权返还给`explorer`。

火绒已经分析出了x86、x64注入的核心函数，参数为目标进程`pid`。

![图片描述](upload/attach/202210/758114_38DQGMTB5T9NG98.png)

跟进x64的函数看一下，首先是一堆栈上赋值操作，推测应该是用了[编译时字符串混淆](elink@abbK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4K9i4c8Z5N6h3u0Q4x3X3g2U0L8$3#2Q4x3V1k6S2L8X3c8J5K9i4k6W2N6q4)9J5c8V1q4p5g2X3!0T1k6Y4g2K6j5$3q4@1L8%4t1`. )。这一大段数据猜测是后续用于注入的`shellcode`。

![图片描述](upload/attach/202210/758114_HX3YAQK7HV36N6H.png)

随后调用`openprocess`、`openthread`函数打开目标线程。

![图片描述](upload/attach/202210/758114_RCJBRMPGS2JDZQ4.png)

选择目标线程的时候则是利用`GetThreadTimes`函数获取线程创建时间，返回最早创建的线程`tid`。

![图片描述](upload/attach/202210/758114_QAJPMGED69Y5FF5.png)

之所以选择该线程可能是因为大部分时候都是处于`WaitMessage`等待事件消息的状态。

![图片描述](upload/attach/202210/758114_4H3BECZQUYJJHGP.png)

获取目标线程`pid`后两次调用常规函数跨进程申请内存、写内存。第一次写注入`dll`的路径，第二次写加载`dll`的`shellcode1`。

![图片描述](upload/attach/202210/758114_CFKVPKXNT9EJU4B.png)

动态调试可以看到申请了地址`0x3a20000`大小`64K`的读写内存。

![图片描述](upload/attach/202210/758114_VKFH37JDKCS3WJB.png)

并向其中写入了注入`dll`的路径。

![图片描述](upload/attach/202210/758114_VKVYY7HCTE5KB2V.png)

第二次申请了地址为`0x2b2000`大小`64K`的可执行内存。

![图片描述](upload/attach/202210/758114_Z5EUEN3HXU7M85Z.png)

向其中写入加载`dll`的`shellcode1`。

![图片描述](upload/attach/202210/758114_C679SWXQ62TZWBB.png)

写完`dll`路径和`shellcode1`后，进入`sub_10003D50`核心注入函数。首先挂起目标线程、获取目标线程的寄存器等上下文。随后继续申请内存写`shellcode2`。最后在改写完`shellcode2`和寄存器上下文之后设置线程将要执行的上下文，恢复目标线程。

![图片描述](upload/attach/202210/758114_RERQ96ADWDNB247.png)

下图可看到申请的`shellcode2`地址为`0x3a30000`，功能为创建到`0x2b2000`的`shellcode1`的线程。

![图片描述](upload/attach/202210/758114_CXRTDWC5CTXN7EF.png)

这里可以看到原始的线程上下文`EIP`为`0x773F932A`指向`user32.dll`空间，将其修改为`0x3A30000`即`shellcode2`的地址。

![图片描述](upload/attach/202210/758114_NYAJD7BR62VHE92.png)

最后一步设置目标线程的上下文，恢复线程即完成x64的整个注入`explorer`进程操作。

最后看下两段`shellcode`，`shellcode2`也就是劫持了原始执行流的`shellcode`调用了`CreateThread`函数，目标地址为`shellcode1`，参数为`dll`路径。

![图片描述](upload/attach/202210/758114_JW7DXCAW5ES9SJH.png)

并在创建完成后返回到原始执行流也就是`user32.dll`空间下的`0x773F932A`地址。

![图片描述](upload/attach/202210/758114_U82WEEHBT8TQK4U.png)

`shellcode1`则直接调用`LoadLibraryW`在`explorer`中加载`dll`。

![图片描述](upload/attach/202210/758114_3277NN2Y9V66XVP.png)

到这x64注入`explorer`进程的流程基本就结束了。下载的安装包证据如图。

![图片描述](upload/attach/202210/758114_U26JM2ARHA5T5HA.png)

不过最后还有一个疑点，`shellcode2`的地址申请的是读写权限的内存，不知道为啥执行的时候内存就变成读写可执行的了。这一点很疑惑，有没有大佬知道为啥的。

`360ini.dll`本身有反调试手段，如果后续想要动态调试的话需要`patch`或者动态过掉两个`TLS`回调函数，并且在`dllmain`中过掉这两个反调试函数。

![图片描述](upload/attach/202210/758114_3D3NJ8N8DQ8GD6A.png)

`360ini.dll`为了阻碍静态分析，系统`api`大部分都是在`dll`加载时动态获取动态调用的，单纯用`ida`很难分析，并且某些关键`api`函数还利用了类似于`wrapper`层去调用`ntdll`的系统调用。不过好在静态代码还能看，没有上花里胡哨的混淆或者壳之类的。
