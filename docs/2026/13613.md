
# [原创]恶意代码分析之调试.NET平台dll

## 常规方式

### 场景一

被调试的母体文件为.NET平台程序，内部会进行内存解密释放执行新的dll文件。可以直接使用`dnSpy`一步步调试，进而直接进入新`dll`程序领空。这里举一个笔者之前分析时接触的案例，如下恶意文件会从资源获取16个字节数据作为密钥，便于后续进行解密。

![](https://bbs.kanxue.com/upload/attach/202007/678001_38VAMNCENJXBR4D.jpg)

经过下面的逻辑进而解密会得到新的`PE`文件（此时都发生在内存中），如下。

![](https://bbs.kanxue.com/upload/attach/202007/678001_8E8Y48HKWTTTZ6R.jpg)

![](https://bbs.kanxue.com/upload/attach/202007/678001_J8M6SJBNXQYW6DF.jpg)

这里先自行提取下便于后续判定，提取的`PE`文件分析后为.NET平台的`dll`文件，如下。

![](https://bbs.kanxue.com/upload/attach/202007/678001_VR6TXKRVFX77M9W.jpg)

![](https://bbs.kanxue.com/upload/attach/202007/678001_3M5Y25JKMG35X2E.jpg)

接着往下分析，发现会内存加载`dll`并反射调用执行`dll`中的`LOLY()`方法，如下。

![](https://bbs.kanxue.com/upload/attach/202007/678001_A6HFTGNTZKTVD48.jpg)

![](https://bbs.kanxue.com/upload/attach/202007/678001_NWJ5AZEDQJW29TS.jpg)

![](https://bbs.kanxue.com/upload/attach/202007/678001_EJ64CBP32V42KKR.jpg)

将上面提取的`dll`进行本地反编译，查看下`dll`文件内容，如下。

![](https://bbs.kanxue.com/upload/attach/202007/678001_369ZCRR3RJR74VF.jpg)

确实存在入口点方法，如下。

![](https://bbs.kanxue.com/upload/attach/202007/678001_2D5JRCSY28HW6FG.jpg)

接下来，就可以直接一步步单步步入调试进入`dll`区域内，进入到入口点，如下。

![](https://bbs.kanxue.com/upload/attach/202007/678001_ZRKTVQQPHF7PHN6.jpg)

之后的调试不再叙述，基本上是与之前进行分析时一样的步骤。

### 场景二

被调试的母体文件非.NET平台程序，而由于缺少标准入口点，`dnSpy`不允许本地调试`dll`，此时就需要借助`loader`进行调试。首先我们可以想到，`ollydbg`是如何调试`dll`文件的？其实会发现工具自身会加载一个`loader`进行辅助调试，调用`dll`里的导出方法或者断点停在`dll`入口区域。

![](https://bbs.kanxue.com/upload/attach/202007/678001_A43NUUK8EDA7FRJ.jpg)

如果是需要调试.NET平台`dll`文件，可能需要自行写一个.NET平台的`loader`，然后根据具体需要修改要调用的导出方法。本着不重复造轮子（其实是不太会写代码）的思想，于是网上搜了下，发现了如下工具（具体更多内容可以自行访问项目地址查看，这里不再过多介绍）。

`hexfati` / `SharpDllLoader`：一个简单的`C＃`可执行文件，它调用任意`C＃ DLL`的任意方法。

`-c` 表示该`dll`的调试的类

`-m` 表示该`dll`调试的实际方法
