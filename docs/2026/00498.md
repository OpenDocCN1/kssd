# [原创]Windows7下的OllyDBG的异常断点补丁(含原理、源码及插件)

**Windows7下的OllyDBG的异常断点补丁(含原理、源码及插件)**

  相信大家与我有类似的经历，那就是在使用OllyDBG调试程序时，对于异常处理回调中的代码，所下的断点并不能被执行到（断不下来）；而经验证，程序在非调试环境下运行时，异常处理回调中的代码又确实可以被执行到。
  **缘起**
  当我们需要在OD中调试异常处理中的代码时，就需要用到看雪前辈所编写的HideOD插件了，它其实就是为系统的kernel32.dll打了一个补丁。不过遗憾的是，HideOD插件并没有更新到Windows 7版本。
  不过正好，目前我在科锐的进度学到了异常相关的知识点，钱老师讲完异常过滤器后，一时兴起与我们谈到了OD的这个“Bug”，又一时兴起谈到了Win 7下的插件的缺失，最后还一时兴起花了二十来分钟手工定位了关键代码，打了一个“人肉补丁”。
  而对于我自己来说，是第一次直观看到，kernel32.dll这样的所谓“系统文件”，在掌握它的流程与原理后，也是可以在其中“为所欲为”的。
  我通过整理上课的笔记，制作了win7版本的异常断点插件，如果有疏漏或误解的地方，还希望各位指正。
  **原理**
  这一部分是假设我们还不知道异常分配流程的前提下，如何通过一些“貌似无用的线索”，定位关键代码的。如果不感兴趣，可以直接跳到后面的【验证】及【分析】部分阅读。
  我们知道，若是需要加载自己的异常处理函数，是需要调用SetUnhandledExceptionFilter这个API，在它的MSDN说明中，我们可以看到：

After calling this function, if an exception occurs in a process that is not being debugged, and the exception makes it to the unhandled exception filter, that filter will call the exception filter function specified by the lpTopLevelExceptionFilter parameter.

  从其中可以看到，当异常产生时，系统会根据是否在调试状态，来决定异常的去向，而其中的”filter”，我们也可以在MSND中到，见UnhandledExceptionFilter的说明：

The UnhandledExceptionFilter function passes unhandled exceptions to the debugger, if the process is being debugged. Otherwise, it optionally displays an Application Error message box and causes the exception handler to be executed.

  可以看出，UnhandledExceptionFilter会根据是否被调试的状态，来控制异常的流向到底是调试器还是用户自定义的handler。于是我们可以大胆猜测，UnhandledExceptionFilter函数包含着重要跳转，是我们打补丁的目标。剩下的工作就是写代码验证而已了（其实以上是研究的思维过程，实际中最快的方法应该是看HideOD中的UnhandleExceptionFilter得到提示）。
  **验证**
  我们第一个要验证的是，UnhandleExceptionFilter确实控制着关键的流程跳转，并且由它来启动我们自定义的异常处理函数。
要达到目的，我们可以通过程序在非调试状态下，异常处理会正常启动这一点来入手。通过在自定义的异常处理函数中编写特殊的代码，来得知其返回地址。再故意激发异常，进而分析出是哪个函数调用了我们自定义的异常处理函数。以下是代码：


```
LONG __stdcall MyException(_EXCEPTION_POINTERS *ExceptionInfo )
{
    int n = *(int*)((int)&ExceptionInfo - 4);

    printf("0x%p \r\n", n);
    return EXCEPTION_EXECUTE_HANDLER;
}

int main(int argc, char* argv[])
{
    SetUnhandledExceptionFilter(MyException);
    __asm int 3
  return 0;
}
```



运行以上代码，获取返回地址，在我本人的机器上，得到的结果为：0x7582030B。于是，打开OllyDBG，直接go到该地址处(0x7582030B)：
![](https://bbs.kanxue.com/upload/attach/201507/687044_00tys3y70uw9uqa.png)

通过往上翻看，查找代码来源，可以得知，这段代码确实来自于UnhandleExceptionFilter函数中。
验证完成，我们接下来就是分析API流程，并改变关键跳转。
  **分析**
  我们下面来分析UnhandleExceptionFilter的程序流程，在kernel32模块中，找到UnhandleExceptionFilter参考，并进入到函数首地址：
![](https://bbs.kanxue.com/upload/attach/201507/687044_wukyswzirflt7gr.png)

  可以发现，在函数的头部不远处，有多个跳转，全部下断点，并运行，观察程序流程并记录其动作：
![](https://bbs.kanxue.com/upload/attach/201507/687044_5c4j9wo99oimqln.png)

  可以看到当执行到0x7580774D处时流程转移，这个跳转跳过了0x7580776f（之后就步出UnHandleExceptionFilter函数了）。所以，为了想要走后面的流程，这里不能让他跳走，跟进跳转前0x75807746的CALL kernel32.75807861 看一下：
![](https://bbs.kanxue.com/upload/attach/201507/687044_qzn2wjcoq48d369.png)

  原来，在这里系统调用了ZwQueryInformationProcess函数，然后根据它的返回值来判断是否需要跳转。
所以，我们的任务是，通过修改ZwQueryInformationProcess的返回值，使得每次跳转条件都实现即可。

方法：直接修改7580774b处的代码，将TEST EAX, EAX改为XOR EAX, EAX。
重新加载程序，并在以上地址进行相应修改。测试结果显示，修改后，异常处理中的代码确实可以断下来了。
至此，这个在科锐从“被发现”到“被消灭”的bug，被我们用人肉的方法光荣消灭。
不过，毕竟每次人肉打补丁这样的低水平重复劳动的活，是为我们不耻的，于是我多花了一点时间开发了一个OD插件，使得每次运行时，插件自动帮我们打补丁。

插件及源码我都放在附件中了，在这里只一下思路和要点：
1.Kernel32.dll是系统dll，会有系统保护机制，因此不能直接在文件中打补丁
2.我编写的OD插件，在每次程序加载完成后，在内存中找到关键代码，并打补丁
3.插件思路：将关键代码及其附近的机器码，作为特征码，利用GetProcAddress得到UnhandleExceptionFilter的函数地址，并对相关区域进行扫描，若匹配特征码，则定位并修改。
