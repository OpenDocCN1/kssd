# [原创]X86内核笔记_6_APC相关

# 0.APC概念
APC（异步过程调用）。具体概念百度很多文章都说了，通俗的来讲就是个官方的Hook回调，只是hook点是事先定义好的。
Windows维护了两种APC队列（内核APC、用户APC），队列中是一个个APC回调函数，在特定情况下Windows会遍历APC对列去执行每个APC回调函数。
## 杀死进程线程
在用户层我们调用TerminateThread一类的函数可以结束某个线程或进程，看上去好像是我们的进程把目标进程给干掉了。实际上一个线程不会被其他线程直接杀死，线程在运行时是独自占有CPU的。线程真正的死亡是“自杀”。结束线程的本质是：线程A向线程B插入一个APC，APC的功能是杀死B线程。当B线程调用一些系统API时，API内部会执行APC函数，从而让B线程杀死自己。
# 1.APC相关结构
> 初步有个概念，不需要背，逆向函数时自然就明白每个成员的作用了。
在进程线程章节中我们看到线程结构体KTHREAD有一些APC相关的成员，这里说明一下作用：
~~~C
struct \_KTHREAD
{
UCHAR Alerted[2]; //0x3a
ULONG Alertable:1; //0x3c
struct \_KAPC\_STATE ApcState; //0x40
volatile ULONG ApcQueueable:1; //0xb8
UCHAR ApcStateIndex; //0x134
struct \_KAPC\_STATE\* ApcStatePointer[2]; //0x168
struct \_KAPC\_STATE SavedApcState; //0x170
}
~~~
- +3A：Alerted：线程可警惕性。
- +3C：Alertable：是否允许被APC唤醒。
- +40：ApcState 当前进程环境下的APC队列。当进程A中线程X挂靠到进程B时时，原ApcState会保存至SavedApcState防止环境错误。此时再向线程X插入APC时，执行环境变为进程B。也就是ApcState中的APC只看当前进程环境。
- +B8：ApcQueueable 是否允许插入APC，1允许，0不允许。默认为1。如：当线程正在执行退出（销毁）时，Windows会将这个值置为0，防止继续插入APC。
- +134：ApcStateIndex ApcStatePointer的索引。
- +168：ApcStatePointer ApcState指针。
- 当非挂靠时：0索引存ApcState，1索引存SavedApcState。
- 当挂靠时：1索引存ApcState，0索引存SavedApcState。
- +170：SavedApcState 备用APC队列。当线程处于挂靠状态时，此处保存挂靠前的ApcState，防止A进程APC在B进程环境下运行导致线性地址解析错误。
## \_KAPC\_STATE
APC管理结构
~~~C
//0x18 bytes (sizeof)
struct \_KAPC\_STATE
{
struct \_LIST\_ENTRY ApcListHead[2]; //0x0
struct \_KPROCESS\* Process; //0x10
UCHAR KernelApcInProgress; //0x14
UCHAR KernelApcPending; //0x15
UCHAR UserApcPending; //0x16
};
~~~
- ApcListHead：APC链表，0号是内核APC链表，1号是用户APC链表。链表结构指向 \_KAPC 的ApcListEntry成员。链表中每一个成员都是一个 \_KAPC->ListEntry 结构。
- Process：当前线程正在运行的进程环境。
- KernelApcInProgress：内核APC是否正在执行。
- KernelApcPending：内核APC是否需要执行。为1时说明ApcListHead的0号链表有值。
- UserApcPending：用户APC是否需要执行。为1时说明ApcListHead的1号链表有值。
## \_KAPC
APC成员结构
~~~C
//0x30 bytes (sizeof)
struct \_KAPC
{
UCHAR Type; //0x0
UCHAR SpareByte0; //0x1
UCHAR Size; //0x2
UCHAR SpareByte1; //0x3
ULONG SpareLong0; //0x4
struct \_KTHREAD\* Thread; //0x8
struct \_LIST\_ENTRY ApcListEntry; //0xc
VOID (\*KernelRoutine)(struct \_KAPC\* arg1, VOID (\*\*arg2)(VOID\* arg1, VOID\* arg2, VOID\* arg3), VOID\*\* arg3, VOID\*\* arg4, VOID\*\* arg5); //0x14
VOID (\*RundownRoutine)(struct \_KAPC\* arg1); //0x18
VOID (\*NormalRoutine)(VOID\* arg1, VOID\* arg2, VOID\* arg3); //0x1c
VOID\* NormalContext; //0x20
VOID\* SystemArgument1; //0x24
VOID\* SystemArgument2; //0x28
CHAR ApcStateIndex; //0x2c
CHAR ApcMode; //0x2d
UCHAR Inserted; //0x2e
};
~~~
- Type：对象类型，APC为0x12。
- SpareByte0：保留。
- Size：KAPC结构大小。
- SpareByte1：保留。
- SpareLong0：保留。
- Thread：当前APC属于哪个线程。
- ApcListEntry：当前线程的APC链表。
- KernelRoutine：内核APC回调函数。
- RundownRoutine：特殊APC回调函数，如线程挂起、线程结束等。
- NormalRoutine：普通APC回调函数。
- 当前为内核APC时，若此处有回调函数，则说明当前是个普通内核APC。若此处为空，则说明当前是个特殊内核APC。特殊内核APC插入时放在链表头部，普通内核APC插入时放到链表尾部。
- 当前为用户APC时，此处存放用户APC处理函数。
- NormalContext：APC回调函数参数1。当前为用APC时，此处存放实际的用户APC回调函数。
- SystemArgument1：APC回调函数参数2。
- SystemArgument2：APC回调函数参数3。
- ApcStateIndex：当前APC插入链表的方式。（具体作用在逆向代码时体会）
- 0：插入到原始环境的APC队列中。
- 1：插入到挂靠环境的APC队列中。
- 2：插入到初始化APC结构时的环境的APC队列中（使用KTHREAD的ApcStateIndex）。
- 3：插入到插入APC结构时的环境的APC队列中（使用KTHREAD的ApcStateIndex）。
- ApcMode：APC模式，0为内核APC，1为用户APC。
- Inserted：当前APC是否已被插入到链表中。

## 小结
APC的插入位置与传入的Enviroment函数相关。如果是插入到了备用APC队列中则执行返回。若是普通APC队列中则继续进行多个判断。

## KiInitializeUserApc分析
### 前导知识
用户APC的执行不像内核APC一样直接调用回调即可。用户APC需要在3环执行，因此在派发时需要将执行环境降到3环。执行APC结束后再返回0环。此时就会产生如下问题：
- 3环的代码从哪开始执行。
- 3环代码执行完毕后如何回到0环继续执行代码。
系统调用进0环时构造了一个TramFrame结构体用于保存3环进来时的环境，系统调用完成返回3环时通过TrapFrame中保存的寄存器信息来继续执行3环代码。因此通过更改TrapFrame中的值可以让当前代码在返回3环时改变执行位置。
由于执行完用APC后还要回到0环继续执行后续代码，但TrapFrame已经被更改。因此需要备份更改前的TrapFrame。KiInitializeUserApc中使用CONTEXT结构备份TrapFrame。
![image-20211220162159862](upload/attach/202112/867232\_36JMA6PUJQAZMSQ.jpg)
## KiUserApcDispather分析
函数内部直接取出栈顶的NormalRoutine并调用，将NormalContext、SystemParam1、SystemParam2作为参数传递。NormalRoutine为用户APC派发函数总入口，由Windows填充，函数为kernel32!BaseDispatherApc。
APC执行完成后通过ZwContinue函数回到0环继续处理剩余用户APC，并根据堆栈中的Context结构来填充TrapFrame结构。

- Size：KAPC结构大小。
- SpareByte1：保留。
- SpareLong0：保留。
- Thread：当前APC属于哪个线程。
- ApcListEntry：当前线程的APC链表。
- KernelRoutine：内核APC回调函数。
- RundownRoutine：特殊APC回调函数，如线程挂起、线程结束等。
- NormalRoutine：普通APC回调函数。

  - 3：插入到插入APC结构时的环境的APC队列中（使用KTHREAD的ApcStateIndex）。
- ApcMode：APC模式，0为内核APC，1为用户APC。

## 小结

当这个APC是自身线程插入给自身的，并且是个特殊内核APC，则会立马触发软中断执行。

如果这个APC是当前线程插入给其他线程的，且是个用户APC。当APC所属线程处于等待时，会尝试唤醒线程来执行APC。如果不是等待状态，则UserOrNormalKernel默认为0，插入后不执行APC。

如果这个APC是当前线程插入给其他线程的，且是个内核APC。当APC所属线程处于运行时，会直接触发软中断执行APC或通知其他核触发软中断执行。当APC所属线程处于等待时，会尝试唤醒线程来执行APC。其他状态则不会立马执行APC。

## KiInitializeUserApc分析

### 前导知识

用户APC的执行不像内核APC一样直接调用回调即可。用户APC需要在3环执行，因此在派发时需要将执行环境降到3环。执行APC结束后再返回0环。此时就会产生如下问题：

- 3环的代码从哪开始执行。
- 3环代码执行完毕后如何回到0环继续执行代码。

系统调用进0环时构造了一个TramFrame结构体用于保存3环进来时的环境，系统调用完成返回3环时通过TrapFrame中保存的寄存器信息来继续执行3环代码。因此通过更改TrapFrame中的值可以让当前代码在返回3环时改变执行位置。

由于执行完用APC后还要回到0环继续执行后续代码，但TrapFrame已经被更改。因此需要备份更改前的TrapFrame。KiInitializeUserApc中使用CONTEXT结构备份TrapFrame。

![image-20211220162159862](https://bbs.kanxue.com/upload/attach/202112/867232_36JMA6PUJQAZMSQ.jpg)

## KiUserApcDispather分析

# 5.进程挂靠函数逆向-KeStackAttachProcess

进程挂靠本质为将某个线程的CR3切换为目标进程的CR3，使该线程的内存映射走目标进程的GDT。函数KeStackAttachProcess就是用于进程挂靠的。

首先判断DPC是否处理完成，如果还有DPC没处理直接蓝屏。

![image-20211223153519537](https://bbs.kanxue.com/upload/attach/202112/867232_NKSWNH9J4RHVZ3H.jpg)

![image-20211223153546756](https://bbs.kanxue.com/upload/attach/202112/867232_APUV2UKR6R9WPYZ.jpg)

否则直接调用KiAttachProcess开始挂靠，第一次挂靠和多重挂靠处理方式不同。

![](https://bbs.kanxue.com/upload/attach/202112/867232_MWQ2ZS4ZN5BN9GA.jpg)

KiAttachProcess有4个参数：当前线程、目标进程、原IRQL等级、原ApcState要保存在哪。

![image-20211223153723787](https://bbs.kanxue.com/upload/attach/202112/867232_V2Y2629FFUBUXUG.jpg)

将当前线程的ApcState队列备份至第四个参数中并清空ApcState。

![image-20211223153844548](https://bbs.kanxue.com/upload/attach/202112/867232_C8CKXHG8GHHR787.jpg)

如果是第一次挂靠，直接交换ApcStatePointer成员并设置挂靠状态。如果是多重挂靠则没必要设置了。

![image-20211223154016997](https://bbs.kanxue.com/upload/attach/202112/867232_XB3J2VAQUMFFABC.jpg)

然后调用KiSwapProcess进行CR3的切换。切换前还会判断进程空间是否被交换到磁盘上了，如果被交换到磁盘上会先恢复进程空间再切换CR3。
