
# [原创]对无重定位表的PE文件模拟启动的另一种思路，欢迎各位交流讨论。

最近有个课后项目为模拟加载进程实现目标进程的控制，课上老师的具体思路如下：

- 思路：将目标PE包含入自己的进程，模拟PE加载过程

- 需要：

  1. 手动修复导入表。
  2. 手动修复重定位表(若无，则忽略)。
  3. 更改线程上下文。

- 具体流程：

  1. 高空运行壳程序(保证目标PE的`ImageBase`)。
  2. 将目标PE载入至其`ImageBase`。
  3. 修复导入表，重定位，拉伸，OEP创建线程运行

***

## 编码过程中遇到的问题

- 目标PE不存在重定位表
- **无法申请到指定的`ImageBase`**

> 由于我所测试的PE文件没有重定位表，如果不能`VirtualAlloc`到指定的`ImageBase`程序便无法运行。多方查询之后，发现大致的解决思路如下：
>
> ![图片描述](upload/attach/202107/922956_YGXAUA24MK9TMPA.png)
>
> 减少壳子的外部依赖`dll`，即尽可能少地隐式加载`dll`，从而使得目标`ImageBase`得以保证。

***

## 我的思路

问题的关键在于**目标PE的`ImageBase`必须保证**，但是操作系统能保证的只有壳子程序的`ImageBase`，利用这点特性，我们可以先用壳子程序先站住目标PE所需要的`ImageBase`，这样就能保证在加载过程中这个基址不会被其他资源占用。启动完毕后，壳子程序主动让出，之后再载入目标PE，这样就能保证目标PE的`ImageBase`了。

***

## 具体代码实现

- 需要：

  1. 手动重定位壳子程序

### 实现步骤:

0. 全局变量定义

```C++
TCHAR g_lpszFilePath[] = TEXT("test.exe");
DWORD g_dwOffset = NULL;
```

2. 加载壳子的相关PE信息

```C++
HMODULE hModule = GetModuleHandle(NULL);
//PEFILE为楼主自定义的类，相关函数功能如其名
PEFILE* lpSrcFile = new PEFILE((LPVOID)hModule, IMAGE);
DWORD dwSize = lpSrcFile->m_pOptionalHeader->SizeOfImage;
```

3. 因为全局变量保存在当前PE中，所以先计算jmp的偏移，再进行复制才能保证`g_dwOffset`的值有效，另外，`VirtualAlloc`的内存必须要为可执行页

```C++
//保存EIP偏移
__asm {
mov eax, L0
mov ebx, hModule
sub eax, ebx
mov g_dwOffset, eax
}
//拷贝当前PE
LPVOID lpDesBuffer = VirtualAlloc(NULL, dwSize,
MEM_COMMIT | MEM_RESERVE, PAGE_EXECUTE_READWRITE);
memcpy(lpDesBuffer, (LPVOID)hModule, dwSize);
//重定位修复
PEFILE* lpNewFile = new PEFILE(lpDesBuffer, IMAGE);
lpNewFile->FixupReloc();
//计算jmp跳转的位置
DWORD dwDesAddress = (DWORD)lpDesBuffer + g_dwOffset;
__asm {
mov eax, dwDesAddress
jmp eax
nop
L0:
nop
}
```

4.C++的类型检查，一言难尽，懒得给编译器类型转换了，直接汇编，方便快捷。

```c++
//卸载当前镜像
hModule = LoadLibrary(TEXT("ntdll.dll"));
DWORD ZwUnmapViewOfSection = (DWORD)GetProcAddress(hModule, "ZwUnmapViewOfSection");
__asm {
push NULL
call GetModuleHandle
push eax
call GetCurrentProcess
push eax
mov eax, ZwUnmapViewOfSection
call eax
}
FreeLibrary(hModule);
```

该段执行完毕之后，x64dbg里面已经可以发现`0x400000`被让出来了。

## 总结

这种方法相对于楼主网上查的方法，壳子程序的构建难度更低，减少了程序运行时的偶然性，省去了手动`GetProcAddress`的步骤，在部分细节进行优化后，基本可以保证申请到目标内存。

## 现有的不足

注意，上面两张图里面，`0x420000`的内存已经被占用，意味着一旦PE文件的`SizeOfImage`超过了`0x20000`，便无法申请成功，楼主现在的思路是在壳子程序的屁股后面加一个空节，`VirtualSize`设置为目标PE的`ImageSize`，人为地拉长主模块的长度，这样就可以保证所申请的空间大小足够使用。
