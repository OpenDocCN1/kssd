如果单纯从结果来讲，不用仔细分析都能够推知函数的功能是返回`GetProcAddress`的地址。

这个没有太多的难点，主要涉及一些基本的PE格式的问题，当然作者稍微是有亮点的。

这里没有给出注释，我们一起再来分析一下:

函数只有一个参数，那就是`kernel32.dll`的基址。所以，`[ebp+8]`，`[ebp-28]`都应该是`kernel_handle`，

我们看到`ADD EDX, DWORD PTR DS:[ECX+3C]`，看到`3C`，应该立刻联想到什么啦？

`IMAGE_DOS_HEADER`结构体的`e_lfanew`字段的偏移正好是`0x3C`，之前`ECX`，`EDX`又都被赋值为`kernel_handle`。所以这条语句得到了PE头`IMAGE_NT_HEADERS`的地址。

`[ebp-24]`就是PE头的地址。

然后我们看到`MOV ECX, DWORD PTR DS:[EAX+78]`。而对于`0x78`这个偏移，我们应该想到是`IMAGE_NT_HEADERS.IMAGE_OPTIONAL_HEADER32`的`IMAGE_DATA_DIREC`的偏移。即定位到了数据目录表!我们注意到此时`EAX+78`是数据目录表的地址，而

`DWORD PTR [EAX+78]`获得的是第一个目录表的第一个字段的值!

`IMAGE_DATA_DIRECTORY`的结构体:

`IMAGE_DATA_DIRECTORY  STRUC`

　　`VirtualAddress`                `DWORD`                ?                ;数据块的起始RVA

　　`Size`                                `DWORD`                ?                ;数据块的长度

`IMAGE_DATA_DIRECTORY        ENDS`

数据目录表一共有16个，其中第一个表为`IMAGE_DIRECTORY_ENTRY_EXPORT`导出表。

而看到`MOV DWORD PTR DS:[EDX+24]`的偏移`0x24`的时候，一时就不太反应得过来了

（后面还有`0x20,1C`的偏移）看看具体的结构吧:

`IAMGE_EXPORT_DIRECTORY                 STRUCT`

　　`0        Characteristisc                        DWORD        ?                ;未使用，总是0`

　　`4        TimeDateStamp                DWORD        ?                ;文件生成时间`

　　`6        MajorVersion                        WORD        ?                ;主版本号，一般为0`

　　`8        MinorVersion                        WORD        ?                ;次版本号，一般为0`

　　`C        Name                                DWORD        ?                ;模块的真实名称`

　　`10        Base                                        DWORD        ?                ;基数，加上序数就是函数地址数组的索引值`

　　`14        NumberOfFunctions        DWORD        ?                ;AddressOfFunctions阵列中的元素个数`

　　`18        NumberOfNames                DWORD        ?                ;AddressOfNames阵列中的元素个数`

　　`1C        AddressOfFunctions        DWORD        ?                ;指向函数地址数组`

　　`20        AddressOfNames                DWORD        ?                ;函数名字的指针地址`

　　`24        AddressOfNameOrdinals DWORD        ?        ;指向输出序列号数组`

`IMAGE_EXPORT_DIRECOTRY                ENDS`

前面的数字是代表字段在结构体的偏移，方便分析。

这样各个数据的含义比较明了了:

`[EBP-20]`，`[EBP-18]`,`[EBP-4]`分别是`AddressOfNameOrdinals`,`AddressOfNames`,

继续往下看，最开始有点茫然，后面把`47h`,`65h`,`74h`,`50h`都翻译成字符的时候突然有点明了了:

判断是否满足字符串的第0,1,2,4,8位是不是分别为`G`,`e`,`t`,`P`,`d`。

理所应当的，`GetProcAddress`满足条件，而且应该是唯一(至少是第一个)满足条件的！

如果条件满足，我们就找到了`GetProcAddress`这个API，不过这只是找到了它的字符串。

我们需要的是它的地址，自然这就引出如何通过字符串找到对应地址的问题。

之前我们提到的判断条件中有一个叫`IndexOfName`的参数，这个从程序的角度上看是循环执行的次数，进一步讲也是找到的`GetProcAddress`这个字符串所对应的RVA在`AddressOfNames`中的数组索引(下标)。

注意到有一个`AddressOfFunctions`的字段，是否说字符串的下标和地址的下标是一样的啦？差不多了，不是一致的，但是它们有个桥梁`AddressOfNameOrdinals`字段:

将`Name`的下标作为`AddressOfNameOrdinals`数组的下标，对应的数值就是`Address`的下标。

注意到`AddressOfNameOrdinals`数组的值是`WORD`类型的，而`AddressOfFunctions`数组的元素的值是`DWORD`类型的，所以我们看到在反汇编代码中是这样的:

```
mov     edx, [ebp+IndexOfName]

mov     eax, [ebp+kernel_AddressOfNameOrdinals]

movzx   ecx, word ptr [eax+edx*2]

mov     [ebp+IndexOfAddr], ecx

mov     edx, [ebp+IndexOfAddr]

mov     eax, [ebp+kernel_AddressOfFunctions]

mov     eax, [eax+edx*4]

add     eax, [ebp+arg_0]
```

片段执行完毕之后，`eax`的值就是`GetProcAddress`的地址值。

所谓的亮点也就是一个小技巧而已，顺带复习了一下PE格式的相关内容。

首先，将字符串:`VtrualAllocTx`的第1位字符`t`变成`i`，第`C`位字符`T`变成`E`，字符串就成了`VirtualAllocEx`，后面通过之前得到的`GetProcAddress`获取其地址，然后就能通过它进行获取内存的操作。



我们注意到一个内存地址：`0x403000`，还记得前面的Peid的截图吗？看到`.text6`节区：`V.offset 3000`

在内存当中我们查看，目前都是一些没有特别意义的数据，当然在后面就能清楚作用了。

`Sub_401390`的作用已经标记出来：返回传入地址的前一个DWORD地址的值。

上面片段中调用的时候传入的是`0x40300+0x4`，那么返回的就是`[0x40300]`，从内存中可以看到该数据是`0x1700`。

这个值传入了`sub_4013A0`函数，该函数的作用是申请指定大小的内存空间：

```
push    ebp
mov     ebp, esp
push    40h             ; PAGE_EXECUTE_READWRITE
push    3000h           ; MEM_COMMIT | MEM_RESERVE
mov     eax, [ebp+arg_0]
push    eax
push    0
push    0FFFFFFFFh
call    VirtualAllocEx     ;之前得到的VirtualAllocEx的地址
pop     ebp
retn
```

关键要注意的是参数`0x40`：`PAGE_EXECUTE_READWRITE` 说明申请的这些空间有执行的权限，这一点需要特别留意。接着对申请的空间进行了清0操作。

根据程序运行的结果，内存空间[`0x3E0000`，`0x3E1700`)返回给程序运行，并且拥有可执行权限。

```c
+0x00c Ldr              : Ptr32 _PEB_LDR_DATA

typedef struct _PEB_LDR_DATA {

ULONG Length;                            //+0x000

BOOLEAN Initialized;                       //+0x004

PVOID SsHandle;                           //+0x008

LIST_ENTRY InLoadOrderModuleList;          //+0x00C

LIST_ENTRY InMemoryOrderModuleList;       //+0x014

LIST_ENTRY InInitializationOrderModuleList;    //+0x1C

} PEB_LDR_DATA, *PPEB_LDR_DATA;
```

在`PEB_LDR_DATA`偏移`0x1C`处是`InInitializationOrderModuleList`。

```c
typedef struct _LDR_MODULE

{

    LIST_ENTRY        InLoadOrderModuleList;            // +0x000

    LIST_ENTRY        InMemoryOrderModuleList;          // +0x008
```



```c
    LIST_ENTRY        InInitializationOrderModuleList;  // +0x010
    PVOID             BaseAddress;                      // +0x018
    PVOID             EntryPoint;                       // +0x01C
    ULONG             SizeOfImage;                      // +0x020
    UNICODE_STRING    FullDllName;                      // +0x024
    UNICODE_STRING    BaseDllName;                      // +0x02C
    ULONG             Flags;                            // +0x034
    SHORT             LoadCount;                        // +0x038
    SHORT             TlsIndex;                         // +0x03A
    LIST_ENTRY        HashTableEntry;                   // +0x03C
    ULONG             TimeDateStamp;                    // +0x044
                                                        // +0x048
} LDR_MODULE, *PLDR_MODULE;
```

每个加载的模块都有一个`LDR_MODULE`结构体，其中的`BaseAddress`字段是模块在内存当中的基地址，`BaseDllName`指向一个`UNICODE_STRING`，其包含模块的名称(`kernel32.dll`等)。

而现在我们能够定位到`PEB_LDR_DATA`，如何转到`LDR_MODULE`啦？我们发现它们有三个'相同'的字段:

```c
    LIST_ENTRY        InLoadOrderModuleList;
    LIST_ENTRY        InMemoryOrderModuleList;
    LIST_ENTRY        InInitializationOrderModuleList;
```

所有的`LDR_MODULE`结构体我们通过三个`LIST_ENTRY`双向链表结构可以连接在一起，遍历寻找。而通过`PEB_LDR_DATA`的三个`LIST_ENTRY`字段中的某一个，可以定位到上述的双线链表中的'头'和'尾'节点。这样就可以遍历出加载的模块。

```asm
003F09B2    MOV EAX,DWORD PTR DS:[ESI+8]
003F09B8    MOV EDI,DWORD PTR DS:[ESI+20]
```

需要注意的是这两处的偏移0x8和0x20！第一反应有点蒙。

主要到程序是通过`InInitializationOrderModuleList`'’跳转‘到`LDR_MODULE`结构体中的，所以此时`ESI`的值相对于`LDR_MODULE`结构体在内存中的首地址是有0x10的偏移的！(双向链表连接的是`InInitializationOrderModuleList`字段而不是`LDR_MODULE`结构体)

所以，`0x8+0x10=0x18`,偏移指向的是`BaseAddress`，`0x20+0x10=0x30`的偏移指向的是:

`BaseDllName.Buffer`字段(模块名的Unicode字符串)

而`MOV ESI,DWORD PTR DS:[ESI]`，则通过双向链表遍历下一个节点数据(下一个模块信息)。

这样理解应该就比较容易了，当然有些知识点还没有扩展开来，作为下一步的学习计划，而就本文的主题而言，分析到这里就行了。

a. 从`fs:[30h]`获取`PEB`地址  
b. 从`PEB`的0x0c偏移获取`PEB_LDR_DATA`地址  
c. 从`PEB_LDR_DATA`偏移0x1c]获取`InInitializationOrderModuleList.Flink`  
d. 从`InInitializationOrderModuleList.Flink`开始前向遍历循环链表  
e. 获取`LDR_MODULE`结构的`BaseAddress`、`FullDllName`信息。

## 5.远线程相关操作

继续往下，`sub_3F09D0`是获取`GetProcAddress`，思路和之前获取的方法差不多，这里为了节约篇幅就省略了。

`sub_3F0970`通过随机函数，计算机名等生成0x20个16进制的随机数据。

`sub_3F1858`是将本进程的权限设置为调试权限，这样可以进行远线程注入。

`Sub_30F0F60`是进行远线程注入的主要部分:

也许这个时候比较'安全'了吧，作者也不太采用一些特别的方法。

## 7.补充

之前留了一个问题，`Sub_401490`函数里面第二次修复的数据到底起什么作用啦？

通过之前的分析，我们知道第二次修复的时候偏移为0x1000。`Notepad.exe`进程空间内的远线程的所在的内存区域首地址为0xAC0000，加上0x1000为0xAC1000，我们来看看相应的代码:

![](https://bbs.kanxue.com/upload/attach/201205/372322_npot7s51ocymrp6.png)

![](https://bbs.kanxue.com/upload/attach/201205/372322_xg5h0t092lmrn1f.png)

相对于0xAC1000的偏移:

```plaintext
0x02: AC0300
0x0A:AC0300
.。。。
0xc607:AC18E0
```

在最后一次进行数据修之前，那些偏移的值分别为:`3F0300`，`3F0300`，。。。`3F18E0`

而我们发现，第二次修复的这些数据要么是作为变量地址，要么是作为`API`的地址。如果不修复的话，引用肯定是错误的，这是不是有点类似于重定向的作用啦。我们我们可以判断出其作用就是重定向数据。
