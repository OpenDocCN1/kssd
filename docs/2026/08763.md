
# 原创DXX CX NX 调试原理

思路来自于山总的调试器对系统打补丁。

## WIN10 下双机调试原理

**DNF**: HOOK `KdpTrap`，解决登陆的时候`WINDBG`一直抛出异常，过滤是不是`TASLogin.exe`在抛出异常，如是的话直接返回 `return STATUS_SUCCESS;`

```cpp
NTSTATUS TwoMachineDebugging::HookedKdpTrap(
    IN PKTRAP_FRAME TrapFrame,
    IN PKEXCEPTION_FRAME ExceptionFrame,
    IN PEXCEPTION_RECORD ExceptionRecord,
    IN PCONTEXT ContextRecord,
    IN KPROCESSOR_MODE PreviousMode,
    IN BOOLEAN SecondChanceException
)
{
    PEPROCESS hp = PsGetCurrentProcess();
    if (!_stricmp((char *)PsGetProcessImageFileName(hp), "TASLogin.exe"))
    {
        return STATUS_SUCCESS;
    }
    return OriginalKdpTrap(TrapFrame, ExceptionFrame, ExceptionRecord, ContextRecord, PreviousMode, SecondChanceException);
}
```

1. `SharedUserData->KdDebuggerEnabled = TRUE;` 这一步可以在`WINDBG`里来设置，也可以用上述代码实现。
2. 定时器循环对`KdDebuggerEnabled`设置为`1`。

```cpp
VOID
Pass
KdDebuggerEnabled
(
    __in struct _KDPC *Dpc,
    __in_opt PVOID DeferredContext,
    __in_opt PVOID SystemArgument1,
    __in_opt PVOID SystemArgument2
)
{
    __try
    {
        *KdDebuggerEnabled = 0x1;
    }
    __except (1)
    {
        return;
    }
    KeSetTimer(&g_PassObjTimer, g_PassObjTime, &g_PassObjDpc);
    return;
}
```

3. 对于某些奇葩系统，TX采用了扫注册表的奇葩方案。具体什么方案，通过`msconfig`开启调试，注册表会发生变化。这个方案可以采取HOOK读取注册表的函数，或者手动去`msconfig`关闭调试模式不重启来解决。我选择了后者。

## DXF

### OD CE 本地附加调试

我记得原来有人问过我，XX在WIN10是不是清空`DebugPort`就不清空了。我原来不分析过，这几天在研究发现确实是清空了。1803也好，WIN7也好，都清空了。

他的清空原理就是调试器退出的原理，所以不触发`PG`。调试器退出调用（已经到R0）`NtRemoveProcessDebug`来移除调试对象，也就是`DebugPort`里的值。

`NtRemoveProcessDebug`的定义：

```cpp
NTSTATUS NtRemoveProcessDebug(IN HANDLE ProcessHandle, IN HANDLE DebugHandle);
```

参数1：`ProcessHandle` 进程句柄  
参数2：调试句柄 `NtCreateDebugObject` 返回

XX通过这个函数来清空了`DebugPort`句柄。说白了就是调试器退出的原理，这样就不会触发`PG`，很高的手法。（个人水平不咋地，感觉这样真的很NB。）

这样一来肯定有人要问了：你是如何分析出来XX调用的`NtRemoveProcessDebug`？这个很简单。直接对`DebugPort`下写断点：`ba w1 EPRPCRESS + 0X420`，断下来之后`k`栈回溯，就会发现HOOK了`NtRemoveProcessDebug`，R0的事就已经结束了。

## R3

CE OD对DXX附加会发现游戏直接崩溃。这个是为什么？其实它是个通用的应用层反调试手法：自己给自己制造异常，自己处理。如果`OD`抢着处理这个异常，反而会使进程崩溃。

解决方案很简单：直接用结束这个线程就可以。（经过我测试几款游戏，发现保护强度由大到小排：`CF` - `DNF` - `NZ`）

我们可以通过`WINDBG`附加游戏来找出这个线程ID是多少在发送异常。找到发送异常线程后，我们通过线程入口地址的后4位作为特征来结束这个线程，这样就可以解决调试器附加游戏崩溃的问题。

## 最后最关键的一步

恢复`DbgUiRemoteBreakin`：远程中断，附加调试器时调试器会发送信息让进程走这里。

以上就是CX DXF的调试解决方案。

## NX

我为什么把NX单独拿出来说呢？因为它是实在太弱了。它只需要创建OB恢复权限，恢复R3的`DbgUiRemoteBreakin`，结束异常发布线程就没了。
