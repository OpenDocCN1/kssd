# 2019 年软件安全的现状
\*\*...以及处理应对的办法\*\*
在这篇文章中，主要谈到了我对过去一年中软件设计和开发状态的一些观察，并且试图今年找到一个更加理性的成长路线。我的观点可能会局限于过去7年半的客户端软件安全性的经历。 尽管如此，对我来说也存在着广泛的趋势和关于行业未来走向的明显迹象。
我希望这篇文章对各种安全人员都有用：不仅是工程师，还有用户体验设计师和研究人员，项目/产品经理，业务经理以及运营人员。 无论如何，通向成功的路径都离不开这些人的帮助。 这篇文章比以往来说包含了更多的链接， 希望这会帮到你们。
下面大部分的关键问题就是复杂性。 硬件，软件，平台和生态系统通常过于复杂，我们的许多安全，隐私和滥用问题源于此。

<a href="elink@ca2K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6A6L8X3k6J5k6i4q4#2k6h3&6@1L8s2W2Q4x3X3g2G2M7X3N6Q4x3V1j5J5x3o6p5^5i4K6u0r3x3o6W2Q4x3V1k6@1K9r3g2Q4x3X3c8V1k6i4k6W2L8r3!0H3k6i4u0Q4x3X3c8W2P5s2m8W2M7X3W2W2L8X3y4W2i4K6u0V1j5X3q4A6N6q4)9J5k6r3q4F1k6q4)9J5k6s2y4%4K9i4c8U0K9q4)9J5c8R3`.`.">网络性能危机</a>（另见hot<a href="elink@c21K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6A6k6r3I4W2N6$3!0J5k6s2y4Q4x3X3g2U0L8$3#2Q4x3V1k6@1j5h3I4C8M7#2)9J5c8Y4N6W2j5Y4y4A6N6r3g2Q4y4h3k6G2j5X3g2K6K9i4c8&6i4K6u0W2K9s2c8E0">[即时评论</a>]）也是类似的情况：非常浪费，并且还没（尚未？......）有自我限制。在过去，我不得不说，即使性能有限，<a href="elink@59aK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6U0L8$3&6X3k6i4u0W2L8X3y4W2M7#2)9J5k6h3!0J5k6h3W2D9L8s2W2Q4x3X3g2U0L8$3#2Q4x3V1k6%4k6h3t1J5k6i4S2H3L8#2)9J5c8Y4N6W2j5X3g2^5M7$3j5J5x3o6l9&6i4K6u0r3M7s2g2T1L8r3W2U0i4K6u0r3M7$3y4Z5k6h3c8#2L8r3g2Q4x3V1k6K6M7r3g2S2K9$3g2J5i4K6u0r3x3e0l9I4y4R3`.`.">安全性也是可以承受的</a>。通过减少明显的膨胀和启用不太明显的优化，可以同时获得性能和安全性，而且现在是可能的。当时的根本原因和现在一样：太多的开发人员没有使用和他们的用户群一样的客户端系统，他们不知道他们所产生的网络、内存和CPU成本。以前，这些成本很难看到。而现在情况大不相同了：每个浏览器都有一个非常好的 Dev Tools 控制台，没有理由不去使用它。
我对像 NPM，CPAN，go get 等这样的依赖包管理系统感到厌恶，它们可能比手动依赖管理更危险，尽管这种做法存在巨大风险，正是因为它们使您的项目依赖图的发展变得更加“容易” - 从而隐式地增加了您信任的个人和组织的数量。 （并且<a href="elink@54cK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2@1K9r3g2J5k6h3N6A6M7%4c8W2M7W2)9J5k6h3y4G2i4K6u0W2N6h3E0Q4x3V1j5J5x3o6p5^5i4K6u0r3x3e0q4Q4x3V1j5J5y4W2)9J5c8X3&6H3L8g2)9#2k6Y4u0W2M7r3!0Q4y4h3k6T1K9i4c8U0L8$3W2F1i4K6g2X3M7%4c8W2j5h3I4W2M7W2)9J5c8R3`.`.">他们的可信度可能会突然变得更糟</a>。）当语言的标准库存在重大差距时，第三方开发人员将急切地用新的依赖关系来填补这些空白，从而以便（并不总是有意识地）继承下去。我强烈支持 那些[正在努力填补 JavaScript 标准库中的空白](<<mark class="encrypted">b7cK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4K9i4c8Z5N6h3u0Q4x3X3g2U0L8$3#2Q4x3V1k6@1j5K6x3&6i4K6u0r3M7s2u0G2M7r3!0K6j5h3I4Q4x3X3c8B7j5i4k6S2M7$3y4J5K9i4m8@1i4K6u0V1M7%4c8S2L8X3c8S2M7X3c8Q4x3X3c8D9K9h3u0J5j5i4u0&6i4K6u0r3K9i4y4K6N6h3g2K6i4K6u0r3x3e0W2Q4x3U0V1`.</mark> 的人的做法。
社交媒体继续放大人们的最坏情绪，而<a href="elink@c55K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2F1P5i4c8A6L8h3g2K6i4K6u0W2j5$3!0E0i4K6u0r3x3U0l9I4z5q4)9J5c8U0p5I4i4K6u0r3x3U0W2Q4x3V1k6@1k6h3y4Z5L8X3!0D9L8$3N6&6i4K6u0r3k6$3g2G2M7X3N6W2i4K6u0V1M7$3!0J5L8%4y4Q4x3X3c8X3j5h3y4W2j5X3!0G2K9#2)9J5k6s2y4Z5k6i4u0&6L8q4)9J5k6s2y4S2L8X3c8T1k6i4u0Y4i4K6u0W2K9s2c8E0L8l9`.`.">社交媒体公司的一些高管仍然是问题的一部分</a>。处理社交媒体的毒性和滥用仍旧是一项长期的，需要多方面的努力， 但作为工程师、项目经理、设计师和管理者，我们可以立即做的一件事是将“参与”作为“成功”的主要或唯一衡量标准。它具有游戏性和游戏性[保留一个游戏性就好]，并且无法在社交媒体上远程捕捉真人的真实体验。人们的经历往往 <a href="elink@266K9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8Y4y4W2M7X3W2G2N6i4y4H3L8$3&6&6i4K6u0W2j5$3!0E0i4K6u0r3N6s2u0G2N6h3u0D9k6g2)9J5k6r3q4@1i4K6u0V1N6r3S2W2i4K6u0V1K9$3!0G2L8r3q4A6k6q4)9J5k6s2m8G2K9h3&6@1i4K6u0r3">非常糟糕</a>，我们作为软件开发人员负责处理我们构建的一切后果。我们是在鼓励人们学习和成长，还是在放大纳粹（Nazis）和契卡（前苏联秘密警察组织 -- Chektists）的蠢货？坚持<a href="elink@bf5K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2W2k6X3k6Q4x3X3g2G2M7X3N6Q4x3V1k6V1k6h3g2H3L8r3W2F1K9%4y4Q4x3V1j5J5x3o6p5^5i4K6u0r3x3o6c8Q4x3V1k6H3L8r3q4@1k6X3!0J5L8g2)9J5k6r3y4W2L8Y4y4G2M7Y4y4Z5K9i4m8Q4x3X3c8%4L8$3&6@1i4K6u0V1k6X3W2^5i4K6u0V1K9h3&6@1k6i4u0F1k6i4b7`.">简单化的言论自由</a> 并不会让我们避免回答这个问题。
## 未来
不幸的是，我想解决所有这些问题。我在 2018 年度过了一段非常有趣的时间，从事底层的防守（[只是众多冒险中的一次](<<mark class="encrypted">222K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6F1L8$3&6U0L8$3#2T1j5i4c8S2L8Y4c8Q4x3X3g2G2M7X3N6Q4x3V1j5J5x3o6p5^5i4K6u0r3x3o6N6Q4x3V1j5I4z5g2)9J5c8X3q4H3M7r3I4A6j5$3q4@1K9h3!0F1i4K6u0V1M7s2u0A6L8X3y4A6M7r3q4D9M7#2)9J5z5g2!0q4c8W2!0n7b7#2)9^5z5g2!0q4c8W2!0n7b7#2)9^5b7#2!0q4z5q4)9^5x3q4)9^5b7#2!0q4y4q4!0n7z5q4)9&6y4q4!0q4z5q4!0n7c8W2)9&6z5q4!0q4y4W2)9&6b7#2)9^5z5g2!0q4y4g2!0n7c8g2)9^5z5q4!0q4y4g2!0m8y4q4)9&6b7g2!0q4y4g2!0n7y4#2!0m8y4g2!0q4y4q4!0n7c8q4)9&6b7#2!0q4z5q4!0m8y4W2)9^5x3g2!0q4y4g2)9^5x3g2)9&6b7g2!0q4x3#2)9^5x3q4)9^5x3R3`.`.</mark> （迫切需要减少许多环境特权！）在帮助获取需要的HTTPS时，我还发挥了很小的作用，而这是值得的 。
但是，我发现最令人头疼的问题 - 一般的滥用类别 - 并不属于我最专业的领域。我的注意基本在语言问题上：有意义的界面，符合人体工程学和安全的库，内存安全性和类型安全性。但这种滥用让我感到心痛。
尽管如此，我看到人们确实提供了 20 或 10 或 5 年前似乎不可能实现的软件改进，我们真的在取得进步。这是我想在2019年看到的内容：
- 抛弃使用“参与度”作为唯一或主要指标的想法。
- 工程社区的社会化政策思考。是时候担负起作为成年人的责任了，我们做的事情很重要（否则我们不会这样做，对吧？），这意味着我们需要考虑并处理后果。
- 提供全面改善网络性能的优势：一个更大的 JavaScript 标准库；框架中的性能提升；工具的改进；客户端干预和预算。
- 破除掉内存不安全是可以接受的想法，并且用内存安全的语言来替换那些原先用内存不安全语言编写的软件。这包括对现有应用程序的直接重写（<a href="elink@24aK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2B7L8$3g2D9L8$3&6K6L8$3k6@1N6$3q4J5k6g2)9J5k6h3y4G2L8g2)9J5c8U0t1H3x3o6m8Q4x3V1j5H3y4q4)9J5c8U0l9$3i4K6u0r3N6r3S2A6L8X3N6K6i4K6u0V1P5h3!0#2i4K6u0V1M7$3S2G2N6h3I4V1i4K6u0V1L8X3g2$3k6i4u0Q4x3X3c8V1L8#2)9J5k6s2m8S2M7Y4c8Q4x3X3c8A6i4K6u0r3">Joel 说这样做并不是很好</a> ）；大多数情况下，我只看到零碎的，直接重写组件（如Servo），以及完善类别中的新应用程序（比如 Xi 和 CrosVM ）。 新的应用程序也让我们有机会重新思考原有的设计，正如 Xi 所做的那样（通过其跨平台，客户端/服务器，多前端设计）。
- 社会化简单的价值，并抛弃所有层次的复杂性：用户体验、语言、库、框架。特别是，没有人应该在 C++ 中启动一个新的项目。
聪明人已经开始在所有的这些事情上努力工作了！我们可以让行业更接近需求，更好地为人们服务。未来更加严峻，还有很多工作要做...

# 2019 年软件安全的现状

**...以及处理应对的办法**

在这篇文章中，主要谈到了我对过去一年中软件设计和开发状态的一些观察，并且试图今年找到一个更加理性的成长路线。我的观点可能会局限于过去7年半的客户端软件安全性的经历。 尽管如此，对我来说也存在着广泛的趋势和关于行业未来走向的明显迹象。

我希望这篇文章对各种安全人员都有用：不仅是工程师，还有用户体验设计师和研究人员，项目/产品经理，业务经理以及运营人员。 无论如何，通向成功的路径都离不开这些人的帮助。 这篇文章比以往来说包含了更多的链接， 希望这会帮到你们。

下面大部分的关键问题就是复杂性。 硬件，软件，平台和生态系统通常过于复杂，我们的许多安全，隐私和滥用问题源于此。

- 恶意软件，垃圾软件或人们故意安装的 “无用软件”。 （这些通常列在合法的商店中，随硬件的设备驱动程序一起提供，或者与边缘软件捆绑在一起。）

[正如预言所说](https://bbs.kanxue.com/elink@67eK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2U0L8q4)9J5k6h3y4S2L8g2)9J5k6h3q4U0i4K6u0W2N6h3E0Q4x3V1k6Q4y4@1g2J5L8X3x3I4i4K6u0r3M7s2u0G2L8$3k6%4L8%4u0C8i4K6u0W2M7r3c8X3)，[工作量证明（proof-of-work）继续不起作用](https://bbs.kanxue.com/elink@23dK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2@1K9r3g2Y4N6h3q4J5k6r3W2S2L8W2)9J5k6h3y4G2L8g2)9J5c8Y4c8W2j5$3S2F1L8$3I4G2k6%4W2Q4x3V1j5J5x3o6p5^5i4K6u0r3L8X3!0$3i4K6u0r3x3o6g2Q4x3V1k6W2L8X3g2J5k6%4W2Q4x3X3c8U0L8%4y4@1i4K6u0V1L8$3k6Q4x3X3c8E0K9h3&6A6L8X3N6Q4x3X3c8T1K9i4c8U0L8$3W2F1i4K6u0V1L8h3!0J5k6g2)9J5k6s2c8Z5j5h3&6Q4x3X3c8@1N6$3W2U0k6g2)9J5k6s2c8Z5j5i4c8Q4x3X3c8G2k6W2)9J5k6r3y4G2M7s2m8W2M7W2)9J5k6r3!0J5i4K6u0V1k6$3!0D9k6l9`.`.)。在未来的几十年里，形势将会越来越严峻，嗯，“挑战”，所有的计算系统都将不得不证明它们的价值，相对于它们**所有的**成本 —— 包括碳和电子垃圾。我们再也不能把这些当作外部因素来一笑置之了。工作量证明系统将继续无法显示出足够的成本价值，甚至可能成为监管的障碍(如果它们不先饿死自己或崩溃的话)。

[网络性能危机](https://bbs.kanxue.com/elink@f1cK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6A6L8X3k6J5k6i4q4#2k6h3&6@1L8s2W2Q4x3X3g2G2M7X3N6Q4x3V1j5J5x3o6p5^5i4K6u0r3x3o6W2Q4x3V1k6@1K9r3g2Q4x3X3c8V1k6i4k6W2L8r3!0H3k6i4u0Q4x3X3c8W2P5s2m8W2M7X3W2W2L8X3y4W2i4K6u0V1j5X3q4A6N6q4)9J5k6r3q4F1k6q4)9J5k6s2y4%4K9i4c8U0K9q4)9J5c8R3`.`.)（另见hot[[即时评论](https://bbs.kanxue.com/elink@f81K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6A6k6r3I4W2N6$3!0J5k6s2y4Q4x3X3g2U0L8$3#2Q4x3V1k6@1j5h3I4C8M7#2)9J5c8Y4N6W2j5Y4y4A6N6r3g2Q4y4h3k6G2j5X3g2K6K9i4c8&6i4K6u0W2K9s2c8E0)]）也是类似的情况：非常浪费，并且还没（尚未？......）有自我限制。在过去，我不得不说，即使性能有限，[安全性也是可以承受的](https://bbs.kanxue.com/elink@ce2K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6U0L8$3&6X3k6i4u0W2L8X3y4W2M7#2)9J5k6h3!0J5k6h3W2D9L8s2W2Q4x3X3g2U0L8$3#2Q4x3V1k6%4k6h3t1J5k6i4S2H3L8#2)9J5c8Y4N6W2j5X3g2^5M7$3j5J5x3o6l9&6i4K6u0r3M7s2g2T1L8r3W2U0i4K6u0r3M7$3y4Z5k6h3c8#2L8r3g2Q4x3V1k6K6M7r3g2S2K9$3g2J5i4K6u0r3x3e0l9I4y4R3`.`.)。通过减少明显的膨胀和启用不太明显的优化，可以同时获得性能和安全性，而且现在是可能的。当时的根本原因和现在一样：太多的开发人员没有使用和他们的用户群一样的客户端系统，他们不知道他们所产生的网络、内存和CPU成本。以前，这些成本很难看到。而现在情况大不相同了：每个浏览器都有一个非常好的 Dev Tools 控制台，没有理由不去使用它。

我对像 NPM，CPAN，go get 等这样的依赖包管理系统感到厌恶，它们可能比手动依赖管理更危险，尽管这种做法存在巨大风险，正是因为它们使您的项目依赖图的发展变得更加“容易” - 从而隐式地增加了您信任的个人和组织的数量。 （并且[他们的可信度可能会突然变得更糟](https://bbs.kanxue.com/elink@5d2K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2@1K9r3g2J5k6h3N6A6M7%4c8W2M7W2)9J5k6h3y4G2i4K6u0W2N6h3E0Q4x3V1j5J5x3o6p5^5i4K6u0r3x3e0q4Q4x3V1j5J5y4W2)9J5c8X3&6H3L8g2)9#2k6Y4u0W2M7r3!0Q4y4h3k6T1K9i4c8U0L8$3W2F1i4K6g2X3M7%4c8W2j5h3I4W2M7W2)9J5c8R3`.`.)。）当语言的标准库存在重大差距时，第三方开发人员将急切地用新的依赖关系来填补这些空白，从而以便（并不总是有意识地）继承下去。我强烈支持 那些[正在努力填补 JavaScript 标准库中的空白](https://bbs.kanxue.com/elink@53bK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4K9i4c8Z5N6h3u0Q4x3X3g2U0L8$3#2Q4x3V1k6@1j5K6x3&6i4K6u0r3M7s2u0G2M7r3!0K6j5h3I4Q4x3X3c8B7j5i4k6S2M7$3y4J5K9i4m8@1i4K6u0V1M7%4c8S2L8X3c8S2M7X3c8Q4x3X3c8D9K9h3u0J5j5i4u0&6i4K6u0r3K9i4y4K6N6h3g2K6i4K6u0r3x3e0V1`.) 的人的做法。

社交媒体继续放大人们的最坏情绪，而[社交媒体公司的一些高管仍然是问题的一部分](https://bbs.kanxue.com/elink@003K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2F1P5i4c8A6L8h3g2K6i4K6u0W2j5$3!0E0i4K6u0r3x3U0l9I4z5q4)9J5c8U0p5I4i4K6u0r3x3U0W2Q4x3V1k6@1k6h3y4Z5L8X3!0D9L8$3N6&6i4K6u0r3k6$3g2G2M7X3N6W2i4K6u0V1M7$3!0J5L8%4y4Q4x3X3c8X3j5h3y4W2j5X3!0G2K9#2)9J5k6s2y4Z5k6i4u0&6L8q4)9J5k6s2y4S2L8X3c8T1k6i4u0Y4i4K6u0W2K9s2c8E0L8l9`.`.)。处理社交媒体的毒性和滥用仍旧是一项长期的，需要多方面的努力， 但作为工程师、项目经理、设计师和管理者，我们可以立即做的一件事是将“参与”作为“成功”的主要或唯一衡量标准。它具有游戏性和游戏性[保留一个游戏性就好]，并且无法在社交媒体上远程捕捉真人的真实体验。人们的经历往往 [非常糟糕](https://bbs.kanxue.com/elink@af2K9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8Y4y4W2M7X3W2G2N6i4y4H3L8$3&6&6i4K6u0W2j5$3!0E0i4K6u0r3N6s2u0G2N6h3u0D9k6g2)9J5k6r3q4@1i4K6u0V1N6r3S2W2i4K6u0V1K9$3!0G2L8r3q4A6k6q4)9J5k6s2m8G2K9h3&6@1i4K6u0r3)，我们作为软件开发人员负责处理我们构建的一切后果。我们是在鼓励人们学习和成长，还是在放大纳粹（Nazis）和契卡（前苏联秘密警察组织 -- Chektists）的蠢货？坚持[简单化的言论自由](https://bbs.kanxue.com/elink@253K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2W2k6X3k6Q4x3X3g2G2M7X3N6Q4x3V1k6V1k6h3g2H3L8r3W2F1K9%4y4Q4x3V1j5J5x3o6p5^5i4K6u0r3x3o6c8Q4x3V1k6H3L8r3q4@1k6X3!0J5L8g2)9J5k6r3y4W2L8Y4y4G2M7Y4y4Z5K9i4m8Q4x3X3c8%4L8$3&6@1i4K6u0V1k6X3W2^5i4K6u0V1K9h3&6@1k6i4u0F1k6i4b7`.) 并不会让我们避免回答这个问题。

## 未来

不幸的是，我想解决所有这些问题。我在 2018 年度过了一段非常有趣的时间，从事底层的防守（[只是众多冒险中的一次](https://bbs.kanxue.com/elink@ffeK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6F1L8$3&6U0L8$3#2T1j5i4c8S2L8Y4c8Q4x3X3g2G2M7X3N6Q4x3V1j5J5x3o6p5^5i4K6u0r3x3o6N6Q4x3V1j5I4z5g2)9J5c8X3q4H3M7r3I4A6j5$3q4@1K9h3!0F1i4K6u0V1M7s2u0A6L8X3y4A6M7r3q4D9M7H3`.`.)），而且还有很多工作要做。 （迫切需要减少许多环境特权！）在帮助获取需要的HTTPS时，我还发挥了很小的作用，而这是值得的 。

但是，我发现最令人头疼的问题 - 一般的滥用类别 - 并不属于我最专业的领域。我的注意基本在语言问题上：有意义的界面，符合人体工程学和安全的库，内存安全性和类型安全性。但这种滥用让我感到心痛。

尽管如此，我看到人们确实提供了 20 或 10 或 5 年前似乎不可能实现的软件改进，我们真的在取得进步。这是我想在2019年看到的内容：

- 抛弃使用“参与度”作为唯一或主要指标的想法。
- 工程社区的社会化政策思考。是时候担负起作为成年人的责任了，我们做的事情很重要（否则我们不会这样做，对吧？），这意味着我们需要考虑并处理后果。
- 提供全面改善网络性能的优势：一个更大的 JavaScript 标准库；框架中的性能提升；工具的改进；客户端干预和预算。
- 破除掉内存不安全是可以接受的想法，并且用内存安全的语言来替换那些原先用内存不安全语言编写的软件。这包括对现有应用程序的直接重写（[Joel 说这样做并不是很好](https://bbs.kanxue.com/elink@a7fK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2B7L8$3g2D9L8$3&6K6L8$3k6@1N6$3q4J5k6g2)9J5k6h3y4G2L8g2)9J5c8U0t1H3x3o6m8Q4x3V1j5H3y4q4)9J5c8U0l9$3i4K6u0r3N6r3S2A6L8X3N6K6i4K6u0V1P5h3!0#2i4K6u0V1M7$3S2G2N6h3I4V1i4K6u0V1L8X3g2$3k6i4u0Q4x3X3c8V1L8#2)9J5k6s2m8S2M7Y4c8Q4x3X3c8A6i4K6u0r3) ）；大多数情况下，我只看到零碎的，直接重写组件（如Servo），以及完善类别中的新应用程序（比如 Xi 和 CrosVM ）。 新的应用程序也让我们有机会重新思考原有的设计，正如 Xi 所做的那样（通过其跨平台，客户端/服务器，多前端设计）。
- 社会化简单的价值，并抛弃所有层次的复杂性：用户体验、语言、库、框架。特别是，没有人应该在 C++ 中启动一个新的项目。

聪明人已经开始在所有的这些事情上努力工作了！我们可以让行业更接近需求，更好地为人们服务。未来更加严峻，还有很多工作要做...
