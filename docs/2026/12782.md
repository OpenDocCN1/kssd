典型的用户态调试程序流程:

```

CreateProcess(…)

DEBUG_EVENT DebugEv;                  
DWORD dwContinueStatus = DBG_CONTINUE; 
while(true) 
{ 
WaitForDebugEvent(&DebugEv, INFINITE); 
dwContinueStatus = DebugEventHandler(&DebugEv);
ContinueDebugEvent(DebugEv.dwProcessId, 
DebugEv.dwThreadId, dwContinueStatus); 
}
```



CreateProcess调试方式打开被调试程序, WaitForDebugEvent等待调试事件, DebugEventHandler处理调试事件, ContinueDebugEvent恢复被调试程序,继续执行

首先从WaitForDebugEvent下手:
WaitForDebugEvent调用DbgUiWaitStateChange
DbgUiWaitStateChange (DBGUI\_WAIT\_STATE\_CHANGE StateChange, PLARGE\_INTEGER)
DbgUiWaitStateChange第一个是返回参数为一个返回的调试对象,第二个参数为超时时间
typedef struct \_DBGUI\_WAIT\_STATE\_CHANGE {
    DBG\_STATE NewState; //枚举常量,代表新的调试状态
CLIENT\_ID AppClientId; //包含进程和线程句柄
//描述详细信息的联合结构
    union {
        DBGKM\_EXCEPTION Exception;
        DBGUI\_CREATE\_THREAD CreateThread;
        DBGUI\_CREATE\_PROCESS CreateProcessInfo;
        DBGKM\_EXIT\_THREAD ExitThread;
        DBGKM\_EXIT\_PROCESS ExitProcess;
        DBGKM\_LOAD\_DLL LoadDll;
        DBGKM\_UNLOAD\_DLL UnloadDll;
    } StateInfo;
} DBGUI\_WAIT\_STATE\_CHANGE, \*PDBGUI\_WAIT\_STATE\_CHANGE;

DbgUiWaitStateChange 压入返回调试信息，超时时间，1,调试对象句柄,调用内核函数NtWaitForDebugEvent
内核里调试对象结构:

这里只看用户模式产生的异常
nt!KiDispatchException首先把TrapFrame封装成一个CONTEXT结构
然后判断是不是第一次异常 如果是则先判断是否发送给内核调试器,判断的条件包括DebugPort为空,内核调试的设置选项中是否接受用户态异常，该异常是否是内核调试器触发的,如果内核态调试器不处理此用户态异常则调用DbgkForwardException(第一次机会)发给调试器
关于第一次第二次异常:
调试器处理收到的异常,首先判断该异常的地址是不是用户用户引起的,如果不是,处理完成后,返回DBG\_CONTINUE,继续执行被调试程序,此时此异常已经修复,因此不会产生第二次异常,如果当前产生的异常是用户自己写代码造的异常,则有两种处理方法,第一种返回DBG\_CONTINUE继续执行(假装处理了),交给用户负责该异常,如果用户自己处理了该异常,如SEH handler里处理,则也不会产生第二次异常,如果用户没有处理该异常则会产生第二次异常,但是中间ntdll! KiUserExceptionDispatcher分发异常行为则被隐藏
第二种是返回DBG\_EXCEPTION\_NOT\_HANDLED 此时可以跟踪ntdll! KiUserExceptionDispatcher的异常分发, OD里的忽略异常则是第一次返回DBG\_CONTINUE,调试器如果接受到此断点已经是第二次异常且调试器未处理,则会再次调用DbgkForwardException发给异常端口,而异常端口指定的通常是windows子系统服务器进程(CSRSS)监听的Windows\apiport端口,CSRSS收到此消息后就会强行终止该进程,并向KiKispatchException回复真, 第二次异常如果调试器返回DBG\_CONTINU则调试器”假装处理了”,会导致异常不会在内核继续分发下去,但是当用户想继续执行后面代码,因为当前异常只是调试器假装处理了,又会触发第一次异常,死循环，周而复始,像使用windbg调试程序时,当一个异常自己没有处理时,如果一直使用G命令执行则会一直重复该异常(first chance,second chance,first chance …),原因就在于windbg在第二次异常时返回DBG\_CONTINU,”假装处理了”, 而OD里则是返回DBG\_EXCEPTION\_NOT\_HANDLED 此时OD左下方提示栏显示调试器无法处理异常,如果用户继续执行,则DbgkForwardException发给异常端口处理,结束应用程序.

系统对int3单字节断点做了特殊处理,不同于普通的断点形式int n的机器码0xcdn,大部分编译器对int3都会生成0xcc,中断后trapframe里保存的异常地址是产生异常指令的下一条指令地址,取出trapframe.eip,减1后保存到ebx, ebx作为参数传入CommonDispatchException函数里,CommonDispatchException用把ebx值存入EXCEPTION\_RECORD的异常地址字段,这样调试器处理异常调试事件时EXCEPTION\_RECORD的产生异常地址是正确的异常指令地址,但是当int3机器码为cd03时,因为机器码为2字节,所以EXCEPTION\_RECORD的产生异常地址不是机器码为cd的地址而是机器码为03的地址. 产生异常时线程的上下文CONTEXT中的eip不是断点地址+1,而是断点地址+2

前面已经分析EXCEPTION\_ACCESS\_VIOLATION异常消息的分发过程, EXCEPTION\_SINGLE\_STEP异常的分发过程与EXCEPTION\_ACCESS\_VIOLATION一致,故不再重复

其他几个异常消息还有另外几个调试事件都可下nt!DbgkpQueueMessage断点,重现调试事件,查看堆栈即可知道大致流程,与上面分析都一样

前面提到DbgkpQueueMessage向调试对象的事件列表插入调试事件后,通知调试器内核函数nt!NtWaitForDebugEvent的等待事件, nt!NtWaitForDebugEvent把要处理的调试事件转换为DBGUI\_WAIT\_STATE\_CHANGE结构体后返回到用户态的WaitForDebugEvent函数, WaitForDebugEvent根据返回的DBGUI\_WAIT\_STATE\_CHANGE的NewState字段,判断调试事件,封转成用户态的DEBUG\_EVENT,等待调试器处理完后,调用ContinueDebugEvent把调试器处理的结果(处理或不处理)通知正在等待的被调试程序

BOOL ContinueDebugEvent(
DWORD dwProcessId,
DWORD dwThreadId,
DWORD dwContinueStatus );

其中第一个参数是被调试程序的进程ID, 第二个参数是被调试程序通知调试器的那个线程的ID ,也就是DbgkpQueueMessage中通知并等待调试器回应的线程的ID, 第三个参数是调试器处理的结果
调用DbgUiContinue通过DbgUiContinue获取调试对象句柄然后进入内核函数NtDebugContinue
DbgUiContinue有两个参数 第一个是指向CLIENT\_ID指针 第二个是dwContinueStatus
