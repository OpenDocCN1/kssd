
```cpp
//mfc42d.Dll版本

PVOID GetDbgFromHandleAddr(HMODULE hModule)
{
    return GetProcAddress(hModule, (LPCSTR) 2220);
}

//mfc42.Dll版本

PVOID GetRlsFromHandleAddr(HMODULE hModule)
{
    return GetProcAddress(hModule, (LPCSTR) 2867);
}
```

对于静态链接的MFC程序，我们只能通过在主模块(exe文件)中搜索特征码来定位`FromHandle`。这里要注意，不同的MFC框架版本其`FromHandle`内部实现往往是不同的，此外，相同版本的MFC框架，其生成的Debug与Release版本的程序，`FromHandle`内部也是不同的。这两者组合起来，**若需要做一个通用的MFC Spy，我们需要提取很多版本的特征码**……这也是为什么网上流传的MFC Spy通用性都有待加强的原因。

不过好在，我们可以借助`flex`巧妙地完成这样的体力活，如下：

STEP1 自己编写对应的静态MFC程序样本，在其中打印出`FromHandle`的地址，方便我们定位函数

![](https://bbs.kanxue.com/upload/attach/201510/651791_x1cwjehrjp8p3bs.png)

STEP2 根据PE信息，将VA转换为文件偏移，用WinHex在文件中找到对应偏移，并拷贝对应字节作为特征码。

![](https://bbs.kanxue.com/upload/attach/201510/651791_lug6stn2w8y9xf2.png)

![](https://bbs.kanxue.com/upload/attach/201510/651791_nn9o48l3h2bkfka.png)

注意WinHex拷贝时，若使用“GREP Hex”，其结果可直接作为`lex`的正则表达式，我们就要用这种拷贝方式。

![](https://bbs.kanxue.com/upload/attach/201510/651791_9zufuwenbnaxnuu.png)

STEP3 特特征码中，要注意像`call`/`jcc`这样的相对跳的指令以及`push offset xxxx`这样的指令，它们之后所接的操作数不能作为特征码参考，我们在编写`flex`文件时要将其改为通配符

最后，我们编写出如下`lex`源码文件（**为重点明确，有省略，具体看源文件**）：

```cpp
%{

#include <stdio.h>
#include <string.h>
#include "Tokens.h"

unsigned int g_dwOffset  = 0;

%}
CALL \xE8[\x00-\xFF]{4,4}
PUSH_NUM \x68[\x00-\xFF]{4,4}
VC6_RLS_STC_PATTERN \x56\x57\x6A\x01{CALL}\x8B\xF0\xFF\x74\x24\x0C\x8B\xCE{CALL}\x8B\xF8\x56\x8B\xCF{CALL}\x8B\xC7\x5F\x5E\xC2\x04\x00
//... 各种特征码
%%

{VC6_RLS_STC_PATTERN} {
    return VC6_STC_RLS;
}

//... 找到特征码后各种对应处理方案

. {
    g_dwOffset += yyleng;
}

\r|\n {
    g_dwOffset += 1; //注意通配符 "." 是不匹配newline的
}

%%
int yywrap()
{
    return 1;
}

int FindMFCVersion(FILE *fp)
{
    yyin = fp;
    yyrestart(fp);
    g_dwOffset = 0;

    switch (yylex())
    {
    case VC6_STC_DBG:
        return VC6_STC_DBG;
        break;
    case VC6_STC_RLS:
        return VC6_STC_RLS;
        break;
    case VS2013_STC_RLS:
        return VS2013_STC_RLS;
    case  VS2013_STC_DBG:
        return VS2013_STC_DBG;
        break;
    }
    return 0;
}

unsigned int GetPatternOffset()
{
    return g_dwOffset;
}
```

其中，将`yylex()`再多包一层，成为`FindMFCVersion()`，并且加入`GetPatternOffset()`函数以获取特征码相对初始位置的偏移。这样做是使得封装性更好，而且，为了避开恼人的编译时头文件检查等，我推荐是直接将`FindMFCVersion`编译成`obj`文件供注入`dll`调用，**具体可参考附件里的对应工程**。

若不使用`flex`帮忙，通常定位特征码的方法，除了在目标函数内部找寻外，**还可以利用交叉引用寻找**（如某个函数调了`FromHandle`，先定位那个函数，再通过它定位`FromHandle`）。那样的策略更具有艺术性（可以找到某个特征码横跨好几个版本的MFC），不过**同时需要更多的精力去测试特征码的通用性、唯一性**。

### 3. 除数为常数的除法定式识别

编译器为了提供程序效率，对于一些特定的表达式，往往会进行优化，用**多条**效率高的指令取代一条效率低的指令（多条效率高的指令周期总和仍少于那条效率低的），也可能是多条指令配合，将有分支流程转为无分支流程。

因为优化的算法是有套路的，所以以上提到的“多条语句”组合在一起也是有套路的，这样的套路我们就称为“**代码定式**”了，按套路对汇编代码进行反解析，就要以得到相应的高级代码。

这里附给大家的是**除法定式的识别程序**，可以直接由IDA汇编代码得到对应的C语言代码。不过因为只支持一个定式一个定式的识别，所以使用前提大家还是得了解下除法优化的相关原理，**能看出某一块汇编代码是在做除法**。好在科锐的前辈已经整理得很完善，我就不啰嗦了，感兴趣可参考<http://bbs.pediy.com/showthread.php?t=113689>中的“**1.9、除法与取模运算的识别与优化原理**”

定式的识别是个苦力活，就是在不断调试语法怎样匹配，匹配成功后再根据优化算法逆回去求出源代码，具体大家看代码就可以体会。

![](https://bbs.kanxue.com/upload/attach/201510/651791_1xmx50iym219wu4.png)

让大家见笑的是，作为科锐的选做当天作业，这个程序还是很粗糙的：输入只能为IDA的反汇编代码（大小写敏感）。程序内部为防溢出用的是`__int64`（而没有使用大数运算库），因此某些情况下可能还是会溢出（虽然我没测出来）。大家把它当作一个智能一点专门针对除法识别的计算器就好……
