
看到日志 `linker: library "/system/lib/libnativehelper.so" ("/system/lib/libnativehelper.so") needed or dlopened by`，可以确定这就是 Android 7.0 开始采用的命名空间限制私有 API 调用。

对其进行过滤，把 LR 寄存器的值改为符合地址范围的值。这里我使用 `dlerror` 的地址，只要符合即可。通过日志可以看到已经成功。

![图片描述](https://bbs.kanxue.com/upload/attach/202001/670707_QDXQA67SVXYB5XW.png)

所以这就是我早期针对 Android 7.0 限制私有 API 的一种绕过方式。比起自己加载系统 so、自己解析，再通过偏移值确定地址，这种方式要好些……通过这还可以延伸出我动态注入时做的一件事情：全局绕过私有 API 限制。以前 Frida 没有这么做过，没看最近的代码，不确定现在是否也采用了这样的方法。

所以对于 hook `dlopen` 可以这么划分：

1. 低于 7.0 的版本，只 hook `dlopen` 即可。
2. 8.0 以上最好 hook `__loader_dlopen` 或者 `do_dlopen`。或者 hook `dlopen`，过滤发现是系统 so（限制的私有 so）时不取返回值，即不修改 LR 寄存器；或者自行解析、重组 `dlopen` 的指令，传入原来的 LR 寄存器，不推荐。
3. 7.0—7.1 的版本 hook `do_dlopen`，因为没有采用 `libdl.so` 做中转。
4. 全局关闭命名空间限制，使用私有 API。不是特别推荐，但其实我是这么做的。
5. 更投机取巧的方法：既然只要 LR 寄存器符合规则即可，那么可以针对 `dlopen`、`dlsym`，从 BL 指令转成先设置 LR 寄存器为某个 `libc` 等 so 里面的一个不常用的函数 `c`。常用的也不是不行，但是可能会对效率有影响。之后使用 B 指令跳转到备份或修复后的 `dlopen` 原函数执行。对 `c` 函数进行 hook，使用一样的跳板，只是 shellcode 有些不一样。

因为 `dlopen` 等函数执行完会跳回 `c` 函数，所以 LR 寄存器就是 `c` 函数的地址。只要 `c` 函数不是递归函数，那么就可以通过判断 LR 寄存器，区别出这是 `dlopen` 等函数的返回，还是其他函数正常调用的 `c` 函数。当是 `dlopen` 函数返回时，再跳回 `dlopen` 的 shellcode 处完成返回。

## 未解决的疑问

我记得梆梆也 hook 了 `dlopen`、`dlsym`，ARM 使用的是 Cydia Substrate 框架，在高版本上应该也存在这个问题。但是以前没仔细看，我记得应该没有特殊处理，比较奇怪。抽时间再逆向一下，除非它修改了生成的 shellcode：对于不是自己要 hook 的 so 就过滤掉，不修改 LR 寄存器。

## 已解决

后来抽时间看了一下，原来也是解析了 `loader_dlopen`、`dl__Z9do_dlopenPKciPK17android_dlextinfoPKv` 等符号：

```c
if (sdk_0 >= 24)
{
    if (g_addr_do_dlopen)
    {
        p_dlopen = (void *(**)(const char *, int))g_addr_do_dlopen;
```

所以也是参照上面的第 3 点来做的。不过它定位了一些 Android 源码中没有的符号，因此也存在兼容性问题？看来同样存在风险。毕竟这不是标准 C/C++ API，确实有可能被魔改。

`dlsym` 等其他几个函数也是类似的处理。甚至如果只是为了调用系统的私有 API，只 hook `loader_dlsym` 即可，使用 `dlsym(RTLD_DEFAULT, "xx")`，把 `loader_dlsym` 的第三个参数改为合法的地址。
