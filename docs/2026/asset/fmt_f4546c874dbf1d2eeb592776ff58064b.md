

# [原创]CVE-2017-7269：IIS 6.0 远程代码执行漏洞逆向分析记录

## 前言以及准备工作

关于 CVE-2017-7269，网上的大神们的分析都很有高度。我作为一个小白，拿着这种给了 `exp` 的漏洞，没有想太多，直接使用 `WinDbg` 和 `IDA` 动静结合进行调试分析。不过，这样可能造成分析有些片面，毕竟是纯逆向进行分析。

好了，首先说说环境。

环境：Windows Server 2003 R2 上开启 WebDAV 服务的 IIS 6.0。

工具：`WinDbg`、`IDA`

接着修改网上的 `EXP` 代码。我们现在不需要完美执行这个 `EXP`，需要的是让它崩溃，所以去掉作者添加的 `shellcode`，只保留 `EXP` 部分，如下图。

![](https://bbs.kanxue.com/upload/attach/202002/93_DMYTQQUDYBWY2HQ.jpg)

现在进行调试，`WinDbg` 直接附加进程。上网查了查，IIS 的进程名称为 `W3WP.EXE`，附加后使用 `g` 运行起来。接着运行修改后的 `EXP`。好了，如下图所示，它崩溃了。

![](https://bbs.kanxue.com/upload/attach/202002/93_2CUTJV5Q7GTYBU3.jpg)

退出 `WinDbg`，再次附加 `W3WP.EXE` 的时候，发现已经找不到这个进程了。这是 IIS 应用池机制的问题，解决办法有两个：

1. 备份虚拟机镜像。
2. 在 IIS 信息服务管理器里面，把网站下的任意网站右键浏览一下，`W3WP.EXE` 就会重新启动。

接着进行调试。这个漏洞作者给出了漏洞函数 `ScStoragePathFromUrl`。使用 `IDA` 进行静态分析，那么 `dll` 是哪个呢？作者并没有写明 `dll` 名称，但是在 IIS 信息服务管理器开启 WebDAV 服务的时候可以知道，如下图。`Dll` 名称为 `httpext.dll`。

![](https://bbs.kanxue.com/upload/attach/202002/93_SNTW54GW229RQ4A.jpg)

我们直接把这个 `dll` 放入 `IDA`，加载其符号表。然后使用 `CTRL+P` 查找函数，输入函数名 `ScStoragePathFromUrl`，双击进行分析。

![](https://bbs.kanxue.com/upload/attach/202002/93_BBYTHDETMWQP6FE.jpg)

其中很有趣的地方是里面有明显的内存拷贝，而且有 `if` 判断，那么是简单的栈溢出吗？

![](https://bbs.kanxue.com/upload/attach/202002/93_DRRAD5BJJAAJVXW.jpg)

## 漏洞原理攻击分析

我们继续进行动态调试。知道了 `dll` 的名称，我们先用 `sxe ld:httpext` 下加载 `dll` 时的断点。

通过 `IDA` 知道了 `ScStoragePathFromUrl` 这个函数的 `retn` 地址为 `0x673F702C`，那我们直接在这个地址下断点，看看每次执行完这个函数时栈返回地址是否被覆盖。但是不幸的是，我尝试几次，返回地址没有被明显地直接覆盖，最后都会以崩溃告终。

![](https://bbs.kanxue.com/upload/attach/202002/93_FM43SDNBUT47CVA.jpg)

好像直接观察堆栈并不能看出什么来，换个思路，完全从逆向的角度分析。先不断下断点定位崩溃函数，看函数崩溃的原因是什么。经过几次断点后，定位到了 `ScStoragePathFromUrl` 内部的一个函数 `ScStripAndCheckHttpPrefix`，这个函数代码如下。

![](https://bbs.kanxue.com/upload/attach/202002/93_NZ2QQVD8PZ45TVV.jpg)

没有错，这个函数调用了虚函数，那么这个洞是简单的堆溢出吗？

再次进行调试。这次进行大量的逆向数据记录，希望从数据的变化中分析出这个洞的成因到底是什么。

首先我们要确定一下需要关注的数据是什么？（地址通过 `IDA` 得到。）

1. 内存拷贝代码地址：`0x673F6F99`
2. 判断是否进行数据拷贝的代码地址：`0x673F6F55`

于是 `WinDbg` 下断点，执行情况如下：

![](https://bbs.kanxue.com/upload/attach/202002/93_JT2N6B94ENHVW98.jpg)

可以发现，这个数据拷贝并不会每次进入 `ScStoragePathFromUrl` 函数都会进行拷贝，而且拷贝次数只有 3 次，分别是第二次调用 `ScStoragePathFromUrl` 函数、第三次调用 `ScStoragePathFromUrl` 函数和第五次调用 `ScStoragePathFromUrl` 函数。（其实没有进行拷贝的调用也很重要。）

既然拷贝了三次数据，那么就下断点进行查看，到底拷贝了什么数据，以及对堆栈造成了什么影响。

再进入 `WinDbg`，只对内存拷贝进行下断点，并且每次跟完全部的拷贝。

第一次拷贝的数据范围：

`edi`：`0130f804~0130f958`

（第二次和第三次执行时，`edi` 的地址会大幅变化，但是受篇幅限制，不能全部展示。）

现在讲讲通过上面的代码，再结合 `IDA`、`WinDbg`，我自己找到的数据关系。

一共三次大内存拷贝，每次进行一次大内存拷贝时，有 4 次小拷贝，其中有两次不会拷贝，而另外进行拷贝的两次的地址 `edi` 是连续的，而 `esi` 是不连续的。

如果 `edi` 的地址在某次大拷贝时变成一个对象的地址，然后进行拷贝，是不是就可以利用了呢？原作者也确实这么做了。

三次大内存拷贝的 `edi` 地址变化范围如下：

- 第一次拷贝的数据 `edi`：`0x0130f804~0x0130f958`
- 第二次拷贝的数据 `edi`：`0x680312c0~0x68031464`
- 第三次拷贝的数据 `edi`：`0x0130fab4~0x0130fc08`

通过数据好像看起来，第一次和第三次好像是栈溢出，第二次是堆溢出。

但是 `edi`、`esi` 的值是怎么被修改的？`edi` 的值来自哪里？`esi` 的值来自哪里？这个问题需要弄明白。

通过 `IDA` 和 `WinDbg`，我找到了这些代码：

```text
edi 值来源 [ebp-450]
.text:673F6F99                 mov     edi, [ebp-450]

[ebp-450] 来源 eax
.text:673F6C9B                 mov     [ebp-450], eax

eax 来源 [ebp+8]
.text:673F6C93                 mov     eax, dword ptr [ebp+8]
```

前两次的 `ebp` 没有变化，都是 `0130f798`，所以 `ebp+8` 地址不变，为 `0130f7a0`。

通过看上面的第一次拷贝范围可以知道，第二次开始的 `edi`（堆地址）的来源地址是 `0130f7a0`。它并没有在第一次拷贝的范围内，但是这个地址就不能通过别的方法修改吗？

通过继续跟踪函数，我找到了这条指令：


当前的 `esp=0130f7a4`，`push` 也就是在给 `0130f7a0` 赋值。

跟到了这里，原来数据来源是 `0130f90c`。结合第一次拷贝的数据范围 `edi：0x0130f804~0x0130f958` 可以知道，这个地址就是拷贝进去的数据。（这里由于篇幅有限，只分析如何通过第一次拷贝的数据修改第二次将进行拷贝的 `edi` 的值，第二次的拷贝如何修改第三次 `edi` 的值，以此类推。）

好了，我们现在能知道，原作者通过第一次的溢出，使第二次的 `edi` 变成自构造的对象堆地址，进行了第二次堆溢出。那么第三次溢出的作用是什么？

第三次拷贝的数据范围 `edi：0x0130fab4~0x0130fc08`。

下面这条指令是给 `ecx`（`this` 指针）赋值的。此时的 `ebp-14h=0130fbbc` 在第三次的溢出范围内。而且结合第二次拷贝的数据范围 `edi：0x680312c0~0x68031464` 可以知道，现在赋值的 `ecx` 就是第二次拷贝的起始地址。

`ecx` 值来源：栈地址 `0130f960` 内容 -> 变成 `680312c0`。

```text
673f578f ff75ec          push    dword ptr [ebp-14h]
ss:0023:0130fbbc=680312c0
```
