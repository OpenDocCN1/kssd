
# [原创]迅雷在win10x64上的services进程注入

这几天分析了一下迅雷在win10x64的上开机启动阶段的services进程注入方法。

注入流程在驱动模块`XLGuard.sys`中，它会在System阶段启动，一开始，注入流程很正常:

(1)创建模块加载回调
(2)在进程名为`services.exe`并且模块名为`ntdll.dll`时构建一段shellcode
(3)在`ntdll!LdrLoadDll`处写入一个内联hook

![](https://bbs.kanxue.com/upload/attach/201903/825829_QXP5SGPKUJ8CE5N.jpg)

(4)内联hook会跳转到shellcode处执行，但这段shellcode的执行流程很简单，就只是调用了`LdrLoadDll`加载一下迅雷注入services进程的dll，其他什么都没有做。

那么问题就来了，win10x64上会对services进程加载的dll进行签名校验，直接调用`LdrLoadDll`一定会失败，那它的dll是如何躲过签名校验的？后来我发现这么一段代码:

![](https://bbs.kanxue.com/upload/attach/201903/825829_MPKAVVU2ZYPGV7C.jpg)

它利用了`EPROCESS`中`SectionSignatureLevel`可以控制是否对dll进行签名校验，将它修改为0就可以躲过签名校验。

然后更大的问题就来了，`PathGuard`是会检查`EPROCESS`中的值是否被修改的，迅雷这么做是会在一定概率上触发蓝屏的，那么它有没有将这个值恢复呢？

![](https://bbs.kanxue.com/upload/attach/201903/825829_7SCD8FRDPKANM73.jpg)

开机启动后使用`livekd`工具查了一下，它并没有将这个字段的值恢复。(其实即使恢复了，也不该这么做)

以上操作是我在win10x64的17134版本虚拟机上安装迅雷后发现的，我又看了一下真机上的迅雷，发现并没有加载`XLGuard.sys`驱动并且services进程也没有被注入dll，可能原因是以前我的电脑被`XLGuard.sys`搞过一次蓝屏，之后迅雷根据蓝屏反馈信息就不再加载该驱动了......

一般来说，win10x64上正确地对services进程注入dll的流程应该是这样:

(1)驱动中调用`ZwCreateSection`创建注入dll的Section句柄
(2)在shellcode中调用`LdrLoadDll`加载注入dll时直接使用驱动创建的Section句柄
(3)`LdrLoadDll`就可以加载成功

我不知道还有哪些方法，但360好像就是这么做的。

迅雷的用户量很大，这么做肯定是不稳定的，出现的蓝屏应该会很多，我不知道是不是自己遗漏了什么东西，但我看到的就是这样。

附件解压后是 迅雷安装包+`XLGuard.sys`+使用ida分析`XLGuard`的分析文件。
