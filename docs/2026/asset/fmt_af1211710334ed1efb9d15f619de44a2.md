
![](https://bbs.kanxue.com/upload/attach/202004/833057_A4DDQQE29AXFWKS.png)

`ecx`的值来自`[edx+esi]`，`edx`的值断下后为`0`，那么包地址就等于`esi`，继续追`esi`

![](https://bbs.kanxue.com/upload/attach/202004/833057_QNUCJ6HQA63QTM6.png)

`esi`来自`[ebx+4]`，而`ebx`来自`[edi+2888]`，那么包地址就等于`[[edi+2888]+4]`

![](https://bbs.kanxue.com/upload/attach/202004/833057_3NNNYD7GH26XG2Y.png)

在这个地方下个断点，可以发现`edi`的地址是不变的。这个时候就没有必要往上追了。

接着我们在`[[edi+2888]+4]`的地址下硬件写入断点，找到往这个地址写入数据的地方

![](https://bbs.kanxue.com/upload/attach/202004/833057_Y74864SU8DJUCNU.png)

断点断下以后，`eax=[edi+2888]`，是被写入数据的地址，包内容=`[eax+4]`

我们需要判断这个地方是在发包线程内还是线程外。

![](https://bbs.kanxue.com/upload/attach/202004/833057_XV69A3Z3845BJR6.png)

判断的方法是对比`WSASend`和找到地址的调用堆栈。

我们发现两个调用堆栈的地址是相同的，说明还没有跳出发包线程。需要继续追`eax`的来源然后下写入断点。

![](https://bbs.kanxue.com/upload/attach/202004/833057_EWXJVWUS7PFC2W6.png)

`eax`来自`[ebx+8]`，`ebx`来自`edx`，而`edx`的地址是不变的，包内容=`[[edx]+8]+4]`，直接在`edx`下写入断点

![](https://bbs.kanxue.com/upload/attach/202004/833057_XS6BGUE4MDCGJT7.png)

断到了第二次断下的位置

![](https://bbs.kanxue.com/upload/attach/202004/833057_ND28QUZAUWSUZ4W.png)

这个时候再查看调用堆栈，返回地址都是游戏主模块，明显这次我们跳出了线程发包函数

### 定位加密封包内容

接着我们需要在这个函数内找到加密的封包内容，之前的包内容偏移如下：

```
包内容=[[edx]+8]+4]
```

![](https://bbs.kanxue.com/upload/attach/202004/833057_WTGUZTTNHVTPZKU.png)

对比之前追的偏移表达式，这个地方就是将`ebp`写入到`[eax]`，`[eax]`其实就相当于包内容表达式的`[edx]`，所以

加密的封包内容就等于`[ebp+8]+4]`

那么怎么验证这个地方就是加密的封包内容呢？直接对比`WSASend`的`pBuffers`和`[ebp+8]+4]`的数据内容

![](https://bbs.kanxue.com/upload/attach/202004/833057_9PY6GVXCM7SN3MS.png)

这两个地方是一致的，那么说明`[ebp+8]+4]`就是加密的封包内容。接下来测试一下能不能通过跳出的发包线程找到游戏的喊话call。在第二次断下的位置下断点

![](https://bbs.kanxue.com/upload/attach/202004/833057_SHB6X8BGQQBE8M9.png)

然后在游戏内喊话，断下以后在堆栈中的返回地址，我们找到了当前的喊话内容，说明这个call就是喊话call

![](https://bbs.kanxue.com/upload/attach/202004/833057_V9USXX3QNSUXJE4.png)

#### 线程发包总结

1. 对于重写发包函数的问题，只需要在三个发包函数的底层函数下断或者搜索内层的特征码即可找到游戏重写的发包函数

2. 对于线程发包的问题，需要找到数据包的地址来源，然后对基地址下写入断点。重复这个过程，即可跳出线程发包函数。

### 定位封包加密call

#### 定位封包加密call

我们在加密封包处下断点，第一层返回地址找到了明文发包函数，那么封包的加密call肯定就在中间。

![](https://bbs.kanxue.com/upload/attach/202004/833057_YDNB8CHUMEYFVT5.png)

在明文发包函数下个断点，`F7`进入函数并单步跟踪，上面所有的跳转都执行了，上面`4`个call没有执行的机会

![](https://bbs.kanxue.com/upload/attach/202004/833057_G6RZGWDX3JNRE6Y.png)

然后在单步不过这个call的时候，喊话的内容被加密了。这个有可能就是加密call。

![](https://bbs.kanxue.com/upload/attach/202004/833057_Q2SPE2X49NY66V5.png)

为了进一步确认，将断点断到加密封包内容处，查看`[[ebp+8]+4]`地址处的值，和之前的内容一致，说明这个call就是我们要的封包加密call

#### 封包加密call参数分析

![](https://bbs.kanxue.com/upload/attach/202004/833057_FPAHSXNT52VKTQ4.png)

首先来看`eax`，`eax`地址指向的值每次都是变化的，对于加密函数来说，为了让密文每次都变得不一样，一个有效的方法就是让秘钥变的随机。这个`eax`加密call的秘钥

`eax`往上追可以追出一个偏移表达式，这里省略追秘钥的过程，直接给出表达式

```
[[[00f84ba4]+4]+0xC+8]+54
```

![](https://bbs.kanxue.com/upload/attach/202004/833057_FYX83BU2J7DJVTY.png)

`edi`是一个数值，可能是包长

![](https://bbs.kanxue.com/upload/attach/202004/833057_SJQBREK3YS8JUET.png)

我们在`WSASend`函数下断，查看一下，和上面的`edi`是一样的。那么`edi`就是包长-`2`。

封包分为两部分：前两个字节是包的头部，头部往后才是封包数据。

这个参数的含义其实就是要加密的内容长度，-`2`是因为要减掉封包头部的长度。

![](https://bbs.kanxue.com/upload/attach/202004/833057_64PTYFWTHKRT695.png)

`ebp`和`ebx`可以用同样的方法论证得出是包地址+`2`。也就是要加密的数据地址，+`2`是为了不加密封包头。

到此，封包加密call的参数就分析完成了
