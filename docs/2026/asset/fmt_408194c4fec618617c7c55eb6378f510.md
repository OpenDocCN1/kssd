## 外挂运行逻辑

外挂进程先通过 Java 层解密出 `sock001` 并运行，将数据读取到`/sdcard/1A.txt`文件中。然后外挂进程的 Native 层不断读取`/sdcard/1A.txt`文件中的数据，同时调用 Java 层的绘图函数，实现透视。

## Java 层分析

在查看外挂 APK 提供的 `so` 文件时，发现里面并没有远程读写的代码，怀疑是新启动了一个进程。在 `assert` 文件夹下发现了几个以 `sock` 开头的可疑文件。

![image-20220424171236773](upload/attach/202204/862028\_MJHYFA7HPWY7QQ9.png)

用 010 打开后，发现所有文件都经过加密，无法直接判断其内容。

![image-20220424171313317](upload/attach/202204/862028\_C3975V7M94UNBCY.png)

开始在 Java 层寻找解密位置。由于 Java 层混淆得非常严重，最终在 `MainActivity` 中找到了对应的解密逻辑。

![image-20220424171504527](upload/attach/202204/862028\_WJBP7U7YKRRVFME.png)

这里是对 `sock1` 进行解密。跟进后可以看到，这是非常明显的 RC4 加密，密钥为 `gamesec`。

![image-20220424171543856](upload/attach/202204/862028\_DA8ZSNWMF3RMT8U.png)

本地使用 Python 对 `sock1` 进行解密：

```python
# coding=utf-8
DEFAULT_KEY = ""

def rc4(data, key=DEFAULT_KEY, skip=1024):
    x = 0
    box = range(256)
    x = 0
    for i in range(256):
        x = (x + box[i] + ord(key[i % len(key)])) % 256
        tmp = box[i]
        tmp2 = box[x]
        box[i] = box[x]
        box[x] = tmp
        x = 0
        y = 0
        out = []
        if skip > 0:
            for i in range(skip):
                x = (x + 1) % 256
                y = (y + box[x]) % 256
                box[x], box[y] = box[y], box[x]
        for char in data:
            x = (x + 1) % 256
            y = (y + box[x]) % 256
            box[x], box[y] = box[y], box[x]
            k = box[(box[x] + box[y]) % 256]
            out.append(chr(ord(char) ^ k))
        return out

if __name__ == '__main__':
    # handle input file or stream
    import sys

    tt = open("sock1", "rb")
    ww = tt.read()
    decrypt_files = rc4(ww, "gamesec", 0)
    decttt = open("sock1dec", "wb")
    decttt.write("".join(decrypt_files))
```

解密后，再用 010 打开，发现这是一个 Android 上的 ELF 可执行文件。

![image-20220424171724232](upload/attach/202204/862028\_X3VGJ65H6MMZ46B.png)

同时，Java 层通过 Shell 命令启动了进程，可以使用`ps -ef`查看启动进程的参数。

![image-20220424171827520](upload/attach/202204/862028\_5B7349S3TZW79PP.png)

发现参数是 `2236 1080`，这两个数字是测试手机屏幕的高和宽，后面会用到。

# 脱变种 UPX 的壳

这里通过 010 Editor 发现，UPX 字符串都被改成了 `ue4`。使用`upx -d`时无法直接识别为 UPX，应该是本地被 `patch` 修改过了，因此尝试进行修复。

将所有出现的 `ue4!` 字符串改成 `upx!`，这是最基本的特征。

# 类似 Shellcode 部分

![image-20220424204515256](upload/attach/202204/862028\_UD5PMX34CSP9BE8.png)

![image-20220424204935908](upload/attach/202204/862028\_YGAF7VUDF7WN45E.png)

在调试过程中，发现 `sock1` 使用密钥 `TencentGameSecurity`，通过 RC4 算法对 `sock002`、`sock003`、`sock004`、`sock005` 进行了加密解密。同时发现 `sock001` 文件中间存在空缺。

![image-20220425100132263](upload/attach/202204/862028\_S2DVQ64JNF9ZPY5.png)

空缺的位置似乎就是那几个文件。于是本地重新分析一个 Android 可执行 ELF 文件，并进行对照分析，得出结论：`sock002` 解密后对应的是 `program table`，并在调试中确认了这一点。

![image-20220425104318674](upload/attach/202204/862028\_3VEHEG28T332P4W.png)

解析 `sock002`（`program table`），然后将 `sock001` 中需要加载的代码加载进内存。下一步是通过解密后的 `sock005` 进行重定位，解密后的 `sock005` 是 `.rel.plt` section。

![image-20220425112112605](upload/attach/202204/862028\_Z4MMJ5MVXMAXUZG.png)

`sock003` 解密后，本地查看发现很明显是动态链接的字符串表。

![image-20220425105240838](upload/attach/202204/862028\_F3QAECESTBNG8PV.png)

经过对比，发现 `sock004dec` 是动态符号表。几个文件的代表意义都已经明确，继续分析后，相当于自行实现了一个 `linker`。

继续调试时发现，`pc` 值跳到了 `sock001`、`sock002`、`sock003`、`sock004`、`sock005` 加载到内存中的区间，说明 `sock1` 进程相当于执行了一段由这几个文件组成的 Shellcode，最终进入了这个外挂的关键函数。

![image-20220424205744937](upload/attach/202204/862028\_J4X3Y7V87B8ZF68.png)

这里为了证实这个函数属于那几个文件，使用 010 搜索机器码的十六进制。
