### `EXCEPTION_BREAKPOINT`异常消息的产生

在OD直接在地址为`0x01012477`下一条指令双击下断点,同样windbg下断`nt!DbgkpQueueMessage`,OD执行到有断点的指令

断下后发现堆栈:

`ChildEBP RetAddr`

`f6086884 809911a3 nt!DbgkpQueueMessage [f:\wrk\wrk\wrk\base\ntos\dbgk\dbgkobj.c @ 624]`

`f60868a8 809912d4 nt!DbgkpSendApiMessage+0x43 [f:\wrk\wrk\wrk\base\ntos\dbgk\dbgkport.c @ 79]`

`f6086934 8082adcc nt!DbgkForwardException+0x8e [f:\wrk\wrk\wrk\base\ntos\dbgk\dbgkport.c @ 257]`

`f6086cf4 808833a2 nt!KiDispatchException+0x1ea [f:\wrk\wrk\wrk\base\ntos\ke\i386\exceptn.c @ 1269]`

`f6086d5c 80883b3c nt!CommonDispatchException+0x4a [F:\WRK\WRK\WRK\base\ntos\ke\i386\trap.asm @ 2087]`

`f6086d5c 01012478 nt!_KiTrap03+0xb0 [F:\WRK\WRK\WRK\base\ntos\ke\i386\trap.asm @ 3062]`

观察堆栈发现`nt!_KiTrap03+0xb0`返回地址为`01012478`,说明在地址为`0x01012478`产生的异常,当中断发生时 系统会自动把当前线程上下文的信息存入`trapframe`,所以对于断点异常来说异常地址都是来自断点指令的下一条指令地址,也就是线程上下文`CONTEXT`里`eip`的值

```asm
80883b23 8bf1            mov     esi,ecx

80883b25 8bfa            mov     edi,edx

80883b27 8bd0            mov     edx,eax

80883b29 8b5d68          mov     ebx,dword ptr [ebp+68h] ;trapframe.eip

80883b2c 4b              dec     ebx ;异常地址减1

80883b2d b903000000      mov     ecx,3 ;异常参数

80883b32 b803000080      mov     eax,80000003h ; EXCEPTION_BREAKPOINT

80883b37 e81cf8ffff      call    nt!CommonDispatchException (80883358)
```

系统对`int3`单字节断点做了特殊处理,不同于普通的断点形式`int n`的机器码`0xcdn`,大部分编译器对`int3`都会生成`0xcc`,中断后`trapframe`里保存的异常地址是产生异常指令的下一条指令地址,取出`trapframe.eip`,减1后保存到`ebx`,`ebx`作为参数传入`CommonDispatchException`函数里,`CommonDispatchException`用把`ebx`值存入`EXCEPTION_RECORD`的异常地址字段,这样调试器处理异常调试事件时`EXCEPTION_RECORD`的产生异常地址是正确的异常指令地址,但是当`int3`机器码为`cd03`时,因为机器码为2字节,所以`EXCEPTION_RECORD`的产生异常地址不是机器码为`cd`的地址而是机器码为`03`的地址. 产生异常时线程的上下文`CONTEXT`中的`eip`不是断点地址+1,而是断点地址+2

这里我使用`windbg`看如何对`cd03`双字节断点的处理,猜测应该是`windbg`的`bug`

`Windbg`对待`int3`断点都是采取处理的方式(第一次断点异常就处理了) , 也就是返回`DEBUG_CONTINUE`,OD则不同,OD发现不是自己设置的断点,则不会处理,也就是OD会交给用户负责,微软的`MSDN`文档描述调试器接受到断点的处理方法:

`// First chance: Update the display of the`

`// current instruction and register values.`

并没有说有第二次异常应该如何处理,但是`int3`异常如果第一次不处理,确实会发送第二次异常的

如果用`VC`使用伪指令写入 生成这样的代码

```
  …
(1)__asm _emit 0xcd
(2)__asm _emit 0x03
  …
  …
```

`windbg`会第一次就返回已处理,但是`CONTEXT.eip`会指向`(2)_emit 0xcd`导致`(2)`与后面代码混淆在一起.按道理如果不处理`CONTEXT.eip`,仅仅返回`DEBUG_CONTINUE`,单字节异常和双字节异常都会得到正确的解决,上面已经说到产生断点异常时线程上下文`CONTEXT.eip`都会指向正确的下一条指令地址. 导致这个`bug`的代码我打包了进来,一个简单的`seh`处理自己的产生的`int3`异常例子.双击可以正确运行,`windbg`执行则会出现上面所叙述的情况
