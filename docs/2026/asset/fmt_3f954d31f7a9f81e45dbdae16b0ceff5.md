
# [原创]分析实战读书笔记12_常见反调试

## 0. 前言

在分析恶意代码的过程中，免不了需要动态分析，所以掌握常见反调试技术是必要的，否则就要出师未捷身先死了。

## 1. 检测调试器

### 1.1 利用winAPI

- `IsDebuggerPresent`：该 API 查询 `PEB` 结构中的 `IsDebugger` 标志位，未调试返回 `0`，调试状态返回 `1`。

- `CheckRemoteDebuggerPresent`：与 `IsDebuggerPresent` 原理一致，此 API 可以检测其他进程的调试状态，只需传入进程句柄。通过传入自身进程句柄可检测自身调试状态，未调试返回 `0`，调试状态返回 `1`。

- `NtQueryInformationProcess`：该 API 用于提取一个进程的状态信息，第一个参数为进程句柄，第二个参数为信息类型，当传入类型为 `0x7`（`ProcessDebugPort`）时会获取调试端口。未调试返回 `0`，调试状态返回调试端口号。

- `OutputDebugString`：此 API 用于输出一个字符串。当未处于调试状态时调用该 API 会设置错误码，处于调试状态时会正常输出。通过对比手动设置的错误码可以检测是否处于调试状态。报错未调试，未报错则处于调试状态。

### 1.2 手动检测

在 `PEB` 结构中存储很多信息可以用来检测调试器。

- `BeingDebugged` 属性：`PEB` 结构偏移为 `2` 的位置为 `BeingDebugged` 属性，宽度 `1` 字节，未调试为 `0`，调试状态为 `1`。

  ```text
  [fs:[0x30]+2] -> byte
  ```

- `ProcessHeap` 属性：`ProcessHeap` 是 `PEB` 结构中 `Reserved4` 数组中一个未公开的属性，偏移为 `0x18`，第一个堆头部有一个属性指明了是否为调试器创建（`ForceFlags` / `Flags`）。

  ```text
  XP:   Flags位于堆头部偏移0x10处  [[fs:[0x30]+0x18]+0x10] -> dword
  WIN7: Flags位于堆头部偏移0x44处  [[fs:[0x30]+0x18]+0x44] -> dword
  ```

  0 为未调试，不为 `0` 处于调试状态。

- `NTGlobalFlag` 属性：`NTGlobalFlag` 是 `PEB` 结构中另一个未公开位置，偏移 `0x68`，这个值指明了如何创建堆结构。如果此处值为 `0x70` 则处于调试状态。

  `0x70` 含义：`FLG_HEAP_ENABLE_TAIL_CHECK | FLG_HEAP_ENABLE_FREE_CHECK | FLG_HEAP_VALIDATE_PARAMETERS`

  ```text
  [fs:[30]+0x68] -> dword == 0x70?调试:非调试
  ```

### 1.3 系统痕迹

- 注册表：`HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\AeDebug`

  该注册表项指定当应用程序发生错误时，触发哪一个调试器。默认情况下它被设置为 `Dr.Watson`，若是变成了 `OllyDbg`，则恶意程序可以确定它处于被调试的状态。

- 文件遍历：恶意代码还可能通过遍历磁盘文件寻找调试器文件名。

- 进程遍历：通过遍历进程寻找是否有黑名单中的进程来监测调试器，如 `od`、`ida`、`x32dbg` 之类的进程名。

- 窗口遍历：通过 `FindWindow` 可以遍历窗口，寻找是否有疑似调试器的程序在运行。

### 1.4 行为扫描

- 断点扫描：调试器断点常使用 `int3` 指令（`0xCC`）触发 3 号中断，因此在下断时会临时修改指令字节。程序可以通过开启线程循环扫描自身代码段数据，查找是否存在 `0xCC` 字节数据。

- CRC 校验：原理同断点扫描类似，程序首先计算自身代码段的 `CRC` 校验值，当运行时开启新线程循环计算自身进程代码段的 `CRC` 校验值并与预先定义好的值进行比较，若不同则说明代码段某一处或多处字节被修改，这时程序可以停止执行，转而执行伪装代码。

- 时钟检测：在调试时程序执行速度会大幅降低，通过比对两处代码的执行间隔可以推断出是否处于调试状态。

  所需指令：`rdtsc`（从开机到此刻的时钟数，存到 `EDX:EAX` 中）

  所需 API：`QueryPerformanceCounter` 与 `GetTickCount`

## 2. 干扰调试器

### 2.1 TLS回调

`TLS` 回调会在程序执行 `OEP` 之前执行，因此若一个样本使用 `TLS` 回调，在 `OD` 分析断在 `OEP` 处时，实际上 `TLS` 回调函数已经执行完毕。

一个样本具备 `TLS` 回调的特征是区段中包含一个 `.tls` 节。正常程序很少使用该技术，因此当样本中出现 `.tls` 区段则很可能具备反调试手段。

若想分析 `TLS` 函数，在 `OD` 中将调试选项中的入口断点改为系统断点即可。

![image-20210304150851982](upload/attach/202103/867232_WG28FJXXAVDB458.jpg)

在 `IDA` 中按下 `Ctrl+E` 可以查看所有入口函数，若包含 `TLS` 回调，则会显示：

![image-20210304151100368](upload/attach/202103/867232_27CVSGXS2XS468W.jpg)

### 2.2 使用异常

![image-20210304152024216](upload/attach/202103/867232_NEW94UVS9R9VKN2.jpg)

使用 `OD` 的“忽略异常”可以让调试器不接收异常，从而将异常处理权限还给进程自身。

![image-20210304152127188](upload/attach/202103/867232_64CQGKKMD2RS5D6.jpg)

### 2.3 插入中断

由于调试器使用 `int3`（`0xCC`）或 `int 3`（`0xCD 03`）指令产生异常，从而接管异常处理来达到“断下来”的效果。因此若在程序中人为地添加中断指令，就会被调试器认为是自己下的断点从而接管程序的执行。（现在的调试器都具备了区分断点归属性的能力，很少被这种技术欺骗）

而这种技术在一些调试器上会恰巧更改程序的执行流程，如下图：

![image-20210304153101066](upload/attach/202103/867232_5CX75HG79F3SRRV.jpg)

这段代码在面对 `WinDbg` 调试器时，会展现它的反调试功能。当程序执行到 `int 3` 指令时，会触发 3 号中断，从而被 `WinDbg` 捕获。捕获后，`WinDbg` 会将中断指令的地址 + 1 存入 `EIP`，这就导致了原本利用 `SEH` 技术将要执行的 `continue` 代码被 `WinDbg` 强行更改为 `int 3` 后面的指令，从而错过了真正的代码流。

#### 2.3.1 ICE断点

指令 `icebp`（`0xF1`）会产生一个单步异常，调试器会误认为是自身单步导致的异常，从而接管异常处理。这时如果恶意作者使用 `icebp` + `SEH` 技术的话，调试器就会由于接管了异常处理而越过恶意代码作者的 `SEH` 函数。因此当代码中出现 `icebp`，不要使用单步执行走过去，而是要在 `SEH` 处理函数下断进行监测。

## 3. 调试器漏洞

### 3.1 PE漏洞

该漏洞是由于调试器在读取 `PE` 数据时过于规则化，从而导致当恶意代码作者在不损坏文件的前提下修改 `PE` 头数据时，会被调试器视为一个损坏的 `PE` 文件从而无法加载。对于这种情况，我们只需观察 `PE` 数据对其进行手动修正即可。

### 3.2 `OutputDebugString`漏洞

此漏洞在目前版本的调试器已不存在，只针对 `OD 1.0` 版本。漏洞内容如下：

```text
OutputDebugString参数为“%s%s%s%s%s%s%s%s%s%s%s”会使调试器崩溃。
```

## 4. 小结

通过本章的知识，可以发现反调试没有一个固定的规则，任何能对分析师或调试器造成欺骗的技术都可以作为反调试。小到一个 `API` 大到一个调试器的漏洞都可以被用来检测调试器，因此需要分析师与时俱进。

另外大多数反调试行为会涉及 `PEB` 结构（`fs:[30]`），因此需要对这种指令十分敏感。
