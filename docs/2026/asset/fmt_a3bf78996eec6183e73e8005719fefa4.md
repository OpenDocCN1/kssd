
还需要修改拦截`MinorFunction`为`IRP_MN_QUERY_DEVICE_TEXT`的请求，请求交给下层成功完成后，修改返回的信息

# 开始重定向：

驱动还需要在`DriverEntry`中创建一个控制设备，跟用户层交互完成如下功能：

1. 用户层跟驱动交互，获取全局链表中的USB设备信息（不包括hub），获取的设备信息包括`deviceid`和`instanceid`，用于唯一标识一个设备用来重定向，还能返回一个设备是否处于重定向状态。
2. 用户层跟驱动交互，发送需要重定向的usb设备对应的`deviceid`和`instanceid`，驱动给用户层返回一个重定向后的usb设备打开的句柄，用户层可以使用这个句柄跟usb设备进行通信，还需要调用`iocontrol`对这个句柄做一个特殊标记，在`fileobject`的`fscontext`变量处，做了标记后当句柄被关闭或者进程退出时可以自动取消重定向。
3. 用户层跟驱动交互，修改驱动的`AddDevice`回调函数置空（用于停止驱动前），由于驱动的`AddDevice`回调指针不为空，因此使用传统的`sc stop`命令停止驱动服务会报错，提示"请求的控件对此服务无效"，因此在停止服务之前，先将驱动对象的`AddDevice`回调函数指针置空。

上面第一步和第三步都没有什么难度，第二步是重点，重定向某一个usb设备，

当驱动收到需要重定向的usb设备的`deviceid`和`instanceid`时，那么从全局链表中找到是否存在对应的usb设备，找到对应的`pdo`

```PUSB_STUB_DEVICE_ID usb = (PUSB_STUB_DEVICE_ID)irp->AssociatedIrp.SystemBuffer;

status = STATUS_INVALID_PARAMETER;

do

{

	if (NULL == usb)

	{

		break;

	}

	KEVENT attach_event;

	KeInitializeEvent(&attach_event, NotificationEvent, FALSE);

	status = AddRedirect(usb->DeviceID, usb->InstanceID, &attach_event);//1

	if (!NT_SUCCESS(status))

	{

		break;

	}

	ULONG symbolic_id = 0;

	ULONG64 handle_usb = 0;

	BOOLEAN need_rollback = FALSE;

	status = ResetUsbDevice(usb->DeviceID, usb->InstanceID, TRUE);//2

	if (NT_SUCCESS(status))

	{

		LARGE_INTEGER timeout;

		timeout.QuadPart = -10 * 1000 * 1000 * 10;  // 10s = 10,000,000 * 100ns

		status = KeWaitForSingleObject(&attach_event, Executive, KernelMode, FALSE, &timeout);//3

		switch (status) {

		case STATUS_SUCCESS:

		{	

			status = OpenRedirectUsbSymbolicId(usb->DeviceID, usb->InstanceID, &symbolic_id, &handle_usb);//4

			break;

		}

		case STATUS_TIMEOUT:

			//DbgPrint("Wait timed out after 10 seconds\n");

			break;

		default:

			break;

		}

		if (!NT_SUCCESS(status))

		{

			need_rollback = TRUE;//5

		}

	}

	RemoveRedirect(usb->DeviceID, usb->InstanceID);//6

	if (need_rollback)

	{

		ResetUsbDevice(usb->DeviceID, usb->InstanceID, TRUE);//7

	}

	else if (0 != symbolic_id)

	{

		irp->IoStatus.Information = sizeof(USB_REDIRECT_RET);

		PUSB_REDIRECT_RET out = (PUSB_REDIRECT_RET)irp->AssociatedIrp.SystemBuffer;

		out->symbolic_id = symbolic_id;

		out->handle_usb = handle_usb;

	}

} while (0);
```

1处的`AddRedirect`函数中会判断全局链表中是否存在对应的`deviceid`和`instanceid`，如果存在，那么会将id信息以及传入的`event`指针 保存到"全局的待重定向的链表"中，如果返回值成功，那么代表能找到对应的设备以及插入成功。

2处的代码`ResetUsbDevice`函数会调用`IoBuildDeviceIoControlRequest`构造一个`IOCTL_INTERNAL_USB_CYCLE_PORT`的`irp`，传入参数为设备对应的`pdo`，操作系统会模拟与 PDO 关联的端口上的设备拔出和重新插入，会触发到我们之前写的Hub的`BusRelations`函数，会触发到2次，第一次触发到的时候判断"丢弃已经移除的usb设备"，会丢弃释放存放于全局链表中的对应的usb设备数据结构，第二次触发到的时候判断"添加新插入的usb设备"，在这个过程中判断此设备是否存在于"全局的待重定向的链表中"(`deviceid`和`instanceid`来比较)，很明显是存在的，此时需要修改"全局的待重定向的链表"中此项设备的父`parent`对象，记录下来此设备对应的父 hub的对象，后续使用。 接着主动调用`AddDevice`回调函数，由于此设备需要重定向，那么在函数`AddDevice`中进行`Attach`，`Attach`这个`Usb`设备之后我们就可以拦截到设备的`irp`请求，在`MajorFunction`为`IRP_MJ_PNP`请求，且`MinorFunction`为`IRP_MN_START_DEVICE`时，先将这个请求下发下去，待请求完成时，在完成函数中查询"全局的待重定向的链表"，找到此设备后，由于1处的代码传入了一个事件`event`的指针，此时我们调用`KeSetEvent`触发这个`event`。

3处的代码是等待`attach_event`，在2处的步骤中最后我们会唤醒这个`event`，所以3处可以等到这个事件。

4处的代码调用`OpenRedirectUsbSymbolicId`函数，先调用`FindRedirectUsbSymbolicId`根据`deviceid`和`instanceid`遍历全局设备链表，找到设备的`symbolicid`，接着根据`symbolicid`组装设备`name`，调用`ZwOpenFile`打开该设备，为了防止打开设备时设备还未在系统层面准备就绪，因此使用了掩饰多次尝试的机制，打开设备成功后，调用`ZwDeviceIoControlFile`发送`IOCTL_USBIP_STUB_EXPORT`请求，本驱动处理该请求为这个`fileobject`的`fscontext`域设置特殊值，后续关闭此句柄时自动取消重定向（用户层主动调用关闭句柄或者由于程序崩溃释放资源关闭句柄），本地可以使用该设备了。

```NTSTATUS OpenRedirectUsbSymbolicId(PWCHAR device_id, PWCHAR instance_id, ULONG* symbolic_id, ULONG64* handle_usb)

{

	if (NULL == symbolic_id || NULL == handle_usb)

	{

		return STATUS_INVALID_PARAMETER;

	}

	

	NTSTATUS status = STATUS_NO_SUCH_DEVICE;	

	ULONG id = FindRedirectUsbSymbolicId(device_id, instance_id);//

	HANDLE open_handle = NULL;

	if (0 != id)

	{

		IO_STATUS_BLOCK IoStatusBlock;

		WCHAR stub_device[NAMEBUF_LEN] = { 0 };

		RtlStringCchPrintfW(stub_device, ARRAYSIZE(stub_device), L"\\Device\\usbip_stub_%04d", id);

		UNICODE_STRING name = {0};

		RtlInitUnicodeString(&name, stub_device);

		OBJECT_ATTRIBUTES ObjectAttributes;

		InitializeObjectAttributes(&ObjectAttributes, &name, 0, NULL, NULL);



		static const LONGLONG RETRY_TIMEOUT_MS = 20;

		ULONG64 iterationsLeft = 10000 / RETRY_TIMEOUT_MS; //Max timeout is 10 seconds



		

		LARGE_INTEGER interval;

		interval.QuadPart = -MillisecondsTo100Nanoseconds(RETRY_TIMEOUT_MS);



		do

		{			

			status = ZwOpenFile(&open_handle,

				GENERIC_READ | GENERIC_WRITE,

				&ObjectAttributes, &IoStatusBlock, 0,

				FILE_NON_DIRECTORY_FILE | FILE_RANDOM_ACCESS);

			if (NT_SUCCESS(status))

			{

				status = ZwDeviceIoControlFile(open_handle, NULL, NULL, NULL, &IoStatusBlock, IOCTL_USBIP_STUB_EXPORT, NULL, 0, NULL, 0);

				if (NT_SUCCESS(status))

				{					

					break;

				}

				ZwClose(open_handle);

				open_handle = NULL;

			}



			KeDelayExecutionThread(KernelMode, FALSE, &interval);

		} while (iterationsLeft-- > 0);

	}

	if (NT_SUCCESS(status))

	{

		*symbolic_id = id;

		*handle_usb = (ULONG64)open_handle;

	}	

	

	return status;

}
```

5处的代码判断如果等待`event`没有成功，那么代表重定向失败，设置`need_rollback`变量为`TRUE`。

6处的代码从"待重定向的链表中"移除这个`deviceid`和`instanceid`对应的这项。

7处的代码判断`need_rollback`如果为`TRUE`，那么重新调用`ResetUsbDevice`函数再次模拟设备的拔出和插入动作，由于6处已经在"待重定向链表"中移除了当前这个项，所以再次模拟这个请求时不会`attach`这个`usb`设备，`usb`设备在本机使用，这个是为了容错处理，重定向失败时恢复此`usb`设备。

发送重定向请求后，用户层使用传回的`handle`句柄即可与驱动程序通信，剩下的按照`usbipstub`原来的应用层逻辑使用即可。

# 取消重定向：

开始重定向时会传出一个`handle`句柄，取消重定向，只需要`CloseHandle`关闭此句柄即可。

在驱动中判断`MajorFunction`为`IRP_MJ_CLEANUP`时，如果`fileobject`的`fscontext`不为空，那么认为是重定向的`usb`设备句柄，关闭句柄时需要取消重定向，此时先将请求下发，之后调用`ResetUsbDevice`模拟`usb`设备拔出插入请求，`usb`设备即可恢复供本机使用，还需要处理`IRP_MN_SURPRISE_REMOVAL`请求(在收到此请求时 代表`usb`设备意外移除，此时需要检查设备是否有未完成的`irp`，并完成这些`irp`)，对这个设备做特殊标记，不再接收`read`、`write`请求了，还有在`hub`的`busrelations`请求中，移除不存在的设备时也需要完成`irp`，这样后续`usb`设备的`IRP_MN_REMOVE_DEVICE`才会被触发，此时需要`detach`设备，并删除设备，关闭之前创建的`USBD`句柄，释放资源。

# 卸载驱动：

卸载驱动时，先修改注册表，取消之前`UpperFilters`中设置的`usbip_stub`的值，然后对系统上的`hub`设备执行软插拔（或者重启系统），接着发送`iocontrol`请求，将驱动的`AddDevice`回调设置为`NULL`指针，然后即可停止服务，删除服务了。
