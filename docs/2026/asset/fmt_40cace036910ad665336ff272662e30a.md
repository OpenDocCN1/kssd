#### traceWrite

那直接分析代码我们分析不了，那我们就只剩下`trace`了，这次我们不直接`trace code`，而是`trace write`！

为什么不选择直接`trace code`然后通过结果来写呢！因为这是一个混淆过的代码，`trace`的`log`会是非常大的！所以我们要化简！

![](upload/attach/202312/93_AK6CVFDN9YMJ6DA.png)

上面就是通过`trace`的`log`了有十多万行！移植起来会是非常棘手的！所以我们选择了`trace write`！这时候就会有一些大佬说为啥不用`trace read`呢？嘿嘿，我们要以结果为导向！所以选择的是`trace write`的`out`！

既然我们要选择`trace write`，那么我们就选择`address`跟`size`了

这时候我们回到`sub_783a`

![](upload/attach/202312/93_R93R3DJ8CG6QEVE.png)

发现`malloc`这里分配了一个`length + 118`大小的内存了，这样子我们就直到`size`是`length + 118`了，那么我们就剩下`addres`了

![](upload/attach/202312/93_EF2YX2PSSSY99AU.png)

通过测试发现，`0x7AA8`执行后他的地址是固定的！那么我们就可以确定`address`为`0x40358000`，而且还是一个固定值！（如果不是固定值咋办呢？嘿嘿，其实加多一个`backend.hook_add_new`来获取实际的即可！）（`time`、`rand`、`srand`这些其实都可以固定的，有兴趣可以翻一下源码或者写`hook`进行固定）

那么就可以愉快的写`trace write`啦！！！

```java
// 0x10为传进来的byte[]大小，这个是已知的
emulator.traceWrite(0x40358000, 0x40358000 + 0x10 + 118);
```
