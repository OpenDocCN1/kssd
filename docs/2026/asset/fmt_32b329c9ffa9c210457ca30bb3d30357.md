
# [原创]Windows condrv.sys 本地拒绝服务漏洞分析

今天这个蓝屏比较火，故做了下分析。

## 直接原因分析

漏洞堆栈如下：

![](https://bbs.kanxue.com/upload/attach/202101/324496_R6DRMXJ9CWBRD39.png)

从堆栈可以看到，当用户态打开路径 `\\.\globalroot\device\condrv\kernelconnect` 时，内核对象管理器会依次解析对象目录，直到解析到 `\device\condrv`，发现这是个设备对象，而设备对象的设备类型是有 `ParseProcedure` 例程的，故调用设备的对象的 `ParseProcedure` 即函数 `IopParseDevice`。函数内部在处理完请求后会去关闭打开的文件对象。

![](https://bbs.kanxue.com/upload/attach/202101/324496_M8BAEGKRJA834HY.png)

关闭文件对象时，内核会调用相应的驱动的 IRP 例程：`IRP_MJ_CLEANUP` 以及 `IRP_MJ_CLOSE`。

即 `condrv` 驱动的函数：`CdpDispatchCleanup`、`CdpDispatchClose`。

而 `CdpDispatchCleanup` 在处理 `IRP_MJ_CLEANUP` 时会尝试引用文件对象 `FILE_OBJECT` 的 `FsContext` 成员，此成员应该为驱动 `condrv` 自己创建的一个透明数据结构。但事实上这个成员是未预期的值 `NULL`，所以导致空指针引用蓝屏。如下图：

![](https://bbs.kanxue.com/upload/attach/202101/324496_RBZS4F9JVRWKPGN.png)

![](https://bbs.kanxue.com/upload/attach/202101/324496_4MYZSY5T5DT5ZWT.png)

## 根因分析

我们可以假设这个文件对象是“非法”的，那么可能从它创建初始化的时候就出现问题。对内核有了解的应该知道，如果要引用设备对象那么必然要有打开操作，即肯定要向 `condrv` 驱动发送 IRP：`IRP_MJ_CREATE`。那么我看下 `condrv` 驱动的 `Create` 例程：

![](https://bbs.kanxue.com/upload/attach/202101/324496_X2GFQ55CV9A853S.png)

如上图所示，它其实是在循环比较要打开的文件名是不是预先定义的，如果是则调用相应的回调函数，如下图：

![](https://bbs.kanxue.com/upload/attach/202101/324496_HCVKXWTSQDTH5VC.png)

由于 Poc 打开的是 `kernelconnect`，所以我们看下函数 `CdCreateKernelConnection`：

![](https://bbs.kanxue.com/upload/attach/202101/324496_EA3CJPG566EV4YC.png)

第一个判断就是如果先前模式是 `usermode` 则返回拒绝，也就是 `condrv` 驱动的设计初衷就是不允许用户态直接访问这个符号链接。

但是问题就出在此处返回拒绝上。因为这是在处理 IRP，它没有设置 IRP 的状态码以及调用 `IoCompleteRequest` 来结束 IRP。

![](https://bbs.kanxue.com/upload/attach/202101/324496_MS3Q5K62XB5R8YB.png)

如上图可以看到 `Irp->IoStatus.Status` 为 0，而 0 表示成功。

而在 `IopPraseDevice` 中是以 IRP 的 `IoStatus.Status` 成员来判断 `IoCallDriver` 是否成功。也就是本意是拒绝用户态打开这个符号链接，但实际因为开发疏忽导致内核认为打开成功。此时文件对象的 `FsContext` 成员没有被 `condrv` 赋值，所以当关闭文件对象时，导致蓝屏。实际测试修改 IRP 的 `IoStatus.Status` 的值为失败时，不会蓝屏。

## 总结

其实归根到底就是 `condrv` 的驱动开发人员在处理 `IRP_MJ_CREATE` 时，没有正确处理拒绝情况，导致本应该失败的内核误以为是成功，进而在后续对文件对象的操作时蓝屏。
