
# [翻译] Android 图像驱动的故事：ARM vs. Qualcomm

![](https://bbs.kanxue.com/upload/attach/201901/93_2MMSNXUXM96G2UR.jpg)

Hugues Evrard、Paul Thomson 和我最近成立了一家专业的自动化图形驱动测试公司——[GraphicsFuzz](https://bbs.kanxue.com/elink@e04K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2Y4M7X3q4H3K9r3W2U0M7$3k6#2P5Y4A6Q4x3X3g2U0L8$3#2Q4x3V1j5`.)。该公司是我们去年在伦敦帝国学院（Imperial College London）取得的一系列研究成果的产物。

![](https://bbs.kanxue.com/upload/attach/201803/747320_S5TCH8H53CAVW5T.jpg)

我们最初的产品是 [ShaderTest GLES](https://bbs.kanxue.com/elink@f1eK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2Y4M7X3q4H3K9r3W2U0M7$3k6#2P5Y4A6Q4x3X3g2U0L8$3#2Q4x3V1k6A6L8X3c8W2P5q4)9J5k6h3S2@1L8h3I4Q4x3U0y4H3M7X3!0V1N6h3y4@1M7H3`.`.)，一套 GPU 开发者可以用于测试 OpenGL ES 驱动器可靠性的片段着色器。

本文是我们通过运行具有代表性的样本着色器，探究 Android OpenGL ES 驱动可靠性系列文章的第一部分。

您还可以通过 [GraphicsFuzz Android 基准测试](https://bbs.kanxue.com/elink@9ffK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2Y4M7X3q4H3K9r3W2U0M7$3k6#2P5Y4A6Q4x3X3g2U0L8$3#2Q4x3V1k6T1k6h3&6U0K9r3#2S2M7X3E0Q4x3V1k6S2L8X3c8J5L8$3W2V1i4K6u0V1N6U0q4Q4x3X3g2Z5N6r3#2D9) 在 Android 设备上体验这些着色器。

## ShaderTest GLES：测试着色编译器的质量

我们从对背景色的渲染来开始测试，如果你等不及，可以跳过这部分。

传统的 GPU 测试模块专注于渲染速度或 API 功能的完备性。ShaderTest GLES 将另一度量维度——着色编译质量——加入测试中。毕竟，如果渲染出错，速度再快也用处不大！（原译文：“这意味着，优秀的渲染速度并不意味着良好的渲染效果如果渲染出错！”语序不当，已修正——译者注）

与工业界的软件工程师交谈时，我们经常听到 GPU 驱动开发工程师优先在知名游戏和应用程序——例如 Google Play Store 上排名前 100 的游戏——上测试他们的产品。由此导致的不良影响是，那些不太受欢迎的应用程序的开发者必须自行解决有关驱动的 bug，才能使应用程序在用户的设备上正确运行。

同时，由于 Android 系统向用户终端推送更新的速度慢得出奇，这就造成了一种循环现象：GPU 驱动 bug 一直得不到重视。一是主流游戏都运行良好（总有一种方法可以暂时处理这个问题）；二是若想要该应用程序能够继续使用，无论如何都得解决这个问题，因此不值得专门报告此漏洞。

（注：此处翻译不当，已修改！原文：

“同时由于 Android 系统向用户终端推送更新的速度烂得出奇，这就造成了一种自我延续效应，GPU 驱动 bug 并不会被视为一个严重的问题，因为主流的游戏都能很好地运行；并且要使应用软件运行，应用开发者必须自己解决问题，因此报告也无济于事。”）

这也使得开发者很难开发出优秀的着色器：只有驱动质量条件改善了，它才可能在一系列设备上运行。

## ShaderTest GLES 方法

（有关着色器和着色编译器的背景知识，请阅读此文 [99dK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6E0k6h3c8A6N6h3#2Q4x3X3g2U0L8$3#2Q4x3V1k6Q4y4o6m8S2k6X3c8Q4y4h3k6A6j5$3I4Q4x3V1k6U0M7X3q4K6K9r3g2K6i4K6u0V1K9r3q4F1k6%4y4Q4x3X3c8S2L8X3c8Q4x3X3c8U0M7X3q4*7P5g2)9J5k6r3W2E0j5h3N6W2M7#2)9J5k6r3u0&6i4K6u0V1j5h3c8V1K9h3&6Y4i4K6u0V1P5X3g2J5L8#2)9J5k6o6j5^5z5h3b7I4y4h3y4W2z5e0t1J5j5R3`.`.](https://bbs.kanxue.com/elink@024K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6E0k6h3c8A6N6h3#2Q4x3X3g2U0L8$3#2Q4x3V1k6Q4y4o6m8S2k6X3c8Q4y4h3k6A6j5$3I4Q4x3V1k6U0M7X3q4K6K9r3g2K6i4K6u0V1K9r3q4F1k6%4y4Q4x3X3c8S2L8X3c8Q4x3X3c8U0M7X3q4*7P5g2)9J5k6r3W2E0j5h3N6W2M7#2)9J5k6r3u0&6i4K6u0V1j5h3c8V1K9h3&6Y4i4K6u0V1P5X3g2J5L8#2)9J5k6o6j5^5z5h3b7I4y4h3y4W2z5e0t1J5j5R3`.`.)

ShaderTest GLES 由众多着色器家族组成，每个系列都包含一个用于渲染单帧参考着色器，以及为数众多的变种着色器——用来渲染视觉上与参考帧相同的帧，不过却是以完全不同的方式实现的。

变种着色器是以保留语义的变换（即在不影响渲染效果的前提下变换参考着色器的源代码）的方式从参考着色器获取相关参数。举例来说，就如同把参考着色器代码块转换成循环的形式：

```c
for (int i = 0; i < 1; i++) {
    // 参考着色器的原始代码
}
```

以上是一个简单例子。

![](https://bbs.kanxue.com/upload/attach/201802/747320_FKB4SE9BXUH89QR.jpg)

图：ShaderTest GLES 通过区分图片渲染中的不匹配问题、错误和渲染崩溃等问题，来找出图形驱动中的 bug。

ShaderTest GLES 重点关注以下 bug 和问题：

- 变种着色器被着色编译器拒绝——编译失败；
- 变种着色器致使驱动的某些部件崩溃——渲染崩溃；
- 变种着色器渲染出的图片与参考图片有肉眼可见的误差——渲染错误；
- 由于时间或内存限制导致驱动程序退出——资源占用问题。

编译失败和渲染崩溃通常意味着 bug。渲染错误通常是由误编译（miscompilation）所致，此时着色编译器产生错误的代码；有时图形系统中的浮点灵敏度也可能产生同样的问题。对于上述两种成因的问题，ShaderTest GLES 都能检测出来。我们在此处最大的进步便是：误编译触发的渲染错误问题，以传统的技术手段非常难以检测。资源占用问题让我们洞悉了图形驱动在非功能方面的限制。

## 渲染问题

Qualcomm GPU 存在更多的渲染问题：相较 ARM，其在测试中存在的问题多 5 个。

例如，以着色器 001 系列的测试结果为例，除了渲染崩溃外，ARM 总是得到与参考图像一致的渲染结果：

![](https://bbs.kanxue.com/upload/attach/201803/747320_MVQCYWQC9XW86GU.jpg)

图：着色器系列 001 的参考图像，所有的变种着色器都应当得到相似的结果。

Qualcomm GPU 大体上能得到良好的结果，不过却有一组图像存在明显错误：

![](https://bbs.kanxue.com/upload/attach/201803/747320_3DNDCTS6RFS2FVB.jpg)

图：Qualcomm GPU 上，我们得到的理想结果如左图，中图和右图为渲染错误图像，这大概是着色编译器 bug。

着色编译器系列 001 的参考着色器并不是浮点数敏感的，这些差异导致的渲染错误与由于着色编译器 bug 产生的误差相似。

我们也观察到 ARM 的渲染错误问题，比如着色器系列 007 的变种着色器 77：

![](https://bbs.kanxue.com/upload/attach/201803/747320_QH6URY48R868V4S.jpg)

图：着色器 007 系列的参考图像（左图），ARM S8 渲染出错的图像（右图）。

## 不确定性问题

我们的测试结果显示了 Qualcomm GPU 存在的两个不确定性问题：有时是着色编译器在编译期间崩溃；有时是编译成功但却渲染出错误的图像。这种情况在着色器 007 系列的变种着色器 123 和着色器 008 系列的变种着色器 51 上出现。

![](https://bbs.kanxue.com/upload/attach/201803/747320_F2KR7A8RVJ8Z43G.jpg)

图：每组图片包括一张理想图像以及一张经过 Qualcomm GPU 渲染的坏的图像。

## 渲染崩溃

这两种图形驱动在渲染图像样本时都存在为数不少的崩溃问题：Qualcomm 的 28 个，ARM 的 15 个。这些都是编译时段错误——致命信号 11（`SIGSEGV`）。

有趣的是，在渲染着色器 006 系列的 34 个变种着色器时，这两类图形驱动都不可避免地崩溃了。然而，正如我们在后续的文章中所见，其他图形驱动却可以很好地解决该问题。

## 编译失败

ARM 的图形驱动存在一个编译失败问题——在处理着色器 003 系列的 216 个变种着色器时。该问题是由于对三元运算符（`?:`）的处理不当造成的。Qualcomm GPU 存在更多的编译失败问题，包括编译器和连接器的错误，一共 9 个。尽管其中有些错误似乎是由于处理 `switch` 语句有关的单个基础问题引起的。

## 资源占用问题

我们的测试结果并没有发现针对 Qualcomm GPU 的资源占用问题，但是 ARM 在渲染着色器 003 系列的 122 个变种着色器时，却反馈了一个 `GL_OUT_OF_MEMORY` 错误。
