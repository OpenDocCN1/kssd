## 3.1 CKCL 获取路径

> `PspHostSiloGlobals+0x360/EtwpHostSiloState -> +0x1b0(假设为LoggerContextTable) -> LoggerContextTable[LoggerId] -> _WMI_LOGGER_CONTEXT`

![图片描述](https://bbs.kanxue.com/upload/attach/202512/832354_EHHXVRQXBW8EGRT.webp)

![图片描述](https://bbs.kanxue.com/upload/attach/202512/832354_BNKSZAWGWDBCBN6.webp)

`PspHostSiloGlobals+0x360`(记录与ETW相关数据的指针)与全局变量`EtwpHostSiloState`一致，这是在`EtwInitializeSiloState`函数中完成赋值的。其中，`rdi`指向`_ETW_SILO_STATE`结构体(未导出，暂且如此称呼吧...)。

![图片描述](https://bbs.kanxue.com/upload/attach/202512/832354_K2JTGRNT3ZC93T7.webp)

`LoggerContextTable[LoggerId]`的相关来源可参见函数`EtwpAcquireLoggerContextByLoggerId`，反汇编伪代码如下：

```
// PWMI_LOGGER_CONTEXT
// EtwpAcquireLoggerContextByLoggerId(
//     _In_ PVOID GlobalLoggerInfo,   // rcx: 全局 Logger 管理结构（如 EtwpGlobalLoggerInfo）
//     _In_ ULONG LoggerId,           // edx: 要获取的 Logger ID（0~255）
//     _In_ BOOLEAN AcquireRef        // r8b: 是否获取引用（rundown protection）
// );
__int64 __fastcall EtwpAcquireLoggerContextByLoggerId(__int64 a1, unsigned int a2, char a3)
{
    __int64 v4; // rbx
    __int64 v6; // rsi
    __int64 v7; // rcx
    __int64 v8; // rdx
    __int64 logger_context; // rbx

    v4 = a2;
    v6 = a2;
    if ( a2 >= *(_DWORD *)(a1 + 16) )
        LOBYTE(v7) = 1;
    else
        v7 = *(_QWORD *)(*(_QWORD *)(a1 + 432) + 8i64 * a2);
    if ( (v7 & 1) != 0
        || !(unsigned __int8)ExAcquireRundownProtectionCacheAwareEx(*(_QWORD *)(*(_QWORD *)(a1 + 424) + 8i64 * a2), 1i64) )
    {
        return 0i64;
    }
    if ( (unsigned int)v4 >= *(_DWORD *)(a1 + 16) )
    {
        logger_context = 1i64;
    }
    else
    {
        _mm_lfence();
        logger_context = *(_QWORD *)(*(_QWORD *)(a1 + 0x1B0) + 8 * v4);
    }
    if ( (logger_context & 1) != 0 )
    {
        ExReleaseRundownProtectionCacheAwareEx(*(_QWORD *)(*(_QWORD *)(a1 + 424) + 8 * v6), 1i64);
        return 0i64;
    }
    if ( a3 )
        KeWaitForSingleObject(logger_context + 648, 0, 0, 0, 0i64);
    if ( !*(_DWORD *)(logger_context + 336) ) // CollectionOn
    {
        LOBYTE(v8) = a3;
        EtwpReleaseLoggerContext(logger_context, v8);
        return 0i64;
    }
    return logger_context;
}
```

## 3.2 Syscall 与 ETW 触发

系统调用服务例程的执行位于`KiSystemServiceCopyEnd`函数中，通过`call rax`实现。图示可以看到，在执行系统调用前进行了两次全局标记的判断，即`KiDynamicTraceMask`和`PerfGlobalGroupMask`。前者用于动态调试信息记录，而后者用于 ETW 日志记录。

![图片描述](https://bbs.kanxue.com/upload/attach/202601/832354_FHW5JPW6B5PG8UV.webp)

`KiDynamicTraceMask__systemcall`代码段内部在“`call rax`”前后分别调用`KiTrackSystemCallEntry`/`KiTrackSystemCallExit`进行事件追踪。事实上，这两个函数内部分别调用`PerfInfoLogSysCallEntry`/`PerfInfoLogSysCallExit`进行 ETW 记录。

![图片描述](https://bbs.kanxue.com/upload/attach/202601/832354_5Z8ZACD5ESXUY4E.webp)

类似的，`PerfGlobalGroupMask__systemcall`内部采用了同样的策略。

![图片描述](https://bbs.kanxue.com/upload/attach/202601/832354_Y4HWRF3XQCK4TBN.webp)

值得注意的是，ETW 的触发依赖于`test dword ptr cs:PerfGlobalGroupMask+8, 40h`。

# 4. InfinityHook

我所参考的 [InfinityHook](https://bbs.kanxue.com/elink@ae6K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4K9i4c8Z5N6h3u0Q4x3X3g2U0L8$3#2Q4x3V1k6r3K9g2W2t1k6i4u0Q4x3V1k6u0L8X3k6A6L8X3W2@1P5f1S2G2L8$3E0b7M7X3!0Q4x3V1k6@1M7X3g2W2i4K6u0r3L8h3q4A6L8R3`.`.) 项目中，ckcl logger context 的定位依赖于`EtwpDebuggerData`特征码扫描定位，而栈帧中存储系统调用服务例程地址的定位依赖于`PerfInfoLogSysCallEntry`函数中的压入栈帧中的 magic。事实上，函数`PerfInfoLogSysCallExit`也同样存在 magic。可以通过两个函数的 magic 差异以判断当前栈帧是`call rax`前/后被触发，可进行定制化的操作。

```
.text:0000000140330EF0                            PerfInfoLogSysCallEntry proc near
.text:0000000140330F1F BF 33 0F 00 00                             mov     edi, 0F33h
.text:0000000140330F3D C7 44 24 28 02 18 50 00                    mov     [rsp+58h+var_30], 501802h
.text:0000000140330F4B 66 89 7C 24 20                             mov     [rsp+58h+var_38], di
.text:0000000140330F7A                            PerfInfoLogSysCallEntry endp

.text:0000000140330F90                            PerfInfoLogSysCallExit proc near
.text:0000000140330FBF BF 34 0F 00 00                             mov     edi, 0F34h
.text:0000000140330FDD C7 44 24 28 02 18 50 00                    mov     [rsp+58h+var_30], 501802h
.text:0000000140330FEB 66 89 7C 24 20                             mov     [rsp+58h+var_38], di
.text:000000014033101A                            PerfInfoLogSysCallExit endp
```

此外，由于记录`system__call`的`LoggerContext->GetCpuLock`触发路径是固定的，可通过计算调用栈来进行快速定位，以尽可能降低延迟。

> **path1 (`test dword ptr cs:PerfGlobalGroupMask+8, 40h`)**: `PerfGlobalGroupMask__systemcall` ==> `PerfInfoLogSysCallEntry`

> **path2 (`test cs:KiDynamicTraceMask, 1`)**: `KiDynamicTraceMask__systemcall` ==> `KiTrackSystemCallEntry` ==> `PerfInfoLogSysCallEntry`

可通过`trap_frame`指针进行快速定位，`_kthread::trap_frame`指针指向`trap_frame+0x00`，即`PerfGlobalGroupMask__systemcall`/`KiDynamicTraceMask__systemcall`的栈顶。需要注意的是，如果系统调用参数个数大于4，函数`KiSystemServiceGdiTebAccess`中将会进行栈扩展以复制来自用户态的参数。

