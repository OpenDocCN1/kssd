
# [原创]X86内核笔记_6_APC相关

## 0.APC概念

`APC`（异步过程调用）。具体概念百度很多文章都说了，通俗的来讲就是个官方的Hook回调，只是hook点是事先定义好的。

Windows维护了两种APC队列（内核APC、用户APC），队列中是一个个APC回调函数，在特定情况下Windows会遍历APC对列去执行每个APC回调函数。

### 杀死进程线程

在用户层我们调用`TerminateThread`一类的函数可以结束某个线程或进程，看上去好像是我们的进程把目标进程给干掉了。实际上一个线程不会被其他线程直接杀死，线程在运行时是独自占有CPU的。线程真正的死亡是“自杀”。结束线程的本质是：线程A向线程B插入一个APC，APC的功能是杀死B线程。当B线程调用一些系统API时，API内部会执行APC函数，从而让B线程杀死自己。

# 1.APC相关结构

> 初步有个概念，不需要背，逆向函数时自然就明白每个成员的作用了。

在进程线程章节中我们看到线程结构体`KTHREAD`有一些APC相关的成员，这里说明一下作用：

```C
struct _KTHREAD
{
UCHAR Alerted[2]; //0x3a
ULONG Alertable:1; //0x3c
struct _KAPC_STATE ApcState; //0x40
volatile ULONG ApcQueueable:1; //0xb8
UCHAR ApcStateIndex; //0x134
struct _KAPC_STATE* ApcStatePointer[2]; //0x168
struct _KAPC_STATE SavedApcState; //0x170
}
```

- +3A：`Alerted`：线程可警惕性。
- +3C：`Alertable`：是否允许被APC唤醒。
- +40：`ApcState` 当前进程环境下的APC队列。当进程A中线程X挂靠到进程B时时，原`ApcState`会保存至`SavedApcState`防止环境错误。此时再向线程X插入APC时，执行环境变为进程B。也就是`ApcState`中的APC只看当前进程环境。
- +B8：`ApcQueueable` 是否允许插入APC，1允许，0不允许。默认为1。如：当线程正在执行退出（销毁）时，Windows会将这个值置为0，防止继续插入APC。
- +134：`ApcStateIndex` `ApcStatePointer`的索引。
- +168：`ApcStatePointer` `ApcState`指针。
  - 当非挂靠时：0索引存`ApcState`，1索引存`SavedApcState`。
  - 当挂靠时：1索引存`ApcState`，0索引存`SavedApcState`。
- +170：`SavedApcState` 备用APC队列。当线程处于挂靠状态时，此处保存挂靠前的`ApcState`，防止A进程APC在B进程环境下运行导致线性地址解析错误。

### `_KAPC_STATE`

APC管理结构

```C
//0x18 bytes (sizeof)
struct _KAPC_STATE
{
struct _LIST_ENTRY ApcListHead[2]; //0x0
struct _KPROCESS* Process; //0x10
UCHAR KernelApcInProgress; //0x14
UCHAR KernelApcPending; //0x15
UCHAR UserApcPending; //0x16
};
```

- `ApcListHead`：APC链表，0号是内核APC链表，1号是用户APC链表。链表结构指向 `_KAPC` 的`ApcListEntry`成员。链表中每一个成员都是一个 `_KAPC->ListEntry` 结构。
- `Process`：当前线程正在运行的进程环境。
- `KernelApcInProgress`：内核APC是否正在执行。
- `KernelApcPending`：内核APC是否需要执行。为1时说明`ApcListHead`的0号链表有值。
- `UserApcPending`：用户APC是否需要执行。为1时说明`ApcListHead`的1号链表有值。

### `_KAPC`

APC成员结构

```C
//0x30 bytes (sizeof)
struct _KAPC
{
UCHAR Type; //0x0
UCHAR SpareByte0; //0x1
UCHAR Size; //0x2
UCHAR SpareByte1; //0x3
ULONG SpareLong0; //0x4
struct _KTHREAD* Thread; //0x8
struct _LIST_ENTRY ApcListEntry; //0xc
VOID (*KernelRoutine)(struct _KAPC* arg1, VOID (**arg2)(VOID* arg1, VOID* arg2, VOID* arg3), VOID** arg3, VOID** arg4, VOID** arg5); //0x14
VOID (*RundownRoutine)(struct _KAPC* arg1); //0x18
VOID (*NormalRoutine)(VOID* arg1, VOID* arg2, VOID* arg3); //0x1c
VOID* NormalContext; //0x20
VOID* SystemArgument1; //0x24
VOID* SystemArgument2; //0x28
CHAR ApcStateIndex; //0x2c
CHAR ApcMode; //0x2d
UCHAR Inserted; //0x2e
};
```

- `Type`：对象类型，APC为0x12。
- `SpareByte0`：保留。
- `Size`：KAPC结构大小。
- `SpareByte1`：保留。
- `SpareLong0`：保留。
- `Thread`：当前APC属于哪个线程。
- `ApcListEntry`：当前线程的APC链表。
- `KernelRoutine`：内核APC回调函数。
- `RundownRoutine`：特殊APC回调函数，如线程挂起、线程结束等。
- `NormalRoutine`：普通APC回调函数。
  - 当前为内核APC时，若此处有回调函数，则说明当前是个普通内核APC。若此处为空，则说明当前是个特殊内核APC。特殊内核APC插入时放在链表头部，普通内核APC插入时放到链表尾部。
  - 当前为用户APC时，此处存放用户APC处理函数。
- `NormalContext`：APC回调函数参数1。当前为用APC时，此处存放实际的用户APC回调函数。
- `SystemArgument1`：APC回调函数参数2。
- `SystemArgument2`：APC回调函数参数3。
- `ApcStateIndex`：当前APC插入链表的方式。（具体作用在逆向代码时体会）
  - 0：插入到原始环境的APC队列中。
  - 1：插入到挂靠环境的APC队列中。
  - 2：插入到初始化APC结构时的环境的APC队列中（使用`KTHREAD`的`ApcStateIndex`）。
  - 3：插入到插入APC结构时的环境的APC队列中（使用`KTHREAD`的`ApcStateIndex`）。
- `ApcMode`：APC模式，0为内核APC，1为用户APC。
- `Inserted`：当前APC是否已被插入到链表中。

## 小结

APC的插入位置与传入的`Enviroment`函数相关。如果是插入到了备用APC队列中则执行返回。若是普通APC队列中则继续进行多个判断。

当这个APC是自身线程插入给自身的，并且是个特殊内核APC，则会立马触发软中断执行。

如果这个APC是当前线程插入给其他线程的，且是个用户APC。当APC所属线程处于等待时，会尝试唤醒线程来执行APC。如果不是等待状态，则`UserOrNormalKernel`默认为0，插入后不执行APC。

如果这个APC是当前线程插入给其他线程的，且是个内核APC。当APC所属线程处于运行时，会直接触发软中断执行APC或通知其他核触发软中断执行。当APC所属线程处于等待时，会尝试唤醒线程来执行APC。其他状态则不会立马执行APC。

> 通过对比发现WRK上的插入逻辑还是有一些区别的，但是大体逻辑相差不大，说明APC插入逻辑是一直在优化细节的

# 4.APC派发函数逆向-KiDeliverApc

APC派发函数在很多函数中都会被调用。

![image-20211217140026542](upload/attach/202112/867232_5MEBHZWYBU6957H.jpg)

这里以`KiServiceExit`为例子，也就是系统调用返回时，会判断用户APC队列是否需要被执行。如果用户APC队列没有值则不派发APC。

![image-20211217140249207](upload/attach/202112/867232_PGQHVXZN47395G4.jpg)

其中派发APC的函数名为`KiDeliverApc`，在WRK中看一下函数声明：

```C
VOID
KiDeliverApc (
IN KPROCESSOR_MODE PreviousMode, //先前模式，要处理的APC模式
IN PKEXCEPTION_FRAME ExceptionFrame, //TrapFrame
IN PKTRAP_FRAME TrapFrame //TrapFrame
)
/*++
Routine Description:
This function is called from the APC interrupt code and when one or
more of the APC pending flags are set at system exit and the previous
IRQL is zero. All special kernel APC's are delivered first, followed
by normal kernel APC's if one is not already in progress, and finally
if the user APC queue is not empty, the user APC pending flag is set,
and the previous mode is user, then a user APC is delivered. On entry
to this routine IRQL is set to APC_LEVEL.
N.B. The exception frame and trap frame addresses are only guaranteed
to be valid if, and only if, the previous mode is user.
Arguments:
PreviousMode - Supplies the previous processor mode.
ExceptionFrame - Supplies a pointer to an exception frame.
TrapFrame - Supplies a pointer to a trap frame.
Return Value:
None.
--*/
```

## KiDeliverApc分析

`KiDeliverApc`函数中首先会检测是否有内核APC，如果有则先处理内核APC。
