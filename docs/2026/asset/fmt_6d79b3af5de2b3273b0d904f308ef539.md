设备指纹也是很核心的字段。这个功能底层获取也是通过 `netlink`，但是 `netlink` 的获取和处理比较复杂，我暂时还没有进行处理。

常用的获取方式包括 Java 获取和命令获取。如果需要进行替换，只需要处理命令行和 Java 的 Hook 即可。

命令行可以在对方执行命令之前，将命令替换成 `cat` 命令，去读取自己提前 Mock 好的文件，效果是一样的。

当然，还有另一种思路：其实这个字段可以由服务端获取，客户端二次上报后进行匹配。

```java
try {
    NetworkInterface networkInterface;
    InetAddress inetAddress;
    for (Enumeration<NetworkInterface> en = NetworkInterface.getNetworkInterfaces(); en.hasMoreElements();) {
        networkInterface = en.nextElement();
        for (Enumeration<InetAddress> enumIpAddr = networkInterface.getInetAddresses(); enumIpAddr.hasMoreElements();) {
            inetAddress = enumIpAddr.nextElement();
            if (inetAddress instanceof Inet6Address) {
                CLog.e("Java 获取 ipv6 " + inetAddress.getHostAddress());
            }
        }
    }
} catch (Throwable ex) {
    CLog.e("printf ipv6 info error " + ex);
}
```

### 包名随机路径

这个是一个非常核心的字段，即 `/data/app/随机Base64路径/base.apk`。

这个随机路径就是设备指纹。例如，一些大厂会读取微信的随机路径，获取微信的包信息，然后获取其中的随机路径。

比如微信、快手、京东、淘宝等应用的随机路径，可以作为核心的唯一设备指纹。只要不卸载微信或其他大厂 APK，设备指纹就永远不会发生变化，无论如何修改其 APK 内部的信息，都不会产生任何影响。

### 系统账号

一般来说，例如小米设备，登录指定账号后，可以得到一个账号 ID 信息，这个信息也需要进行处理。最好的办法是不登录账号。

### APK 签名

提到环境检测，不得不说的就是 APK 重打包检测。现在检测方法千奇百怪，这里也逐一罗列，把可能存在的风险点、检测方式和绕过原理详细叙述一下。当然，如果有更好的思路，也可以在文章下面留言。

想要绕过签名检测，最好或者说成本最低且有效的办法，就是修改完毕以后不签名，配合核心破解直接安装。

> 核心破解是 `LSP` 的模块，可以直接从 `LSP` 商店下载。它会 Hook APK 的系统签名解析方法，直接绕过签名检测流程，实现不签名直接安装。

首先说一下大厂或者一些企业壳的检测点。Java 层基础的获取签名方法，这里不再一一叙述。

#### Native 层获取签名方法

##### 检测

这里以 Hunter 源码为例进行介绍。

核心分为三部分：

- 通过 `svc openat` 读取 APK，并解析签名。
- 检测打开的 `fd`，对 `fd` 的路径进行反查。这里有一个细节：`buff[len] = '\0';`。如果攻击者没有修改 `readlinkat` 的返回值，就可以检测出来。
- 检测完路径以后，对文件权限进行反查。正常 APK 位于系统目录下，权限的 `GID` 和 `UID` 应该是 `1000`。如果攻击者忘记修改权限，也可以检测出来。

```cpp
const char *path = getApkPath(env, context);

// check svc apk sign
const string &string = checkSign(env, path).substr(0, 10);
LOG(INFO) << "apk sign  " << string;

if (string == Base64Utils::VTDecode("TFtCRU58UERAUQ==")) {
    // check sign success, but maybe svc io hook
    // check apk path
    int fd = my_openat(
        AT_FDCWD,
        reinterpret_cast<const char *>(path),
        O_RDONLY | O_CLOEXEC,
        0640
    );

    // check apk path
    char buff[PATH_MAX] = {0};
    std::string fdPath("/proc/");
    fdPath.append(to_string(getpid()))
          .append("/fd/")
          .append(to_string(fd));

    long len = raw_syscall(
        __NR_readlinkat,
        AT_FDCWD,
        fdPath.c_str(),
        buff,
        PATH_MAX
    );

    if (len < 0) {
        return getItemData(
            env,
            "APK签名验证失败",
            "readlinkat error",
            true,
            RISK_LEAVE_DEADLY,
            TAG_REPACKAGE
        );
    }

    // 截断，如果攻击者 Hook 了 readlinkat，
    // 只修改了参数，没修改返回值也可以检测出来。
    buff[len] = '\0';

    LOG(INFO) << "check apk sign path " << buff;

    if (my_strcmp(path, buff) == 0) {
        LOG(INFO) << "check apk sign path success ";

        // start check memory & location inode
        struct stat statBuff = {0};
        long stat = raw_syscall(__NR_fstat, fd, &statBuff);

        if (stat < 0) {
            LOG(ERROR) << "check apk sign path fail __NR_fstat<0";
            return getItemData(
                env,
                "APK签名验证失败",
                "fstat error",
                true,
                RISK_LEAVE_DEADLY,
                TAG_REPACKAGE
            );
        }

        // check uid & gid (1000 = system group)
        if (statBuff.st_uid != 1000 && statBuff.st_gid != 1000) {
            LOG(ERROR) << "check apk sign gid&uid fail ";
            return getItemData(
                env,
                "APK签名验证失败",
                nullptr,
                true,
                RISK_LEAVE_DEADLY,
                TAG_REPACKAGE
            );
        }

        size_t inode = getFileInMapsInode(path);

        if (statBuff.st_ino != inode) {
            LOG(ERROR) << "check apk sign inode fail "
                       << statBuff.st_ino
                       << " maps ->"
                       << inode;

            return getItemData(
                env,
                "APK签名验证失败",
                nullptr,
                true,
                RISK_LEAVE_DEADLY,
                TAG_REPACKAGE
            );
        }

        LOG(ERROR) << ">>>>>>>>>> check apk sign success! uid-> "
                   << statBuff.st_uid
                   << " gid-> "
                   << statBuff.st_gid;
    } else {
        LOG(ERROR) << "check apk sign path fail ";

        return getItemData(
            env,
            "APK签名验证失败",
            nullptr,
            true,
            RISK_LEAVE_DEADLY,
            TAG_REPACKAGE
        );
    }

    LOG(INFO) << "check apk sign success";
    return nullptr;
}
```

##### 对抗

针对上面的检测，对 `svc` 的 `openat` 拦截后，再对 `readlinkat` 和 `stat` 函数进行处理即可，很轻松就可以绕过检测。

很多加壳方案基本都会检测 Root、LSP 调用栈之类的内容，并不只是单一地检测签名。例如，发现开启了 `seccomp` 就会闪退，发现 Root 也会闪退。

#### Java 层获取签名方法

##### 检测

###### 检测 `CREATOR` 是否被替换

这里先说一下 Hunter 的 Java 层检测签名方法。这相当于反射 `CREATOR` 变量，该变量保存了一些 IPC 通信相关的内容。

很多攻击者会使用 `Lspatch` 进行打包，并对变量进行替换。这时可以检测该变量的 `ClassLoader` 是否为系统 `ClassLoader`，以防止被替换。

```java
try {
    Field creatorField = PackageInfo.class.getField("CREATOR");
    creatorField.setAccessible(true);

    Object creator = creatorField.get(null);

    if (creator != null) {
        ClassLoader creatorClassloader =
                creator.getClass().getClassLoader();
        ClassLoader sysClassloader =
                ClassLoader.getSystemClassLoader();

        if (creatorClassloader == null || sysClassloader == null) {
            return null;
        }

        // 系统的是 bootclassloader
        // 用户创建的都是 pathclassloader
        // 如果相等，则认为系统的被替换
        if (sysClassloader.getClass().getName()
                .equals(creatorClassloader.getClass().getName())) {
            return new ListItemBean(
                    "Apk签名验证失败！",
                    ListItemBean.RiskLeave.Deadly,
                    "Apk签名方法被替换!\n"
                            + creatorClassloader.getClass().getName()
                            + "\n"
                            + sysClassloader.getClass().getName()
            );
        }

        return null;
    }
} catch (Throwable e) {
    CLog.e("checkApkPackageInfoCreator error " + e);
}
```

###### Hook 服务端解析签名方法

在系统进行签名解析的时候进行签名替换。
