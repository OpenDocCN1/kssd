# 0x02. 反混淆流程（child\_func函数）

在复原后的main函数中我们可以看到子进程读取了60个字节的输入之后调用了`child_func`函数，接下来我们来看看如何复原`child_func`函数。

## 1. 混淆结构

还是先来看看混淆结构：

![图片描述](upload/attach/202201/910514\_NA4MCKZEH828XGK.png)

乍一看好像变成两层的控制流平坦化了？仔细分析发现原来是有几个基本块“特立独行”，它们的末尾是直接跳转，但没有像正常真实块那样跳转到预分发块，而是直接跳到了另外一个真实块：

![图片描述](upload/attach/202201/910514\_RXCFKYHCSKZKGQP.png)

至于为什么会出现这种特立独行的基本块，根据题目的源代码来看，应该是因为编译器的神奇优化，将这几个异或操作之后的赋值操作合并到一个基本块中了（也即是402AA0中的`mov [rax], cl`指令）：

![图片描述](upload/attach/202201/910514\_25JD62JWVQT3ASQ.png)

## 2. 处理方法

对于这几个特立独行的基本块，我们在分析时仍然将其当做真实块，但不要对它的跳转进行Patch。v1版本的去混淆脚本仍然适用，因为这几个基本块中没有`mov eax, xxx`指令，也就会被认为没有后继真实块，自然不会被Patch。

## 3. 反混淆效果检验

还是先运行一下，确定没有爆炸：

![图片描述](upload/attach/202201/910514\_YPR68ZNC5SHY4AC.png)

拖进IDA查看，基本是正常的：

![图片描述](upload/attach/202201/910514\_7AQ35RHNFFSCKWE.png)

用Biary Ninja复原一下函数调用，`ptrace`表明有父进程调试子进程的操作：

![图片描述](upload/attach/202201/910514\_PCKYBDPRSYZR6NX.png)

中间的一大坨循环暂且跳过，再看看最后的函数调用：

![图片描述](upload/attach/202201/910514\_AT6HHWC72BSU4GC.png)

中间的循环Binary Ninja的反汇编效果不是很好，所以还是用IDA看，结合最后的函数调用可以看出是一个**解密ELF文件然后执行**的操作：

![图片描述](upload/attach/202201/910514\_HECFGVZ67VFMG2S.png)

加密后的ELF前四个字节与输入的前四个字节异或，要得到合法的ELF头`0x7F和ELF三个字符`。于是得到了输入的前四个字符：
