### [激活 Moniker](http://www.kanxue.com/article-write.htm)

- 然而，初始化“script” `moniker`事实上并不会让你“运行”内部的脚本。
- 你仍然需要去“绑定”（“激活”）这个对象。
- 一个简单的实验可以证明该点。
- 用“script：`[0e1K9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8Y4y4W2M7Y4k6W2M7W2)9J5c8Y4c8W2M7%4c8Q4x3X3g2K6j5%4b7`.](https://bbs.kanxue.com/elink@d68K9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8Y4y4W2M7Y4k6W2M7W2)9J5c8Y4c8W2M7%4c8Q4x3X3g2K6j5%4b7`.)”作为参数调用`MkParseDisplayName()`并不会让你的代码得到执行（只有`scrobj.dll`这个`moniker dll`会被加载）。
- 但是在初始化对象时调用`BindToObject()`会给你带来一切。
- 这样一个“verb”动作执行尝试通过 PowerPoint 放映的“动画”特性去激活相关联的对象。
- `IMoniker::BindToObject()`被调用。
- 不像“RTF URL Moniker”漏洞，被利用的进程起始于 `OLE API OleCreateLink()`，而不是`OleRun()`。

### [对根本原因的总结](http://www.kanxue.com/article-write.htm)

- 这个漏洞是由于 `monikers` 可以通过一个 PowerPoint 放映文件来初始化和激活这一事实。
- 关键点在这里，在 PowerPoint 的动画特性中尝试去执行“verb”动作时激活了对象，这最终调用了 `moniker` 上的 `BindToObject()`。
- Windows 脚本组件（“script” `Moniker`）被设计用来发现和运行脚本，无需来自另外 OLE 对象的帮助。

## [微软是如何修复这些漏洞的？](http://www.kanxue.com/article-write.htm)

- 正如我们前面提及的那样，“RTF URL Moniker”漏洞和“PPSX Script Moniker”漏洞都被分配在 `CVE-2017-0199`。并且在 2017 年 4 月的安全更新中被修复。
- 但是，微软的补丁是如何修复它们的？
- 我们相当好奇。因此，我们对补丁做了一些逆向工程。
- 事实上，我们对结果感到有些惊讶。

### [COM](http://www.kanxue.com/article-write.htm) 激活过滤器

- 微软 4 月的补丁介绍/适配了一个我们叫做“COM 激活过滤器”的机制。
- 这是一个系统层面的改变（Windows 7 上在 `ole32.dll` 里），任何应用程序都适用。
- 这是一个“回调”风格的机制。
- 一个应用程序在初始化时设立这个“回调”机制。
- 这个“回调”例程（由应用程序所提供）将会在任何 COM 对象后续的实例中被调用。
- 这允许任何应用程序在运行时去控制哪个 COM 对象被禁止。

> 注意：我们研究的补丁位于 Windows 7 + Office 2010 环境。在 Windows 8/8.1/10 上，这项机制已经存在相当长的时间了，或许从 Windows 8 发布之时就有了。

- 详细地讲，引入下面的新函数：
  - `CoRegisterActivationFilter()`：用以注册过滤器的导出函数。
  - `FilterActivation()`：调用所提供的“回调”例程的内部函数。
- 微软在下列的内部函数里面增加了代码，在它们做真正的工作之前调用 `FilterActivation()`：
  - `ICoGetClassObject()`
  - `ICoCreateInstanceEx()`
  - `GetInstanceHelper()`
- 既然“COM 创建” APIs（例如，`CoCreateInstance`、`CoGetClassObject`）事实上调用了其中一个上述函数，程序执行流最终会调用“回调”例程。

### [IActivationFilter](http://www.kanxue.com/article-write.htm)

- `CoRegisterActivationFilter()`函数在 [MSDN](https://bbs.kanxue.com/elink@a6fK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6E0M7$3c8F1i4K6u0W2L8h3W2U0M7X3!0K6L8$3k6@1i4K6u0W2j5$3!0E0i4K6u0r3k6h3&6Q4x3X3c8#2M7#2)9J5c8X3I4A6j5Y4u0S2M7Y4W2Q4x3V1k6%4K9h3&6V1L8%4N6K6i4K6u0r3k6r3g2K6K9%4c8G2M7q4)9J5c8X3#2@1y4K6V1$3y4o6V1@1i4K6t1^5N6W2)9K6c8s2k6K6i4K6u0W2z5o6g2Q4x3U0W2Q4x3X3g2S2M7%4m8^5)上有描述。

### [它禁用了两个 COM 对象！](http://www.kanxue.com/article-write.htm)

- 两个被禁用的 `CLSIDs`：
  - `{3050F4D8-98B5-11CF-BB82-00AA00BDCE0B}`
  - 在“RTF URL Moniker”漏洞中使用的“htafile” OLE 对象！
  - `{06290BD3-48AA-11D2-8432-006008C3FBFC}`
  - 在“PPSX Script Moniker”漏洞中使用的“script” Moniker 对象！
- “htafile” OLE 对象和“script” Moniker 对象都不会在任何 Office 进程中被创建了。
- 既然 `MSO.DLL` 是一个任何 Office 应用程序共享的核心 `dll`，这是一个 Office 范围的“COM killbit”补丁，而不仅仅是为 Word/PowerPoint。

### [第二点思考](http://www.kanxue.com/article-write.htm)

- 这个补丁并没有杀死这两个对象。
- 这是一个通用的机制和一处轻量级的修改。
- 毋庸置疑，这并没有停止（另外潜在的）远程代码攻击。
- 我们担心被另外不安全的 COM 对象引入的潜在危险。
- RTF OLE “StdOleLink”特性仍然可以运行 `moniker`/COM 对象（除了黑名单列表里的那两个）。
- PPSX“动画”特性仍然可以运行 `moniker`/COM 对象（除了黑名单列表里的那两个）。
- 这是一个开放领域。
- 当用户安装第三方应用程序的时候，不安全的 COM 对象也许会被引入。

## [结论](http://www.kanxue.com/article-write.htm)

- 我们讨论了这两个有趣漏洞的根本原因。
- 它们都与 Office 能“运行” `moniker` 对象的能力相关；然而，这样的特性由两个不同的 Office 特性所提供：
  - RTF OLE “StdOleLink”
  - PPSX 有“verb”动作的动画
- 第一个特性的代码通过 URL `Moniker` 提供的 HTA 内容（“htafile” OLE 文件对象）来完成，第二个特性的代码通过“script” `Moniker`直接执行。
- 微软使用了一种通用机制来修复这两个逻辑漏洞，尽管我们仍担心潜在的风险。
- 我们建议安全人员持续关注 Office 中的 COM。
