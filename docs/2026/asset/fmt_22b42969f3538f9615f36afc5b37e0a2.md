## 小结

APC的插入位置与传入的`Enviroment`函数相关。如果是插入到了备用APC队列中则执行返回。若是普通APC队列中则继续进行多个判断。

当这个APC是自身线程插入给自身的，并且是个特殊内核APC，则会立马触发软中断执行。

如果这个APC是当前线程插入给其他线程的，且是个用户APC。当APC所属线程处于等待时，会尝试唤醒线程来执行APC。如果不是等待状态，则`UserOrNormalKernel`默认为`0`，插入后不执行APC。

如果这个APC是当前线程插入给其他线程的，且是个内核APC。当APC所属线程处于运行时，会直接触发软中断执行APC或通知其他核触发软中断执行。当APC所属线程处于等待时，会尝试唤醒线程来执行APC。其他状态则不会立马执行APC。

> 通过对比发现WRK上的插入逻辑还是有一些区别的，但是大体逻辑相差不大，说明APC插入逻辑是一直在优化细节的

# 4.APC派发函数逆向-KiDeliverApc

APC派发函数在很多函数中都会被调用。

![image-20211217140026542](https://bbs.kanxue.com/upload/attach/202112/867232_5MEBHZWYBU6957H.jpg)

这里以`KiServiceExit`为例子，也就是系统调用返回时，会判断用户APC队列是否需要被执行。如果用户APC队列没有值则不派发APC。

![image-20211217140249207](https://bbs.kanxue.com/upload/attach/202112/867232_PGQHVXZN47395G4.jpg)

其中派发APC的函数名为`KiDeliverApc`，在`WRK`中看一下函数声明：

```
VOID
KiDeliverApc (
IN KPROCESSOR_MODE PreviousMode,
/ / 先前模式，要处理的APC模式
IN PKEXCEPTION_FRAME ExceptionFrame,
/ / TrapFrame
IN PKTRAP_FRAME TrapFrame
/ / TrapFrame
)
```

## KiDeliverApc分析

`KiDeliverApc`函数中首先会检测是否有内核APC，如果有则先处理内核APC。

![image-20211217140806113](https://bbs.kanxue.com/upload/attach/202112/867232_G6XDCFPSH3C3EG4.jpg)

![image-20211217140825722](https://bbs.kanxue.com/upload/attach/202112/867232_2HXYVWRZG3Q2VYP.jpg)

如果内核APC链表没有值或者处理完毕了，就开始处理用户APC链表。处理用户APC时也会先执行`KernelRoutine`回调。

![image-20211217142646976](https://bbs.kanxue.com/upload/attach/202112/867232_SRWJGQABNE4NHXQ.jpg)

随后执行`KiInitializeUserApc`函数来派发用户APC，而不是像内核APC一样直接执行。

![image-20211217150254068](https://bbs.kanxue.com/upload/attach/202112/867232_UMKUJB6WD5CNMXK.jpg)

## KiInitializeUserApc分析

### 前导知识

用户APC的执行不像内核APC一样直接调用回调即可。用户APC需要在3环执行，因此在派发时需要将执行环境降到3环。执行APC结束后再返回0环。此时就会产生如下问题：

- 3环的代码从哪开始执行。
- 3环代码执行完毕后如何回到0环继续执行代码。

系统调用进0环时构造了一个`TramFrame`结构体用于保存3环进来时的环境，系统调用完成返回3环时通过`TrapFrame`中保存的寄存器信息来继续执行3环代码。因此通过更改`TrapFrame`中的值可以让当前代码在返回3环时改变执行位置。

由于执行完用APC后还要回到0环继续执行后续代码，但`TrapFrame`已经被更改。因此需要备份更改前的`TrapFrame`。`KiInitializeUserApc`中使用`CONTEXT`结构备份`TrapFrame`。

![image-20211220162159862](https://bbs.kanxue.com/upload/attach/202112/867232_36JMA6PUJQAZMSQ.jpg)

## KiUserApcDispather分析

函数内部直接取出栈顶的`NormalRoutine`并调用，将`NormalContext`、`SystemParam1`、`SystemParam2`作为参数传递。`NormalRoutine`为用户APC派发函数总入口，由Windows填充，函数为`kernel32!BaseDispatherApc`。

APC执行完成后通过`ZwContinue`函数回到0环继续处理剩余用户APC，并根据堆栈中的`Context`结构来填充`TrapFrame`结构。

![image-20211220162755338](https://bbs.kanxue.com/upload/attach/202112/867232_SMZ6VAFXTFPYGQS.jpg)

# 5.进程挂靠函数逆向-KeStackAttachProcess

进程挂靠本质为将某个线程的`CR3`切换为目标进程的`CR3`，使该线程的内存映射走目标进程的`GDT`。函数`KeStackAttachProcess`就是用于进程挂靠的。

首先判断`DPC`是否处理完成，如果还有`DPC`没处理直接蓝屏。

![image-20211223153519537](https://bbs.kanxue.com/upload/attach/202112/867232_NKSWNH9J4RHVZ3H.jpg)

如果当前线程已经是在目标进程的环境下了，直接返回。

![image-20211223153546756](https://bbs.kanxue.com/upload/attach/202112/867232_APUV2UKR6R9WPYZ.jpg)

否则直接调用`KiAttachProcess`开始挂靠，第一次挂靠和多重挂靠处理方式不同。

![](https://bbs.kanxue.com/upload/attach/202112/867232_MWQ2ZS4ZN5BN9GA.jpg)

`KiAttachProcess`有4个参数：当前线程、目标进程、原`IRQL`等级、原`ApcState`要保存在哪。

![image-20211223153723787](https://bbs.kanxue.com/upload/attach/202112/867232_V2Y2629FFUBUXUG.jpg)

将当前线程的`ApcState`队列备份至第四个参数中并清空`ApcState`。

![image-20211223153844548](https://bbs.kanxue.com/upload/attach/202112/867232_C8CKXHG8GHHR787.jpg)

如果是第一次挂靠，直接交换`ApcStatePointer`成员并设置挂靠状态。如果是多重挂靠则没必要设置了。

![image-20211223154016997](https://bbs.kanxue.com/upload/attach/202112/867232_XB3J2VAQUMFFABC.jpg)

然后调用`KiSwapProcess`进行`CR3`的切换。切换前还会判断进程空间是否被交换到磁盘上了，如果被交换到磁盘上会先恢复进程空间再切换`CR3`。

![image-20211223154133642](https://bbs.kanxue.com/upload/attach/202112/867232_FEF9YV3H4WWQ7S6.jpg)
