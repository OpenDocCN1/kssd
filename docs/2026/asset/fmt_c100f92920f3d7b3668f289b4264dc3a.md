
```c
    LIST_ENTRY        InInitializationOrderModuleList;  // +0x010
    PVOID             BaseAddress;                      // +0x018
    PVOID             EntryPoint;                       // +0x01C
    ULONG             SizeOfImage;                      // +0x020
    UNICODE_STRING    FullDllName;                      // +0x024
    UNICODE_STRING    BaseDllName;                      // +0x02C
    ULONG             Flags;                            // +0x034
    SHORT             LoadCount;                        // +0x038
    SHORT             TlsIndex;                         // +0x03A
    LIST_ENTRY        HashTableEntry;                   // +0x03C
    ULONG             TimeDateStamp;                    // +0x044
                                                        // +0x048
} LDR_MODULE, *PLDR_MODULE;
```

每个加载的模块都有一个`LDR_MODULE`结构体，其中的`BaseAddress`字段是模块在内存当中的基地址，`BaseDllName`指向一个`UNICODE_STRING`，其包含模块的名称(`kernel32.dll`等)。

而现在我们能够定位到`PEB_LDR_DATA`，如何转到`LDR_MODULE`啦？我们发现它们有三个'相同'的字段:

```c
    LIST_ENTRY        InLoadOrderModuleList;
    LIST_ENTRY        InMemoryOrderModuleList;
    LIST_ENTRY        InInitializationOrderModuleList;
```

所有的`LDR_MODULE`结构体我们通过三个`LIST_ENTRY`双向链表结构可以连接在一起，遍历寻找。而通过`PEB_LDR_DATA`的三个`LIST_ENTRY`字段中的某一个，可以定位到上述的双线链表中的'头'和'尾'节点。这样就可以遍历出加载的模块。

```asm
003F09B2    MOV EAX,DWORD PTR DS:[ESI+8]
003F09B8    MOV EDI,DWORD PTR DS:[ESI+20]
```

需要注意的是这两处的偏移0x8和0x20！第一反应有点蒙。

主要到程序是通过`InInitializationOrderModuleList`'’跳转‘到`LDR_MODULE`结构体中的，所以此时`ESI`的值相对于`LDR_MODULE`结构体在内存中的首地址是有0x10的偏移的！(双向链表连接的是`InInitializationOrderModuleList`字段而不是`LDR_MODULE`结构体)

所以，`0x8+0x10=0x18`,偏移指向的是`BaseAddress`，`0x20+0x10=0x30`的偏移指向的是:

`BaseDllName.Buffer`字段(模块名的Unicode字符串)

而`MOV ESI,DWORD PTR DS:[ESI]`，则通过双向链表遍历下一个节点数据(下一个模块信息)。

这样理解应该就比较容易了，当然有些知识点还没有扩展开来，作为下一步的学习计划，而就本文的主题而言，分析到这里就行了。

### 总结

a. 从`fs:[30h]`获取`PEB`地址  
b. 从`PEB`的0x0c偏移获取`PEB_LDR_DATA`地址  
c. 从`PEB_LDR_DATA`偏移0x1c]获取`InInitializationOrderModuleList.Flink`  
d. 从`InInitializationOrderModuleList.Flink`开始前向遍历循环链表  
e. 获取`LDR_MODULE`结构的`BaseAddress`、`FullDllName`信息。

## 5.远线程相关操作

继续往下，`sub_3F09D0`是获取`GetProcAddress`，思路和之前获取的方法差不多，这里为了节约篇幅就省略了。

有了`GetProcAddress`之后就把`LoadLibrary`的地址获取到，然后根据根据`API`对应的模块名称就可以将想要的`API`地址获取，还记得之前内存里面有一堆`API`字符串名称吧？然后还有一个指针数组专门指向这一堆`API`。

`sub_3F0970`通过随机函数，计算机名等生成0x20个16进制的随机数据。

`sub_3F1858`是将本进程的权限设置为调试权限，这样可以进行远线程注入。

`Sub_30F0F60`是进行远线程注入的主要部分:

首先明确注入的对象是`notepad.exe`进程

`Process32First`

`lstrcmpiA`

也许这个时候比较'安全'了吧，作者也不太采用一些特别的方法。

然后申请了一个0x1C00大小的内存空间，将`0x3F0300`的数据拷贝到了那里。

获取了`notepad.exe`进程句柄后，在其内存空间中申请了一块0x1C00大小的内存，并且拥有可执行权限:

## 7.补充

之前留了一个问题，`Sub_401490`函数里面第二次修复的数据到底起什么作用啦？

通过之前的分析，我们知道第二次修复的时候偏移为0x1000。`Notepad.exe`进程空间内的远线程的所在的内存区域首地址为0xAC0000，加上0x1000为0xAC1000，我们来看看相应的代码:

![](https://bbs.kanxue.com/upload/attach/201205/372322_npot7s51ocymrp6.png)

![](https://bbs.kanxue.com/upload/attach/201205/372322_xg5h0t092lmrn1f.png)

相对于0xAC1000的偏移:

```plaintext
0x02: AC0300
0x0A:AC0300
.。。。
0xc607:AC18E0
```

在最后一次进行数据修之前，那些偏移的值分别为:`3F0300`，`3F0300`，。。。`3F18E0`

而我们发现，第二次修复的这些数据要么是作为变量地址，要么是作为`API`的地址。如果不修复的话，引用肯定是错误的，这是不是有点类似于重定向的作用啦。我们我们可以判断出其作用就是重定向数据。
