## 一、整体布局

基于本期工程复杂度分析，由于只需调用 `MessageBoxA` 与 `RtlExitUserThread`，因此只需规划一块远程内存，即可同时放下 ROP 主链、字符串数据，以及 Win32 API 调用时的栈空间。

> 演示中划分 `1MB`，便于观察与调试；就本期链路而言，`4KB` 量级通常也够用。

**1MB 远程内存自高地址向低地址分为三区：**

```
1MB 远程内存 高地址
┌──────────────────────────────────┐
│ A 区 · 4KB · ROP 主链（控制中心） │
├──────────────────────────────────┤
│ B 区 · 4KB · 数据区（字符串等） │
├──────────────────────────────────┤
│ C 区 · 剩余 · MessageBoxA 专用栈 │
│ 及返回主链时的栈切换预留 │
└──────────────────────────────────┘
低地址
```

## 二、最难的第一步：`CreateRemoteThread`

**第一个 gadget：** `push rcx; pop rsp; ret`（chain entry pivot）

```
CreateRemoteThread
lpStartAddress : 第一个 gadget 的地址
lpParameter : A 区基址（blockBase + 0xFF000）指向 ROP 主链
DWORD WINAPI ThreadProc(
_In_ LPVOID lpParameter // 第一个参数 rcx -> A 区基址（blockBase + 0xFF000）
);
```

**讲解：**

1. `push rcx`：线程入口里 `rcx` 即 `lpParameter`，为 A 区基址（`blockBase + 0xFF000`），也是 ROP 主链起点。

2. `pop rsp`：`RSP` 切到 A 区 ROP 主链（`blockBase + 0xFF000`），后续 `ret` 从主链上依次取址。

3. `ret`：从主链 `[0] A+0x00` 弹出下一跳，进入 `gadget_pop_rcx_ret`（`pop rcx; ret`，见图 3 主链首颗 gadget）。

4. 至此，该线程执行流由 ROP 主链接管。

> **疑问：** 入口 gadget 能否用 `mov rsp, rcx; ret`？语义上不是更直接吗？

> **答：** 理论上可以——此时 `rcx` 已携带 A 区基址，一条指令即可完成栈切换。只不过，此小零件往往并不存在（这需要你根据具体不同的进程，使用 ROP 工具自行确认）。ROP 只能基于二进制里**现成**的指令片段拼装；理想路径一旦缺失，就必须用等价 gadget 组合（如 `push rcx; pop rsp; ret`）或改用其他启动方式，这是 ROP 工程里常遇到的约束。

## 三、`MessageBoxA` 四参数

如图 5 中选中的 gadgets 会在调用 `MessageBoxA` 前，按 x64 约定写好 `rcx`、`rdx`、`r8`、`r9`。其中两个是立即数，两个是指向 B 区字符串的指针：

- `rcx`（`hWnd`）：父窗口句柄，本期为 `0`（`NULL`）
- `rdx`（`lpText`）：正文，指向 B 区字符串
- `r8`（`lpCaption`）：标题，指向 B 区字符串
- `r9`（`uType`）：按钮与图标，本期为 `0`（`MB_OK`）

## 四、`RSP` 切到 C 区

如图 6 选中的 gadgets，在调用 `MessageBoxA` 前会把 `RSP` 从 A 区（主链所在）暂时切到 C 区。API 会在栈上压参、保存现场，耗栈深度事先难以估准；若仍让栈在 A 区向下生长，就可能覆盖 B 区里的字符串与布局。因此用 C 区单独承担这次调用的栈空间。

> 对于红队渗透测试，ROP 常用于拉起一个 Shell 进程，宿主进程的奔溃往往并不在意，这种情况下无需任何「合理栈安排工作」。如果用作后门，或者游戏外挂程序，则需要严格做好「合理栈安排工作」。

## 收尾问题

### 收尾问题一

**问：** 入口 gadget `push rcx; pop rsp; ret` 在目标进程里找不到，怎么办？

**答：** 这很常见——换进程、换模块组合后，ROP 工具未必能搜到完全匹配的连续片段。常见替代如下：

1. `SetThreadContext`：直接设定 `RIP` / `RSP` 指向 A 区主链，绕开入口 pivot。
2. PE 空隙写入：在 code cave 临时补齐所需指令，链跑通后再抹掉。

### 收尾问题二

**问：** `shadow space`（影子空间）是什么？对 ROP 有什么影响？如何规避？

**答：** x64 调用约定下，许多函数序言会向 `[rsp + offset]` 写入（参数 home space 等）。若在 A / C 区栈上紧排返回链与数据，Win32 API 的序言写入可能**覆盖**相邻槽位，导致无法按图 6 的布局回到主链。

规避时不必放弃调用 API，也不必找替代函数；更常见做法是沿调用链**下钻**到更底层实现（例如 `NtGdiSetPixel` 替代 `SetPixel`）。众所周知，底层函数往往更加「干净」，更加适合 ROP 的选择和调试。

## 本篇小结

- 本期在远程进程中划分 `1MB`（A 主链 / B 数据 / C API 栈），用 `CreateRemoteThread` + `push rcx; pop rsp; ret` 把 `RSP` 切到 A 区，再沿 ROP 链完成 `MessageBoxA` 与 `RtlExitUserThread`。

- 调用 Win32 API 前需把 `RSP` 切到 C 区，避免 API 栈破坏 B 区与主链布局；返回主链时再次切换 `RSP`。

- 入口 pivot 找不到时可换 `SetThreadContext` 或 PE 空隙；`shadow space` 会在 `[rsp+…]` 写入，破坏精心布局，可向下选用更底层 API 规避。
