
尽管有这些好处，但外场引用不如 DEFLATE 引用灵活。它不像 DEFLATE 引用那样链式：每个本地文件头不仅必须包含紧接的下一个头，而且还必须包含*所有*后面的头。随着接近 zip 文件的开头，额外字段的长度会增加。因为额外字段的最大长度为 2^16 - 1 个字节，假设文件名[按照描述分配](<https://bbs.kanxue.com/elink@a81K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2T1j5h3#2K6L8$3k6@1N6$3q4J5k6g2)9J5k6h3y4G2L8g2)9J5c8X3S2S2j5$3E0K6i4K6u0r3P5X3W2H3j5X3!0E0j5W2)9J5c8W2)9J5x3$3k6A6L8r3g2F1j5h3#2W2M7H3`.`.)>)，则最多只能引用 1808 个本地文件头（或带有 Zip64 的 1170 个）。（在 DEFLATE 的情况下，您可以对第一个（最短的）本地文件头使用额外字段引用，然后切换到剩余的 DEFLATE 引用。）另一个问题是，为了符合额外字段中的内部数据结构，必须选择 16 位类型标记（[`APPNOTE.TXT` 第 4.5.2 节](<https://bbs.kanxue.com/elink@504K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6H3K9%4N6S2M7X3g2Q4x3X3g2U0j5h3y4Z5k6h3k6D9P5g2)9J5k6h3&6W2N6q4)9J5c8Y4N6W2j5X3c8G2j5%4y4Q4x3V1k6U0j5i4y4W2M7%4c8#2k6r3W2W2M7#2)9J5c8V1q4b7f1p5&6a6g2p5g2Q4x3X3g2f1h3q4b7`.)>)，并将其置于引用的数据之前。我们想要选择一个类型标记，它将导致解析器忽略引用的数据，而不是试图将其解释为有意义的元数据。Zip 解析器应该忽略未知类型标记，因此我们可以随机选择类型标记，但是存在将来可能分配标记的风险，从而破坏了构造的兼容性。

![](https://bbs.kanxue.com/upload/attach/201907/805461_6UUV7KCQNXESMXT.png)

上图说明了使用带有和不带 Zip64 的 `bzip2` 的额外字段引用的可能性。两条线都有一个膝盖，在该拐点处，生长从二次转变为线性。在非 Zip64 情况下，膝盖出现在最大未压缩文件大小（2^32 - 2 个字节）到达时；在此之后，人们只能增加文件数量，而不能增加文件的大小。当文件数达到 1809 时，当我们在额外字段中用尽空间来引用额外标题时，该行完全结束。在 Zip64 情况下，膝盖发生在 1171 个文件处，之后文件的大小可以增加，但不是它们的数量。外场引用也有助于 DEFLATE，但差别很小，以至于在视觉上难以察觉，因此从图中省略了。它将 `zbsm.zip` 的压缩比提高了 1.2%；`zblg.zip` 0.019%；以及 `zbxl.zip` 0.0025%。

## 讨论

在相关工作中，[Plötz 等人](<https://bbs.kanxue.com/elink@287K9s2c8@1M7q4)9K6b7g2)9J5c8W2)9J5c8Y4y4S2M7W2)9J5k6h3W2F1k6X3!0J5L8h3q4@1K9h3E0Q4x3X3g2Z5N6g2)9J5k6r3u0W2M7X3I4A6L8W2)9J5k6h3c8W2i4K6u0r3M7X3g2K6k6h3q4J5j5$3S2Q4x3V1k6H3N6h3u0D9K9h3y4S2N6r3W2G2L8Y4y4Q4x3V1k6A6L8X3c8W2P5q4)9J5k6h3S2@1L8g2)9J5x3#2y4m8f1W2)9J5k6q4m8d9i4K6u0V1x3U0l9H3y4W2)9J5k6o6l9@1)>) 使用重叠文件创建了近自我复制的 zip 文件。Gynvael Coldwind [之前曾建议](<https://bbs.kanxue.com/elink@9a9K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4P5h3&6$3j5h3g2D9i4K6u0W2j5$3!0D9k6s2N6A6L8X3c8Q4x3X3g2H3L8q4)9J5c8W2)9K6c8X3W2V1i4K6y4p5y4U0R3J5)>)（幻灯片 47）重叠文件。

为了兼容性，我们设计了引用重叠 zip 炸弹结构，考虑了许多实现差异，其中一些显示在[下表中](<https://bbs.kanxue.com/elink@1c6K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2T1j5h3#2K6L8$3k6@1N6$3q4J5k6g2)9J5k6h3y4G2L8g2)9J5c8X3S2S2j5$3E0K6i4K6u0r3P5X3W2H3j5X3!0E0j5W2)9J5c8W2)9J5x3$3y4G2L8i4m8S2N6r3W2T1K9h3I4A6N6s2V1`.)>)。由此产生的结构与通常从后到前工作的 zip 解析器兼容，首先咨询中心目录并将其用作文件索引。其中包括 [Nail](<https://bbs.kanxue.com/elink@59fK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2#2M7$3g2F1K9i4S2Q4x3X3g2G2M7X3N6Q4x3V1k6U0L8$3&6X3k6i4u0W2L8X3y4W2i4K6u0r3L8%4y4V1K9e0p5@1i4K6u0r3N6r3g2U0K9r3&6A6j5$3q4D9i4K6u0V1M7$3g2K6M7$3W2G2L8Y4y4Q4x3V1k6H3M7X3g2K6k6h3&6@1j5i4c8A6L8$3&6Q4x3V1k6T1j5h3&6Y4k6i4u0@1)>)中包含的示例 zip 解析器，这是从正式语法自动生成的。但是，这种结构与“流”解析器不兼容，这些解析器是在没有首先读取中心目录的情况下从头到尾解析 zip 文件的解析器。就其性质而言，流式解析器不允许任何类型的文件重叠。最有可能的结果是他们只会提取第一个文件。它们甚至可能引发错误，就像[`sunzip`](<https://bbs.kanxue.com/elink@780K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6Y4K9i4c8Z5N6h3u0Q4x3X3g2U0L8$3#2Q4x3V1k6E0j5h3c8D9k6i4u0Q4x3V1k6K6N6h3&6*7K9i4l9`.)>)一样，它解析了最后的中心目录并检查它与已经看到的本地文件头的一致性。

如果您需要提取的文件以除本地文件头的字节之外的某个前缀开头，则可以在引用下一个头的非压缩块之前插入 DEFLATE 块。并非 zip 文件中的每个文件都必须参与炸弹构造：如果需要，您还可以包含普通文件以符合某种特殊格式。（[源代码](<https://bbs.kanxue.com/elink@201K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6%4N6%4N6Q4x3X3g2T1j5h3#2K6L8$3k6@1N6$3q4J5k6g2)9J5k6h3y4G2L8g2)9J5c8X3S2S2j5$3E0K6i4K6u0r3P5X3W2H3j5X3!0E0j5W2)9J5c8W2)9J5x3%4y4G2N6i4u0U0k6b7`.`.)>)有一个 `--template` 选项来促进这个用例。）许多文件格式使用 zip 作为容器；示例是 Java JAR、Android APK 和 LibreOffice 文档。

[PDF](<https://bbs.kanxue.com/elink@03eK9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6W2L8W2)9J5k6i4N6A6K9$3W2H3k6h3c8A6j5g2)9J5k6h3!0J5k6#2)9J5c8Y4N6A6K9$3W2Q4x3V1k6b7c8p5j5`.)>)在许多方面类似于 zip。它在文件末尾有一个交叉引用表，指向文件中较早的对象，它支持通过 `FlateDecode` 过滤器对对象进行 DEFLATE 压缩。我没有尝试过，但也许可以使用引用重叠的想法制作 PDF 压缩炸弹。甚至可能没有必要努力工作：`binaryhax0r` 在[博客文章](<https://bbs.kanxue.com/elink@883K9s2c8@1M7s2y4Q4x3@1q4Q4x3V1k6Q4x3V1k6T1K9h3&6S2M7Y4W2Z5j5i4R3H3M7W2)9J5k6h3u0D9L8$3N6K6M7r3!0@1i4K6u0W2j5$3!0E0i4K6u0r3x3U0l9I4x3q4)9J5c8U0l9$3i4K6u0r3k6X3I4S2N6r3g2V1k6h3y4G2k6r3g2Q4x3X3c8V1k6h3y4G2k6r3g2J5i4K6u0W2K9s2c8E0L8l9`.`.)>)中建议人们可以简单地在单个对象上指定多层 `FlateDecode`，这使得压缩炸弹变得容易。
